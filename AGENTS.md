# AGENTS.md — Project Map

A navigation file for AI collaborators: what this project looks like, where to find things, where to make changes, where new features should go, and what can be reused from where.

## What this project is

Backend for the NAATI CT translation practice software. .NET 10 + EF Core (Npgsql) + Supabase (hosted Postgres).
Standard four-layer Clean Architecture + CQRS (MediatR) + Repository/UnitOfWork.

**There is no frontend in this repo.** The design doc specifies a Next.js/React frontend, but nothing for it — no project, no scaffold, not even a folder — exists anywhere in this working directory. Don't assume one exists elsewhere in the workspace; it hasn't been started, and starting it is a separate scoping decision (App Router vs. other, TailwindCSS/shadcn vs. Ant Design, etc.) that hasn't been made yet.

## AI integration (Step 3): provider abstraction, config, and gotchas hit for real

- **Provider-neutral by design — 4 providers wired up for real: Claude, OpenAI, DeepSeek, Mimo.** `ILlmClient` (Application) knows nothing about any of them. Each is registered as a **keyed** service (`AddKeyedTransient<ILlmClient, ...>("claude" | "openai" | "deepseek" | "mimo")`, see `DependencyInjection.cs`). Handlers never inject `ILlmClient` directly or depend on a concrete provider — see the next bullet.
- **Which provider is active lives in the database, not config** (`llm_provider_settings` table, one row per provider, `is_active` marks the current one — a partial unique index guarantees at most one). **Which model that provider currently uses is a separate, dedicated table — `llm_provider_models` — not a column on `llm_provider_settings`.** `LlmProviderSettings` originally had its own `Model` string column alongside the `llm_provider_models` catalog, which meant two independently-editable copies of "the current model" that could silently disagree (PATCH the settings row's `Model` without touching the catalog, or vice versa). That was replaced (migration `20260829110847_AddLlmProviderModels`, still the *first* real deploy of this table since it was never applied before the fix) so `llm_provider_models` is the single source of truth: `IsCurrent` on that table (partial unique index **per `ProviderKey`**, not globally like `llm_provider_settings.IsActive`) marks which cataloged model is in effect for that provider. `ILlmClientResolver.GetActiveClientAsync()` (Infrastructure/Ai/LlmClientResolver.cs) loads the active `LlmProviderSettings` row, then separately loads that provider's current `LlmProviderModel` row, and wraps both into `ConfiguredLlmClient` so `ThinkingEnabled`/`Effort`/`ExtraSettings` (from settings) and `Model` (from the catalog's current row) become that call's defaults — a caller can still override any of them per-request on `LlmCompletionRequest`. If a provider has no current model row, `Model` stays null and the adapter's own appsettings-configured `Model` wins (same fallback behavior as before). `GenerateQuestionCommandHandler` calls the resolver instead of injecting `ILlmClient`. **Switching providers/models/effort is a data UPDATE, not a redeploy** — takes effect on the very next AI call. Table creation and seeding are hand-run SQL (`Infrastructure/Persistence/Migrations/{add,seed}_llm_provider_settings.sql`) by design — see "Known pitfalls" below for why this one didn't get auto-applied like everything else.
- **Mimo is both the seeded default and the code-level fallback.** `seed_llm_provider_settings.sql` inserts `mimo` as the only `is_active=true` row. Separately, `LlmClientResolver.FallbackProviderKey = "mimo"` is a hardcoded safety net in `GetActiveClientAsync()`: if `llm_provider_settings` has no `is_active=true` row at all (table not yet applied to Supabase, or someone deactivated everything), it logs a warning and resolves the keyed `mimo` client directly instead of throwing — so a missing/misconfigured table degrades to "use Mimo with its appsettings-configured defaults," not a hard failure of every AI feature. These two are independent: the seed decides what the *DB says* is active; the fallback decides what happens when the DB has *no opinion*.
- **Admin API for switching provider/model/thinking/effort at runtime** — `LlmProviderSettingsController` (`Api/Controllers/LlmProviderSettingsController.cs`), CQRS slice under `Application/Features/LlmProviders/`:
  - `GET /api/v1/llm-provider-settings` — lists all provider rows (`ListLlmProvidersQuery`).
  - `PATCH /api/v1/llm-provider-settings/{providerKey}` — partial update of `ThinkingEnabled`/`Effort`/`ExtraSettingsJson` (`UpdateLlmProviderSettingsCommand` — only non-null fields in the request body change; 404 via `NotFoundException` if the key doesn't exist). **Does not take a `Model` field** — that's `llm_provider_models`, see below.
  - `POST /api/v1/llm-provider-settings/{providerKey}/activate` — makes this provider the active one (`ActivateLlmProviderCommand`). Deliberately does **two sequential `SaveChangesAsync` calls** (deactivate every other currently-active row first, then activate the target) rather than one batched save — the partial unique index `ux_llm_provider_settings_single_active` is checked per-statement in Postgres, not deferred, so activating the new row before the old one's deactivation is committed would transiently violate it within the same transaction.
  - No create/delete endpoints — rows are meant to be seeded via SQL (one per known provider), matching the "reference data, hand-managed" treatment the rest of this table already gets.
- **`llm_provider_models` is both the catalog of known models per provider AND the single source of truth for which one is current.** `Domain/Entities/LlmProviderModel.cs` (`ProviderKey`, `Model`, `Label`, `IsCurrent`, `CreatedAt`) + `LlmProviderModelConfiguration.cs` — unique index on `(provider_key, model)` so a model can only be cataloged once per provider, plus a **partial unique index scoped to `provider_key`** (`ux_llm_provider_models_single_current_per_provider`, `WHERE is_current = true`) so each provider independently has at most one current model — unlike `llm_provider_settings.IsActive`'s partial unique index, which is global (one active provider across *all* rows), this one is per-provider (each provider can each have its own `IsCurrent=true` row simultaneously; selecting a model for `claude` doesn't touch `deepseek`'s current model). Endpoints on the same `LlmProviderSettingsController`:
  - `GET /api/v1/llm-provider-settings/{providerKey}/models` — list the catalog for one provider, each entry's `IsCurrent` included (404 if the provider itself doesn't exist).
  - `POST /api/v1/llm-provider-settings/{providerKey}/models` — add a new cataloged model, always `IsCurrent=false` (409 if `(providerKey, model)` already exists). **Adding a row here never changes what's currently running.**
  - `POST /api/v1/llm-provider-settings/{providerKey}/models/{model}/select` — makes an already-cataloged model the current one (`SelectLlmProviderModelCommand`; 404 if that exact `(providerKey, model)` isn't cataloged yet — add it first). Deliberately does **two sequential `SaveChangesAsync` calls** (un-set any other current row for the *same* `ProviderKey` first, then set the target), same reasoning as `ActivateLlmProviderCommand`. This is the only way to change what model a provider uses — `keeping claude-opus-5 cataloged while also using claude-sonnet-5` is exactly this: both stay in the catalog, `Select` just flips which one is current.
  - **No delete/rename endpoint for a catalog entry, and no way to un-select a current model back to "none" via the API** — consistent with this codebase's append-only-reference-data convention (see the CQRS section's Create+GetById+List-only rationale), but concretely means a typo'd model string added by mistake can only be fixed with direct SQL, and once a provider has a current model, switching to "no current model" (falling back to the adapter's appsettings default) isn't reachable except by picking another model first. Flagged, not yet requested to be fixed.
  - `ListLlmProvidersQuery`'s result now includes `CurrentModel` (nullable — joined from the catalog's `IsCurrent=true` row for that provider, null if none set) so the provider list still shows "what's running" at a glance without a second request.
  - Table creation/seeding follow the exact same hand-run-SQL convention as `llm_provider_settings`, but in **more steps since this table's deploy also had to migrate data off the old `llm_provider_settings.Model` column** — see "Known pitfalls" below for the exact run order (`add_llm_provider_models.sql` → `migrate_llm_provider_settings_model_to_catalog.sql` → optionally `seed_llm_provider_models.sql` → `remove_model_column_from_llm_provider_settings.sql`). The seed only adds models this project has actually confirmed (either live-tested or the exact model-id string independently verified) — currently just `claude-sonnet-5` (the migrate step already carries over whatever was actively in use, e.g. `claude-opus-5`). It deliberately does **not** include a guessed `deepseek-v4-pro` or similar — don't add an unverified model id to this table on a guess; confirm the exact string against that provider's own docs first (same rule that applied to Mimo's whole integration).
- **Secrets (API keys, Claude's WorkspaceId) are environment variables, not config or database** — keys `Llm:Claude:ApiKey`, `Llm:Claude:WorkspaceId`, `Llm:OpenAi:ApiKey`, `Llm:DeepSeek:ApiKey`, `Llm:Mimo:ApiKey`. No code change was needed for this — ASP.NET Core's default config pipeline already merges env vars (`Llm__Claude__ApiKey`, double-underscore = nested-key separator) and **.NET User Secrets** on top of `appsettings.json`; the only change was **removing** the `ApiKey`/`WorkspaceId` values that used to live in `appsettings.Development.json`.
  - **Local dev**: set once via `dotnet user-secrets set "Llm:Claude:ApiKey" "..." --project src/DeepLearning.Api` (repeat per key) — stored in `%APPDATA%\Microsoft\UserSecrets\<UserSecretsId>\secrets.json`, **outside the repo entirely**, auto-loaded by both `dotnet run` and `dotnet test`/`WebApplicationFactory` in Development (verified: the live tests pass with zero `export` needed once secrets are set this way). The Api project's `<UserSecretsId>` in the `.csproj` is just a random GUID pointing at that file — not a secret itself, fine to commit.
  - **CI/production**: real environment variables (`Llm__Claude__ApiKey=...`), same convention as `ConnectionStrings__DefaultConnection` further down this file — User Secrets is Development-only by design and won't be present there.
  - `BaseUrl`, `Model` (fallback only — the DB row's `Model` wins when going through the resolver), and the OpenAI-compatible per-provider fields stay in `appsettings.Development.json` since they aren't secret.
- **Two adapter classes, not four.** `ClaudeLlmClient` has its own shape (Anthropic's Messages API is structurally different — top-level `system`, content-block array, `thinking`/`output_config.effort`). OpenAI/DeepSeek/Mimo all speak the **same** OpenAI Chat Completions wire format (confirmed against each provider's own docs on 2026-08-29 via WebFetch, not assumed from memory — Mimo in particular is easy to get wrong by guessing), so they share **one** `OpenAiCompatibleLlmClient`, parameterized per provider by `OpenAiCompatibleOptions` (base URL, auth header name/prefix — Mimo uses a bare `api-key` header, not `Authorization: Bearer`, model id, and the output-length field name — DeepSeek uses `max_tokens`, OpenAI/Mimo use `max_completion_tokens`). Adding a 5th OpenAI-shaped provider needs **zero new C#**: one more named-options section + one more `AddKeyedTransient` line in `DependencyInjection.cs`, plus one more `llm_provider_settings` row. Adding a structurally different provider (Gemini, etc.) means one more adapter class shaped like `ClaudeLlmClient`.
- **`ThinkingEnabled`/`Effort` are honestly scoped to Claude only.** Claude: `ThinkingEnabled=false` sends `thinking:{type:"disabled"}` (omitted otherwise, runs adaptive); `Effort` maps to `output_config.effort`. For OpenAI/DeepSeek/Mimo, "thinking" isn't a universal boolean in the Chat Completions format — OpenAI's reasoning models use separate model ids or a Responses-API-only field, DeepSeek's reasoning is a distinct model name, Mimo's mechanism isn't confirmed — so rather than guess a field name, `OpenAiCompatibleLlmClient` leaves those two alone and relies on `ExtraSettings` (JSONB passthrough, merged directly into the request body — e.g. `{"reasoning_effort":"high"}`) as the generic escape hatch for whatever provider-specific knob is needed once actually confirmed against that provider's docs.
- **Raw `HttpClient`, not official provider SDKs — deliberate.** Matches the design doc's own "HttpClient+Polly" architecture, and a uniform raw-HTTP adapter shape is what actually makes swapping/adding providers cheap; the resilience pipeline (`LlmResiliencePipeline.cs`, via `Microsoft.Extensions.Http.Resilience` — Polly v8 under the hood) attaches to `HttpClient`, not to an SDK client, and is shared by all 4 providers' HttpClients.
- **Real bugs found only by actual live calls, all fixed**:
  1. Sending `"system": null` in Claude's request body (instead of omitting the key) got a real 400 ("system: Input should be a valid array") — fixed with `[JsonIgnore(Condition = JsonIgnoreCondition.WhenWritingNull)]` on `ClaudeLlmClient`'s request DTO.
  2. `AddStandardResilienceHandler`'s library defaults (10s per-attempt / 30s total timeout) are tuned for ordinary REST calls, not an LLM completion — a real Claude question-generation call with default adaptive thinking took longer than that and tripped `Polly.Timeout.TimeoutRejectedException`, uncaught by the original `catch (HttpRequestException)` clause, surfacing as a raw 500 instead of a clean `AiCallFailedException`→503. Fixed by widening the catch clause (both adapters) and raising `AttemptTimeout`/`TotalRequestTimeout` to 60s/180s in `LlmResiliencePipeline.Configure` — note the circuit breaker's `SamplingDuration` must stay ≥ 2× `AttemptTimeout` or `AddStandardResilienceHandler` fails **at startup** with an `OptionsValidationException`, not at call time.
  3. OpenAI's live test fails with 429 `insufficient_quota`/`credit_balance_exhausted` — that account has no billing credits. Not a code bug: the request is correctly authenticated (a bad key would be 401) and Polly correctly retried 3 times before giving up. DeepSeek and Mimo both succeeded for real on the same run, including again after secrets moved to env vars.
- **`prompt_templates` needed a new row for Step 3 to work at all**: the exam_specific/question_gen row seeded back in Step 1 only specifies content requirements (topic, difficulty), not an output contract — because the code that would consume it didn't exist yet. Added one new `shared_methodology`/`question_gen` row (subject_category=`translation`) via the real `POST /api/v1/prompt-templates` endpoint instructing the model to output *only* the JSON shape `GenerateQuestionCommandHandler` parses. If question generation ever starts failing to parse, check this row (`prompt_templates` where `template_type='question_gen' AND layer='shared_methodology'`) hasn't been deactivated or superseded incompatibly. This row instructs JSON output generically — it isn't Claude-specific, so it works unchanged no matter which provider is active.
- **Live-call tests are excluded from the default run** — see "Running the tests" below. `ClaudeLlmClientLiveTests.cs` and `OpenAiCompatibleLlmClientLiveTests.cs` (3 methods — one per OpenAI-shaped provider) both resolve their `ILlmClient` by DI key directly, bypassing `ILlmClientResolver`/the database entirely — they're testing the adapters, not the provider-switch mechanism. Requires the env vars above to be set.
- **Test-coverage gap, found by audit on 2026-08-29, closed same day**: no single test exercised the full real chain — real Postgres rows → `LlmClientResolver` querying them → keyed-DI resolution → an actual HTTP call. `LlmClientResolverTests.cs` (Infrastructure/Ai) covers the resolver's merge/fallback logic but against fake `ILlmProviderSettingsRepository`/`ILlmProviderModelRepository` implementations, never a real Postgres. `GenerateQuestionControllerTests.cs` swaps `ILlmClientResolver` itself for a fake (`FakeLlmClientResolver`), so it never ran the real resolver at all. The live-call tests above bypass the resolver entirely. Closed by `tests/DeepLearning.UnitTests/Api/LlmClientResolverFullChainTests.cs`: uses `ApiWebApplicationFactory.WithWebHostBuilder(...).ConfigureTestServices(...)` to re-register the keyed `"claude"`/`"deepseek"` `ILlmClient` *after* `AddInfrastructure`'s own registration (DI resolves the last registration for a given service+key, so the override wins) — the override still constructs the real `ClaudeLlmClient`/`OpenAiCompatibleLlmClient` classes, just wired to a `HttpClient` backed by an in-memory `HttpMessageHandler` returning a canned response instead of a real socket. Costs zero tokens/dollars, needs no API keys, not tagged `LlmIntegration` — runs on every `dotnet test`.

### Development-only AI call tracing (added 2026-08-30, user request)

- **`Infrastructure/Ai/AiTracingHandler.cs`** is a `DelegatingHandler` attached to every provider's `HttpClient` (`DependencyInjection.cs` captures the `IHttpClientBuilder` from `AddHttpClient<ClaudeLlmClient>`/`AddHttpClient("llm-openai-compatible")` into a variable, then calls `.AddStandardResilienceHandler(...)` and `.AddHttpMessageHandler<AiTracingHandler>()` on it separately — `AddStandardResilienceHandler` returns `IHttpStandardResiliencePipelineBuilder`, not `IHttpClientBuilder`, so it can't be chained directly into `AddHttpMessageHandler`, but both still append to the same underlying handler list in call order). Registered **after** the resilience handler, making it the *inner* handler — a Polly retry re-invokes everything inside it, so each logged "AI call #N" is a real outbound HTTP attempt, including retries, not one entry per logical `ILlmClient.CompleteAsync` call.
- **No-op outside Development** — checks `IHostEnvironment.IsDevelopment()` internally per call rather than being conditionally registered, so the DI wiring stays simple and the same either way; the check is cheap when it short-circuits. `dotnet run` picks up `Development` automatically via `Properties/launchSettings.json`; `WebApplicationFactory`-based tests default to `Production` (confirmed empirically — the full suite stayed clean, no tracing output), so **none of the test infrastructure needed to change**.
- **Logs the raw request/response JSON bodies verbatim** — deliberately at the HTTP layer rather than wrapping `ILlmClient`, so Claude's extended-thinking content comes along for free when thinking is enabled: `ClaudeLlmClient`'s own response parsing discards thinking blocks and keeps only the final text, but that parsing happens *after* this handler has already seen and logged the untouched raw body. No separate thinking-capture logic was needed.
- **Never logs headers** — `x-api-key` (Claude) and `Authorization`/`api-key` (the OpenAI-compatible clients) carry real secrets; only the method, URI, status code, elapsed time, and bodies are logged.
- **Correctness hazard avoided**: reading `HttpContent` off a one-shot stream exhausts it, which would leave `ClaudeLlmClient`/`OpenAiCompatibleLlmClient`'s own subsequent `ReadAsStringAsync()` call with nothing. Fixed by calling `LoadIntoBufferAsync()` before reading — once buffered, `HttpContent` supports being read any number of times. `AiTracingHandlerTests.cs` pins this down directly (asserts the response body is still intact after the handler runs, in both Development and non-Development modes, plus a content-less GET request) rather than trusting it by inspection.
- **Fixed a real, previously-dormant gap while wiring this up**: `Program.cs` never actually called `UseSerilog(...)` — `Serilog.AspNetCore` was referenced and `CorrelationIdMiddleware` was already pushing `CorrelationId` into `Serilog.Context.LogContext`, but with no Serilog sink ever configured, that push had nowhere to go. Fixed with a minimal `builder.Host.UseSerilog(...)` (Console sink, `Enrich.FromLogContext()`, `Microsoft.AspNetCore` overridden to `Warning`) — this is also what makes `AiTracingHandler`'s log entries carry the originating HTTP request's `CorrelationId` (the outbound `HttpClient` call runs inside the same async flow, and `LogContext` is `AsyncLocal`-based), giving real request-to-AI-call traceability without any extra plumbing.
- **Deliberately console-only, no separate file sink and no dev HTTP endpoint for browsing recent calls** — asked and the user picked Serilog console/structured logs only. If a dedicated `logs/ai-calls-.log` file or a `GET /api/v1/dev/ai-calls` browsing endpoint is wanted later, `Serilog.Sinks.File` and an in-memory ring buffer + dev-only controller are the natural next additions, not a redesign.

## Submissions & grading (Step 4): state machine, AI orchestration, structured-output validation

- **`Submission.TransitionTo(SubmissionStatus)`** (Domain/Entities/Submission.cs) is the whole state machine from design doc §4.1, encoded as a `Dictionary<SubmissionStatus, SubmissionStatus[]>` of legal next-states — `draft→submitted→grading→{grading_failed,graded}`, `grading_failed→{grading,grading_abandoned}` (the retry path — `grading_abandoned` itself is still never reached automatically, see the retry-executor note below; nothing auto-abandons a submission, that stays a manual/caller decision, deliberately not built), `graded→{under_dispute,archived}`, `under_dispute→{standard_revised,graded}`, `standard_revised→graded`. An illegal move throws `InvalidSubmissionStateException` (a `ConflictException`, so it's a 409, not a 400/404).
- **The idempotency guarantee under genuine concurrency — found broken by a full audit, fixed same day (2026-08-30).** There is deliberately no separate idempotency-key column on `submissions` (the design doc §7 calls for one, but the schema never grew a field for it); `Submission.TransitionTo(grading)` alone only ever guarded **sequential** misuse (a second, later grade() call on an already-`Graded`/`Grading` submission correctly 409s) — it did nothing for two `Handle` calls that both read `Submitted` before either commits, which would both pass the in-memory check and both persist their own `GradingResult`/`ErrorListItem` rows for the same submission. **Fixed with Postgres's built-in `xmin` system column as an EF optimistic-concurrency token** — `SubmissionConfiguration.Configure` maps a shadow `uint xmin` property with `.IsRowVersion()` (no new column, no data migration: `xmin` already exists on every Postgres table). `UnitOfWork.SaveChangesAsync` (Infrastructure) catches EF's `DbUpdateConcurrencyException` and translates it to `ConflictException` (Application can't reference EF Core directly, so the translation has to happen at the Infrastructure/Application boundary, not in the handler) — whichever of the two racing `SaveChangesAsync` calls loses gets a clean 409 instead of silently double-writing. **A migration exists (`20260830123650_AddSubmissionXminConcurrencyToken`) but its `Up()`/`Down()` are deliberately empty** — EF's migration diff sees a "new" xmin property and by default wants to `AddColumn`, but `xmin` is a reserved Postgres system column name; running that literal `AddColumn` would fail outright. The migration file exists only so `__EFMigrationsHistory`/`AppDbContextModelSnapshot.cs` stay consistent for future `migrations add` diffing — safe to run `dotnet ef database update` for it, it changes nothing in the real schema. Proven for real (not just by inspection) by `Integration/SubmissionConcurrencyTests.cs`: two separate `AppDbContext`s both load the same `Submitted` row, the first `TransitionTo(grading)`+save succeeds, the second's identical attempt throws `DbUpdateConcurrencyException` — deterministic (two contexts racing over one row), not a flaky `Task.WhenAll`-based timing test.
- **§4.2's AI-retry sub-state-machine — found half-real by the same audit (`AttemptCount`/`MaxRetries` were dead, every validation failure went straight to final_failure on attempt 1), fixed same day.** See the new "AI-call retry executor (design doc §4.2)" section below — the fix is shared across all 4 AI-orchestration handlers, not just grading, so it's documented once there rather than repeated per-step. `SubmissionStatus.grading_abandoned` is still never reached automatically post-fix — by design: the retry executor's job is "retry a few times within one grade() call," not "decide the submission is a lost cause." A submission that still ends up `GradingFailed` after the retry executor gives up is retried by the caller invoking grade() again, same as before.
- **`GradeSubmissionCommandHandler`** (Application/Features/Submissions/Commands/GradeSubmission) is the AI-orchestration handler, same shape as `GenerateQuestionCommandHandler` (Step 3): create an `AiCallLog` row + transition the submission to `Grading`, save immediately so both survive a hung call; build the prompt via `IExamConfigLoader`/`PromptRenderer` (unchanged from Step 3); call `ILlmClientResolver.GetActiveClientAsync()` (also unchanged — grading goes through the same DB-driven provider switch as question generation); parse the JSON response; validate it; persist `GradingResult`/`ErrorListItem` rows; transition to `Graded`. Any failure at any of those steps transitions the submission to `GradingFailed` and marks the `AiCallLog` `final_failure` before rethrowing (`FailAsync`, mirroring `GenerateQuestionCommandHandler`'s own `FailAsync`) — the caller retries by calling grade again, which is legal from `GradingFailed`.
- **Isolation (design doc §10.2) is structural, not a prompt reminder**: the handler only ever loads `Question.SourceText`, `Question.FlawedTranslationText` (TaskB only — see below), the submission's own `Content`, `MeaningCheckpoint` rows, and (TaskB only) `TaskBSeededError` rows. At the time this was originally written, `IReferenceTranslationRepository` didn't exist at all, which was itself the guarantee. Step 7 later added that interface (for reference-translation generation) and injected it into `CreateFollowUpQuestionCommandHandler` (for reference-translation follow-ups, see "Reference-translation follow-ups" below) — `GradeSubmissionCommandHandler` still does **not** inject it and has no code path to `reference_translations`, so the isolation guarantee itself is unchanged; only the "the interface doesn't even exist" reasoning for it is now historical.
- **TaskB grading sends `Question.FlawedTranslationText` (the full text the user was annotating), not just `SourceText`** — `TaskBSeededError.PositionStart/PositionEnd` are character offsets into that flawed text, so without the text itself the AI has positions and category labels with nothing to locate them against and can't judge whether the user's annotations are actually correct. This was missing from the first version of `BuildTemplateModel`/`add_grading_content_prompt_template.sql` — caught by inspection the same day, before the SQL file was ever run against real Supabase — and is now covered by `SubmissionsControllerTests.Grade_for_task_b_includes_the_flawed_translation_text_in_the_prompt_sent_to_the_ai` (uses a prompt-capturing fake `ILlmClient` to assert on the actual rendered prompt, not just on persisted output).
- **`ExamTypeId` is caller-supplied on `GradeSubmissionCommand`, not derived from the Submission/Question** — same precedent as `GenerateQuestionCommand`. `Question` has no `exam_type_id` column (design doc §9.4 defers that FK until a second exam type exists), and the MVP only has one exam type anyway, so there's nothing to derive it from.
- **Structured-output validation is a hard constraint in code, not a prompt reminder** (design doc §10.3 — grading is where this first actually applies, since `error_category`/`dimension_key` only exist on grading output, not on question generation): every `dimensionKey` in the AI's response — both in `dimensions[]` and in each `errors[].dimensionKey` — must match a `dimension_key` among the `AssessmentDimension` rows loaded for that exam type + task type, or `RubricVersionNotFoundException` (a 404) is thrown; every `errors[].errorCategory` must match a `category_key` among the loaded `ErrorTaxonomy` rows, or the call is rejected (`AiCallFailedException`, a 503) — an AI response referencing a category/dimension not on file is never persisted, matching how `GenerateQuestionCommandHandler` already treats an unparseable JSON response as a hard failure rather than trying to salvage it.
- **`IGradingResultInterpreter` picks per-`scale_type` pass/fail logic** (`Infrastructure/Ai/GradingResultInterpreters/{Band15,Score100,RubricLevel}Interpreter.cs`), registered as three `IGradingResultInterpreter` entries in DI and selected in the handler via `IEnumerable<IGradingResultInterpreter>.ToDictionary(x => x.ScaleType)`. **Only `Band15Interpreter` has real data behind it** — NAATI CT's `assessment_dimensions` are 100% `scale_type='band_1_5'`, and every `level_descriptions` row numbers Band 1 as the best performance and Band 5 the worst (verified against the seeded rubric text), so `Band15Interpreter` reads `"Pass: Band 2 or above"` as "Band 2 or numerically better" (`pass_bool = reported_band <= threshold_band`). `Score100Interpreter`/`RubricLevelInterpreter` exist so the dispatch is real rather than a stub, but their bucketing/comparison logic is a documented placeholder with zero real exam-type data to validate it against — revisit both once a second exam type actually uses either scale.
- **`grading_results.band` is a fixed `INT 1-5` column regardless of `scale_type`** (schema's own `ck_grading_results_band_range` CHECK constraint) — `Score100Interpreter` buckets a 0-100 score into that 1-5 range for storage (`>=90→1 … <40→5`), also an unverified placeholder given zero real score_0_100 data exists yet.
- **A new `prompt_templates` row was needed, same reason as Step 3's question_gen row**: the three grading rows seeded by `seed_naati_ct_en_zh.sql` only specify HOW to grade (rubric criteria, error taxonomies, task-type pass thresholds) — none of them existed to inject the actual material to grade or an output contract, because `GradeSubmissionCommandHandler` didn't exist when they were written. [add_grading_content_prompt_template.sql](src/DeepLearning.Infrastructure/Persistence/Migrations/add_grading_content_prompt_template.sql) adds one `shared_methodology`/`grading` row supplying `{{ source_text }}`/`{{ flawed_translation_text }}`/`{{ submission_content }}`/`{{ meaning_checkpoints }}`/`{{ seeded_errors }}` and the exact JSON contract (`dimensions[]`/`errors[]`, camelCase keys) `GradeSubmissionCommandHandler` parses — same hand-run-SQL convention as `llm_provider_settings`/`llm_provider_models`. **Applied to the real Supabase DB by the user on 2026-08-30.** The Testcontainers test DB never runs this file either way — tests seed their own minimal `PromptTemplate` rows directly. If grading ever starts failing to parse, check this row (`prompt_templates` where `template_type='grading' AND layer='shared_methodology'` with the content-injection variables) hasn't been deactivated.
- **Scriban's nested-dictionary iteration (`{{ for band in dim.level_descriptions }}`) had never been exercised before Step 4** — the seeded grading prompt's `{{ for dim in dimensions }} ... {{ for band in dim.level_descriptions }}` shape (iterating a `Dictionary<string,string>` nested inside a list of anonymous objects) was written into `seed_naati_ct_en_zh.sql` back before grading existed, so nothing had ever rendered it. Pinned down by `tests/DeepLearning.UnitTests/Infrastructure/Ai/PromptRendererDimensionRenderingTests.cs` (calls `PromptRenderer` directly, no DB) before `GradeSubmissionCommandHandler` was built on top of the assumption that it works.
- **`CreateSubmissionCommandHandler`** rejects a `TaskType` mismatch between the request and the target `Question` (a `Question` created as TaskType.B can't be submitted against as TaskType.A) via a manually-thrown `FluentValidation.ValidationException` — this lives in the handler rather than the `AbstractValidator`, same reasoning as `ImportUserQuestionValidator`'s cross-field checks: it needs a DB lookup (`Question.TaskType`) that a pure `AbstractValidator` (no repository access) can't do. `Submission.Content` is raw JSON text (same `jsonb`-backed convention as `Question.Brief`) — TaskA sends a JSON-encoded string, TaskB a JSON array of `{positionStart, positionEnd, errorCategory, correctedText}` annotation objects (`CreateSubmissionValidator.HaveConsistentTaskShape`, added 2026-08-30 — see below; positions are offsets into the question's `FlawedTranslationText`, same convention as `TaskBSeededError`).
- **No persisted `Draft` state** — `CreateSubmissionCommandHandler` constructs the `Submission` (C# default `Status=SubmissionStatus.draft`) and immediately calls `TransitionTo(Submitted)` in the same handler call, so `Draft` is real (exercised, not skipped) but never durably observable via a GET — matches the design doc's actual flow (the user submits an already-composed answer; there's no separate "save draft" interaction in scope).

## AI-call retry executor (design doc §4.2, added 2026-08-30, self-audit fix)

Fixes the "half-real §4.2 retry sub-state-machine" gap (see the top-of-file audit note) — applies identically to all 4 AI-orchestration handlers (`GenerateQuestionCommandHandler`, `GradeSubmissionCommandHandler`, `CreateFollowUpQuestionCommandHandler`, `GenerateDeepLearningContentCommandHandler`), documented once here rather than per-step.

- **Two genuinely different layers of "retry" exist, and only one of them was ever real.** `LlmResiliencePipeline.cs`'s Polly config retries HTTP-transport failures (timeouts/429/5xx) **inside** one `ILlmClient.CompleteAsync()` call — that was already correct (§7's "最多3次重试,指数退避+熔断"), untouched by this fix. What was missing: a 200-OK response whose *content* fails structured-output validation (malformed JSON, an `errorCategory`/`dimensionKey` not on file, etc.) used to be treated as an immediate, single-shot `final_failure` — Polly never sees this at all, since it only inspects transport-level outcomes, not response bodies.
- **`Application/Interfaces/IAiCallRetryExecutor.cs`** (impl: `Infrastructure/Ai/AiCallRetryExecutor.cs`, registered `AddSingleton` in `DependencyInjection.cs`) — `Task<T> ExecuteAsync<T>(AiCallLog log, Func<Task<T>> attempt, CancellationToken)`. Runs `attempt`; on any exception, increments `log.AttemptCount` and retries with exponential backoff + jitter (2s/4s/8s.../base delay configurable via constructor, defaults to 2s) as long as `AttemptCount < MaxRetries`, otherwise lets the exception propagate unchanged so the handler's own `catch`/`FailAsync` logic still decides the final state — this executor only owns *whether to retry*, never the failure-handling policy itself.
- **Each handler wraps only the "build request → call LLM → parse → validate" portion**, not the later entity-construction/persist step — a DB write failure isn't something re-prompting the AI would fix. For `GradeSubmissionCommandHandler`/`CreateFollowUpQuestionCommandHandler`/`GenerateDeepLearningContentCommandHandler` this meant splitting what used to be one big "everything from the LLM call onward" try/catch into two: an inner retry-wrapped one for "get a valid payload" and an outer one (unchanged in spirit) for "persist it." `GenerateQuestionCommandHandler` already had this shape as two separate try blocks, so it just needed the first one's body moved inside the executor's delegate.
- **Test-speed pitfall already hit and fixed**: the executor's real 2s/4s/8s backoff would make every existing "AI response is invalid" test sit through real multi-second sleeps for no product-relevant reason. `ApiWebApplicationFactory.ConfigureWebHost` overrides `IAiCallRetryExecutor` with a 1ms base delay for the whole API test collection — retry/attempt-count behavior is still exercised for real, just fast. Direct unit tests of the executor (`Infrastructure/Ai/AiCallRetryExecutorTests.cs`) construct their own instance with an explicit tiny delay the same way.
- **Tests**: `Infrastructure/Ai/AiCallRetryExecutorTests.cs` (pure, no DB/HTTP — succeeds first try without incrementing AttemptCount, retries then succeeds with AttemptCount matching the number of real calls, gives up after exactly `MaxRetries` attempts and rethrows the last exception, `MaxRetries=1` never retries at all, respects cancellation mid-backoff) and `Api/GenerateQuestionControllerTests.Generate_retries_on_a_malformed_ai_response_and_succeeds_once_the_ai_returns_something_valid` (end-to-end through the real API + real Postgres — a fake `ILlmClient` returns unparseable garbage twice then a valid response the third time, asserts 201 Created and that the persisted `AiCallLog.AttemptCount` is really `3`, not `1`).

## Auth (Supabase JWT), added 2026-08-30

Registration/login are entirely Supabase Auth's job now — this backend never issues or validates credentials itself, only validates the JWT Supabase Auth already issued (design decision, user-confirmed: front-end/clients call Supabase Auth's own REST API directly for sign-up/sign-in; nothing here proxies that). Auth is **opt-in, not `[Authorize]`-enforced** on any existing endpoint (user-confirmed decision) — every endpoint that used to require an explicit `UserId`/`CreatedBy` in the request body/query still accepts one, but a valid JWT's identity always wins when present. This was a deliberate choice to keep all 220+ pre-existing tests working unchanged (none of them send a JWT) while still letting new, authenticated calls omit the id entirely.

- **JWT verification**: `Program.cs` configures `AddAuthentication().AddJwtBearer(...)` against `Supabase:ProjectUrl` (new appsettings key — real value goes in `appsettings.Development.json`, same non-committed-secrets convention as `ConnectionStrings`; already filled in there since the Supabase project ref is derivable from the existing connection string). `options.Authority = "{ProjectUrl}/auth/v1"` — Supabase's newer **asymmetric JWKS signing** (user-confirmed this project's setup), so ASP.NET Core auto-discovers the public signing keys, no secret to store. `options.MapInboundClaims = false` so claims keep their raw JWT names (`sub`, `email`) instead of being remapped to the long `ClaimTypes.*` URIs. **Not yet verified against a real Supabase project's token** — the one piece flagged as needing a real end-to-end check: whether Supabase's `/auth/v1` truly serves the OIDC discovery document `Authority`-based config expects at `.well-known/openid-configuration`. If a real token ever fails to validate, this is the first thing to check — the fallback fix is `options.MetadataAddress` pointed directly at `{ProjectUrl}/auth/v1/.well-known/jwks.json` instead of relying on `Authority` discovery. If `Supabase:ProjectUrl` is unset (e.g. a fresh clone before the config is filled in), `AddJwtBearer`'s configure action returns early — no crash, tokens just never validate, same "missing config degrades gracefully" precedent as `LlmClientResolver`'s fallback.
- **`Application/Interfaces/ICurrentUserService`** (`UserId`/`Email`, both nullable) — impl `Api/Services/CurrentUserService.cs` via `IHttpContextAccessor`, reading the `sub`/`email` claims off `HttpContext.User`. Lives in Api (not Infrastructure) because `IHttpContextAccessor` is an ASP.NET Core hosting concept — same layering precedent as `GlobalExceptionHandler`/`CorrelationIdMiddleware`. Every controller that needs a user id now does `_currentUser.UserId ?? request.UserId` (or the equivalent for `CreatedBy`) — `SubmissionsController`, `FollowUpsController`, `ReviewLibraryController` (all 4 actions — `userId`/`request.UserId` are now `Guid?`, falling through to `Guid.Empty` only if truly neither source has one), `WeakPointsController`, `QuestionsController` (`Import`/`Generate`). **The Application-layer Commands/Queries themselves are unchanged** — they still just take a `Guid`/`Guid?` UserId parameter; only the Api-layer controllers gained a second, JWT-sourced input to prefer. No `[Authorize]` attribute anywhere yet — deliberately deferred, see above.
- **`Api/Middleware/EnsureUserProfileMiddleware.cs`** (registered after `UseAuthentication()`, before `UseAuthorization()`/`MapControllers()`) syncs a `public.users` row from a validated JWT's `sub`/`email` claims the first time that `sub` is seen — Supabase's `auth.users` and this project's own `public.users` are separate tables, and every FK-constrained table (`submissions.user_id`, `weak_points.user_id`, etc.) needs a `public.users` row to point to. Deliberately **not** a Postgres trigger on `auth.users` (the standard Supabase-idiomatic approach) — that would need hand-run SQL against a schema this project's own migration tooling doesn't manage, and wouldn't be testable via `WebApplicationFactory`. Instead: plain C# middleware, `GetByIdAsync` check + insert-if-missing, only runs (any DB work at all) for requests that actually carry a valid JWT — zero overhead for the anonymous/explicit-`UserId` path. A concurrent double-insert race for the exact same brand-new `sub` (two requests both see "doesn't exist yet") is caught (`DbUpdateException`, from the `Username`/`Email` unique indexes) and swallowed, not treated as an error.
- **`User.PasswordHash` is now nullable, not removed** — Supabase Auth owns credentials, so nothing writes to this column anymore, but design doc §7's "migrations only add, never remove" discipline (see the top-of-file audit note about the one migration that already broke this once) means the column itself stays. `UserConfiguration.cs` drops `.IsRequired()`; migration `20260830122531_MakeUserPasswordHashNullable` is a real, safe `AlterColumn` (loosening a constraint, not narrowing one) — **still needs `dotnet ef database update` run against the real Supabase DB**, not yet applied.
- **Removed entirely, not deprecated-in-place**: `RegisterUserCommand`/`Handler`/`Validator`/`Result`, `IPasswordHasher`/`Pbkdf2PasswordHasher`, and `UsersController`'s `POST` registration action. These won't ever be called again now that Supabase Auth owns sign-up — kept-but-dead code here would just be confusing, unlike the `PasswordHash` column (which stays because dropping *columns* specifically violates the stated migration discipline; deleting dead *C# code* doesn't). `UsersController` now only has `GetById` (profile reads still useful).
- **Tests**: `Api/JwtAuthenticationTests.cs` — self-signs a test JWT with a symmetric key (via `PostConfigure<JwtBearerOptions>` in `ConfigureTestServices`, overriding `Program.cs`'s real Authority-based config for just that test client) so tests never need a real Supabase project; proves a valid JWT creates the `public.users` profile row on first sight, a second request from the same JWT doesn't error or duplicate it, requests without any JWT still work off the body-supplied `UserId` (nothing broken for the 220+ pre-existing tests), and — the actual point of making this opt-in rather than replacing the old field — a JWT's identity overrides an explicit-but-different `UserId` in the request body. ## Follow-ups & Rubric calibration (Step 5): observing/active state machine, auto- vs. manual-activation

- **`standard_overrides` is NOT a mechanism for rewriting the official rubric** (user-corrected 2026-08-30, same day as the initial build — the first version of this section and of `add_followup_prompt_template.sql` framed it that way, which was wrong). `assessment_dimensions.level_descriptions` stays authoritative and untouched; a `StandardOverride` row is a **correction note that patches how the AI applies the standard** in a recurring situation. `OriginalRuleText`/`RevisedRuleText` hold "what the AI's flawed judgment was" / "what it should conclude next time in a similar situation," not before/after rubric wording.
- **The prompt asks the AI to self-review against an 8-category checklist of ways its own prior judgment could have been wrong** (expanded same day from an initial 2-example list, also by user feedback) — not just "missed an error": false positive (flagging a correct translation as wrong, often because the AI's own internally-generated "ideal phrasing" quietly became an invisible answer key — the same reference-answer contamination risk §10.2 already guards against for `reference_translations`, just harder to spot since it never touches that table), source-text misreading, error miscategorized (right that it's wrong, wrong about which of the 8 `error_taxonomies` categories), wrong dimension attributed (worse than miscategorizing — each dimension has its own Band text/pass threshold, so misattribution inflates one dimension and deflates another), Band severity miscalibrated, cumulative density missed (§5's individually-minor-but-taken-together principle — a missed *relationship* between errors, not a missed error itself), inconsistent repeat judgment (no external cause, the AI is just unstable call to call), and (TaskB only, rendered via `{{ if task_type == "B" }}`) position mismatch (matching the user's annotation to the wrong seeded error). See `add_followup_prompt_template.sql`'s top comment and its 重要说明 block for the full wording; `PromptRendererFollowUpTemplateRenderingTests.cs` pins down that the TaskB-conditional bullet actually renders/omits correctly around this much Chinese punctuation (same "exercise the exact Scriban shape before building on top of it" precedent as `PromptRendererDimensionRenderingTests.cs` from Step 4).
- **`CreateFollowUpQuestionCommandHandler`** (Application/Features/FollowUps/Commands/CreateFollowUpQuestion) implements design doc §2.1's Q/R/S/T nodes and §10.6's calibration mechanism, same AI-orchestration shape as `GradeSubmissionCommandHandler`/`GenerateQuestionCommandHandler`. It requires the submission to already be `Graded` — `submission.TransitionTo(SubmissionStatus.under_dispute)` is the first mutating step, so a submission still `Grading`/`GradingFailed`/etc. gets a 409 (`InvalidSubmissionStateException`) before any AI call is even attempted. The AI answers the question and returns a `verdict` (`user_correct`/`user_incorrect`/`partial` — never `pending`, which is rejected as invalid AI output); `user_correct` additionally proposes a `standardRevision` (`scope`/`dimensionOrRule`/`originalRuleText`/`revisedRuleText`). The submission always ends back at `Graded`: `user_incorrect`/`partial` transition straight back, `user_correct` passes through `StandardRevised` first per §4.1's state machine (`Graded → UnderDispute → StandardRevised → Graded`). Unlike `Submission`, `FollowUpQuestion` has no state machine of its own and no "in-progress" persisted row — it's only constructed and saved once a valid AI response has been parsed; a failed AI call just fails the `AiCallLog` and resets the submission back to `Graded`, so the user simply resubmits the follow-up.
- **A `standard_overrides` row is insert-only and always starts `observing`** (never immediately authoritative, per §10.6) — `PreviousOverrideId` is set to whatever `StandardOverride` is currently `active` for that exact `(Scope, DimensionOrRule)` pair (`IStandardOverrideRepository.GetActiveByRuleAsync`), or `null` if none exists yet, forming the audit chain. **`StandardOverride` has no `exam_type_id` column** (design doc §9.4 defers that FK, same as `Question`), so this matching is global across all exam types by design — tests must use a unique `dimensionOrRule` string per scenario or they'll pollute each other's confirmation counts (see `FollowUpsControllerTests`' per-test GUID-suffixed `dimensionKey`).
- **Two independent activation paths, both landing on the same `(status=active, EffectiveFrom=now)` update, and both deprecating whatever was previously active for that rule**:
  1. **Automatic, count-based** (`CreateFollowUpQuestionCommandHandler.TryAutoActivateAsync`, runs after every `user_correct` verdict): `IStandardOverrideRepository.CountDistinctQuestionsPendingAsync(scope, dimensionOrRule, baselineOverrideId)` counts **distinct `Question` ids** (joined `StandardOverride → FollowUpQuestion → Submission`) among `observing` rows sharing the same rule and the same baseline — grouping by baseline means a rule already promoted starts a fresh confirmation count for its own eventual successor. `StandardOverrideActivationPolicy.ShouldActivate` (pure/static, same testable-without-a-database convention as `DifficultyDistributionSelector`) compares that count against a threshold read from `generation_policy` (`policy_key='override_activation_threshold'`, value shape `{"confirmations_required": N}`, reusing the existing generic config table rather than adding a new one), falling back to `StandardOverrideActivationPolicy.DefaultConfirmationsRequired` (3, matching design doc §10.6's own "如3次" example) if no policy row exists yet — same safe-fallback convention as `difficulty_distribution`. **A real `override_activation_threshold` row (`confirmations_required: 3`, matching the fallback exactly) was seeded into the real Supabase `generation_policy` table by the user on 2026-08-30** — the fallback still applies to any future exam type that doesn't get its own row.
  2. **Manual, "经过一次人工复核"** (`Application/Features/StandardOverrides/Commands/ActivateStandardOverride` → `POST /api/v1/standard-overrides/{id}/activate`): promotes a specific `observing` row regardless of confirmation count. 409 (`ConflictException`) if the target isn't currently `observing` (already `active` or `deprecated`).
- **`Application/Features/StandardOverrides/Queries/{GetStandardOverrideById,ListStandardOverrides}`** + `StandardOverridesController` give read access to the chain (`ListStandardOverrides` takes an optional `OverrideStatus` filter) — nothing yet wires *active* overrides back into `GradeSubmissionCommandHandler`'s prompt (design doc's "上下文长度管理" retrieval/summarization strategy for feeding overrides into future grading calls is still open, not scoped into Step 5).
- **A new `prompt_templates` row was needed, same recurring reason as Steps 3-4**: no `template_type='followup'` row existed before this, because nothing consumed it. [add_followup_prompt_template.sql](src/DeepLearning.Infrastructure/Persistence/Migrations/add_followup_prompt_template.sql) adds one `shared_methodology`/`translation` row supplying `{{ question_text }}`/`{{ context_ref }}`/`{{ source_text }}`/`{{ submission_content }}`/`{{ grading_results }}`/`{{ errors }}`/`{{ dimensions }}`/`{{ error_taxonomies }}` and the JSON contract (`aiResponse`/`verdict`/`standardRevision`) `CreateFollowUpQuestionCommandHandler` parses. **Applied to the real Supabase DB by the user on 2026-08-30**, same hand-run-SQL convention as the grading/question_gen rows. The Testcontainers test DB never runs this file either way — tests seed their own minimal marker-string `PromptTemplate` rows directly (see `FollowUpsControllerTests.SeedGradingAndFollowUpTemplatesAsync`).
- **A pre-existing `exam_specific`/`followup` row (id `4ac934d3-85ca-4742-809c-ef1017d0cf90`, seeded by `seed_naati_ct_en_zh.sql` on 2026-08-29, before this handler existed) was actively harmful once the new shared_methodology row above joins it** — found by inspection before either file was run against real Supabase, same day both were written. `IExamConfigLoader.BuildPromptAsync` concatenates ALL active rows matching a template_type (not just the latest version), shared_methodology first then exam_specific after, so both would render into one prompt: (1) the old row references `{{ followup_question_text }}`, which was never actually `question_text` (Scriban silently renders an unknown variable as empty string, not an error, so the user's real question would just silently drop out of the prompt); (2) worse, its closing plain-text line ("最终请给出verdict:...,并说明理由") lands *after* the new row's strict "只输出JSON" instruction and directly contradicts it — since the handler parses the response as JSON and rejects anything else, this risked breaking every real NAATI CT follow-up call outright, not just degrading quality. Verified via `select * from prompt_templates where exam_type_id='11111111-1111-1111-1111-111111111111' and template_type='followup' order by version` showing `version=1` (the old id) `is_active=false` and `version=2` (a new id) `is_active=true`.
- **`grading_rubric`-scoped correction notes are validated against real `AssessmentDimension` rows, `translation_reference`-scoped ones aren't** — same design doc §10.3 "hard constraint in code, not a prompt reminder" philosophy as grading's `error_category`/`dimension_key` checks: if `standardRevision.scope == grading_rubric`, `dimensionOrRule` must match a `dimension_key` actually loaded for that exam type + task type, or the whole AI response is rejected (`AiCallFailedException`, 503). `translation_reference` scope has no equivalent taxonomy to check against (there's no "known translation rule" table), so it's only required to be non-empty.

## A real EF Core bug found and fixed while building Step 5: `HasDefaultValue` + an enum whose "default" member isn't ordinal 0

- **Symptom**: `CreateFollowUpQuestionCommandHandler`'s own API test asserted the response's `Verdict` was `user_correct` and got back `pending` instead — despite the handler explicitly setting `Verdict = payload.Verdict` (confirmed `user_correct` via a debug trace) right before `SaveChangesAsync`.
- **Root cause**: `FollowUpQuestionConfiguration` had `builder.Property(x => x.Verdict).HasDefaultValue(FollowUpVerdict.pending)` — and EF Core's convention is that `HasDefaultValue(...)` **implicitly sets `ValueGeneratedOnAdd`** on that property unless told otherwise. For a newly-`Add`ed entity, EF Core treats a property whose current CLR value equals **the type's default** (for an enum, always its ordinal-0 member — `FollowUpVerdict.user_correct`, since `FollowUpVerdict` is declared `{ user_correct, user_incorrect, partial, pending }`) as "not explicitly set", omits it from the `INSERT` column list, lets Postgres apply the column's `DEFAULT` (`'pending'`), and then reads the DB-generated value back into the in-memory entity (Npgsql's provider does this via `RETURNING`) — silently overwriting the `user_correct` the handler had just assigned. `FollowUpVerdict.user_incorrect` (ordinal 1) never triggered this, which is why the sibling test with that verdict passed from the start and the bug went unnoticed until the specific `user_correct` path was exercised.
- **Why nothing else had hit this yet**: every *other* `HasDefaultValue(...)` enum column in the schema happens to have its designated "default" value **coincide with ordinal 0** (`CallStatus.pending`, `Visibility.Private`, `SubmissionStatus.draft`, `MasteryLevel.New`, `WeakPointStatus.active`, `OverrideStatus.observing`) — so the same silent-omission mechanism fires just as often, it just happens to substitute back the exact value the code already intended, making it invisible. **One more genuine landmine found by inspection, not yet exercised by any test**: `WeakPointConfiguration`'s `Priority` column defaults to `Priority.medium`, but `Priority` is declared `{ high, medium, low }` — `high` is ordinal 0, `medium` is not — so the day `Features/WeakPoints` (Step 6+) explicitly constructs a new `WeakPoint` with `Priority.high`, it would silently save as `medium` instead, exactly like `Verdict` did.
- **Fix**: added `.ValueGeneratedNever()` to all 10 of these enum property configurations (`FollowUpQuestion.Verdict`, `WeakPoint.{Status,Priority}`, `AiCallLog.Status`, `Question.Visibility`, `StandardOverride.Status`, `Submission.Status`, `{UserVocabReview,UserPatternReview,UserKnowledgePointReview}.MasteryLevel`) — the application always sets these explicitly at construction time (matching this codebase's own convention of setting `CreatedAt`/etc. in code rather than leaning on DB defaults), so EF should never treat any of them as store-generated. **Confirmed via `dotnet ef migrations add` that this produces an empty migration (no `Up`/`Down` operations)** — `HasDefaultValue(...)` (the actual DB-level `DEFAULT` constraint, still needed for the hand-run SQL seed scripts and any direct-SQL insert) is unchanged; only EF's own "is this store-generated" bookkeeping changes, which is a design-time-only concept with no DDL representation — so `AppDbContextModelSnapshot.cs` was updated to match (10 `.ValueGeneratedOnAdd()` annotations removed) but no new numbered migration file was kept.

A user-requested audit of Steps 1-4 (prompted by re-reading the source prompt doc, `NAATI_CT_陪练评卷提示词.md`, added to the repo root that day) turned up several real gaps beyond what Step 4's own build already covered. - **Difficulty ratio (design doc §2's 简单30%/中等50%/困难20%) was never read anywhere.** `generation_policy` already had the right row seeded (`difficulty_distribution`, `{"easy":0.3,"medium":0.5,"hard":0.2}` — present in `seed_naati_ct_en_zh.sql`, which AGENTS.md's own "Known pitfalls" section already documents as run against Supabase; not independently re-verified via `psql` this session, so worth a quick `SELECT * FROM generation_policy WHERE policy_key='difficulty_distribution'` check before relying on it — the code has a safe 30/50/20 fallback either way, see below), but `GenerateQuestionCommand.Difficulty` was a required, always-caller-specified field with no code path that ever consulted the policy table. - **`CreateSubmissionValidator` had no TaskA/TaskB shape check for `Content`** — unlike `ImportUserQuestionValidator`'s `HaveConsistentTaskShape`, any valid JSON was accepted regardless of `TaskType`. Fixed: `HaveConsistentTaskShape` now requires TaskA's `Content` to be a JSON string and TaskB's to be a non-empty JSON array of `{positionStart, positionEnd, errorCategory, correctedText}` objects (this pins down the annotation shape the design doc only loosely specified as `{position,error_category,corrected_text}` — the project didn't have a settled convention for it before this).
- **A real stuck-submission bug**: if the AI reported a `band` outside grading_results' `1-5` CHECK constraint, or if anything else failed during the final persist step of `GradeSubmissionCommandHandler`, the submission could be left sitting in `Grading` forever — there's no `Grading→Grading` transition, so a stuck submission could never be retried. Root cause: entity construction + the final `SaveChangesAsync` happened outside any try/catch that would call `FailAsync`. ## Domain events & Step 6 downstream subscribers

Design doc §5's promise for `BE4`(Grading Orchestration Service): grading publishes one event, `BE7`/`BE8`/`BE12` (weak points / progress / review library) each subscribe independently, and a fourth future subscriber is "add an `EventHandler`", never "go change `GradeSubmissionCommandHandler`". Built and proven for real this session (2026-08-30), same day as the Step 5 work above.

- **`AggregateRoot` (Domain, still framework-free)** now carries `DomainEvents`/`AddDomainEvent`/`ClearDomainEvents` — a plain `List<object>`, not a MediatR type, so Domain still has zero package dependencies (design doc's own dependency-direction rule). `Submission`, `StandardOverride`, and `WeakPoint` are the three `AggregateRoot`s that currently raise events.
- **`Application/Common/DomainEventNotification<TDomainEvent>.cs`** is the only place a domain event touches MediatR — a generic `INotification` wrapper. `UnitOfWork.SaveChangesAsync` (Infrastructure) doesn't know the concrete event types at compile time, so it wraps each one via `typeof(DomainEventNotification<>).MakeGenericType(domainEvent.GetType())` + `Activator.CreateInstance` and publishes that. A handler subscribes to `INotificationHandler<DomainEventNotification<SubmissionGradedEvent>>`, not to `SubmissionGradedEvent` directly.
- **Dispatch order in `UnitOfWork.SaveChangesAsync`**: collect every tracked `AggregateRoot`'s pending events and clear them *before* calling `_context.SaveChangesAsync()`, then publish only *after* that save succeeds — a failed save never publishes anything for a transaction that didn't commit. A handler that itself calls `_unitOfWork.SaveChangesAsync()` to persist its own new aggregate (e.g. `WeakPoint` raising `WeakPointRecurredEvent`) goes through this exact same method recursively — no special-casing for nested saves, and no infinite loop risk since nothing currently subscribes to `WeakPointRecurredEvent`/`StandardOverrideActivatedEvent` (both are raised — by `WeakPoint` on a resolved→active flip, and by `StandardOverride` on both its activation paths — as forward-compatible hooks per the "adding a subscriber is free" design, but genuinely have zero listeners today).
- **The three `SubmissionGradedEvent` subscribers, and why each is scoped the way it is** (a user-requested clarifying discussion before writing any of this settled all three, since the design doc's own Step 6 roadmap line clashes with pieces of Steps 7/9 it also names — see each bullet):
  1. **`UpdateWeakPointsOnGraded`** (`Application/Features/WeakPoints/EventHandlers/`) — **rule-based, not a second AI call.** Design doc §2.1's flowchart shows an "AI归类薄弱点" step, but `ai_call_logs.request_type`/`prompt_templates.template_type` have no enum value for weak-point classification, and every signal it would need (`error_category`, `dimension_key`) already came out of the grading call that just ran. Buckets `error_list` rows by `"{DimensionName} - {ErrorCategoryName}"` per submission (deduped — 3 errors of the same category in one submission is one occurrence, not three) and upserts `weak_points`/`weak_point_occurrences`. Implements design doc §10.4's recurrence semantics for real: a `resolved` weak point seen again flips back to `active`, `RecurrenceCount` increments, `Priority` bumps to `high`, and a `WeakPointOccurrence.IsRecurrence=true` row is written — distinct from the ordinary "still active, seen again" case, which doesn't count as a recurrence. **There is no automated trigger anywhere yet that ever sets a `WeakPoint.Status` to `resolved`** — that's still open (not scoped into Step 6), so the recurrence branch is real but currently only reachable by manually flipping the status (exactly how `UpdateWeakPointsOnGradedTests` exercises it).
  2. **`UpdateProgressOnGraded`** (`Application/Features/Progress/EventHandlers/`) — **only ever touches TODAY's `progress_snapshots` row**, recomputed from source `grading_results` (not incremented in place — recomputing avoids the class of bug where an incremental average silently drifts from what a fresh query would show).   3. **`ExtractKnowledgePointsOnGraded`** (`Application/Features/ReviewLibrary/EventHandlers/`) — was written as **the Step 6 "最小闭环" version, not Step 7's AI extraction**, and was never changed once Step 7 actually landed (see "Deep learning module (Step 7)" below): if the graded `Question` already has `SentencePattern`/`VocabExpression` rows linked via their `QuestionId` FK, upsert `user_pattern_review`/`user_vocab_review` (increment `TimesEncountered`) for this user. ## Deep learning module (Step 7): isolated reference-translation generation, sentence patterns, vocab

Design doc §11.2's Step 7 line: "reference_translations独立调用生成、sentence_patterns/vocab_expressions". Built and proven the same day as Step 6 (2026-08-30).

- **`GenerateDeepLearningContentCommandHandler`** (`Application/Features/Questions/Commands/GenerateDeepLearningContent/`) is the AI-orchestration handler, same shape as `GenerateQuestionCommandHandler`/`GradeSubmissionCommandHandler`: create an `AiCallLog` row (`RequestType=AiOperationType.deep_learning`) + save immediately, build the prompt via `IExamConfigLoader`/`PromptRenderer` (unchanged infrastructure), call `ILlmClientResolver.GetActiveClientAsync()` (same DB-driven provider switch every other AI call goes through), parse the JSON response, validate it, persist, mark the `AiCallLog` success. Any failure marks the log `final_failure` and rethrows, mirroring every other AI-orchestration handler in this codebase.
- **Isolation is structural, not a prompt reminder — design doc §10.2 mirrored the other direction.** §10.2 already guarantees grading never reads `reference_translations`; this handler is the other half: its template model is **only** `{ TaskType, SourceText }` off the `Question` — there is no code path here that could pull in a `Submission`'s content, its `GradingResult`s, or `MeaningCheckpoint`s, so a generated reference translation can never be contaminated by (or leak into) any one user's specific answer. Proven for real, not just by inspection, by `DeepLearningContentControllerTests.Generate_is_isolated_from_grading_context_persists_content_and_is_idempotent_on_a_second_call`: it grades a submission whose `Content` carries a random marker string, then generates deep-learning content for the same question with a prompt-capturing fake client, and asserts the marker never appears in the captured prompt — the exact test design doc §11.2 calls for ("断言'参考译文生成请求'的实际payload里不包含评分相关上下文,验证隔离机制真正生效而非只是文档描述").
- **One AI call produces all three outputs together** (`referenceText`, `comparisonNotes`, `sentencePatterns[]`, `vocabExpressions[]`) — design doc §2.1 displays reference translation + sentence-pattern accumulation + vocab accumulation at the same "深入学习" flowchart step, so one call covers all three rather than three separate ones. `comparisonNotes` and each pattern's `breakdownSteps` are accepted as arbitrary JSON (`JsonElement`, stored via `.GetRawText()`) — same convention `Question.Brief` already uses — rather than a fixed shape, since design doc §6.9/§6.10 both type these columns as unstructured `JSONB`.
- **Idempotent per `Question`, not per `Submission`** — `reference_translations` has no `submission_id`/`user_id` column (design doc §6.9), only `question_id`, so a reference translation is generated once per `Question` and reused by every user who reaches that question's "深入学习" step afterward. `GenerateDeepLearningContentCommandHandler` checks `IReferenceTranslationRepository.GetByQuestionIdAsync` first and returns the cached row (`WasCached=true` on the result) without ever calling the LLM again if one already exists — proven by `DeepLearningContentControllerTests`' idempotency assertions (`FakeDeepLearningLlmClient.CallCount` stays `1` after a second call).
- **`comparison_notes` deliberately stays general, not per-user/per-submission — evaluated and decided against adding a field, user-requested review, 2026-08-30.** The design doc describes it as "与用户译文的对比说明" (comparison to *the* user's translation), but the table has no column to say *which* user/submission, unlike literally every other per-user/per-submission signal in this schema (`submissions`, `grading_results`, `error_list`, `follow_up_questions`, `weak_point_occurrences`, `user_pattern_review`, `user_vocab_review` all carry an explicit `user_id`/`submission_id` FK). That total absence, in a schema this consistent about the pattern everywhere else, reads as an intentional signal that `reference_translations` was meant to stay question-scoped, not a gap. Decision: `comparison_notes` stays general technique/pitfall commentary the AI writes alongside the reference text (already how `GenerateDeepLearningContentCommandHandler` implements it) — a literal per-submission diff is left to the frontend simply showing the user's own already-visible submission text next to the reference text, no additional AI-generated field needed for that. If a real product need for genuine per-submission comparison text ever surfaces, the additive fix is a new nullable `submission_id` column (or a separate join table) — cheap to add later and deliberately not built ahead of a real requirement (design doc §9.7's own YAGNI precedent).
- **New `AiOperationType` enum value: `deep_learning`** — added to the C# enum, the native Postgres enum (`ai_operation_type_enum`), and `prompt_templates.template_type`/`ai_call_logs.request_type` share this same enum, so no other schema change was needed. Migration `20260830093243_AddDeepLearningAiOperationType` adds the new label via `ALTER TYPE ... ADD VALUE` — **confirmed applied to the real Supabase DB by the user on 2026-08-30** (`dotnet ef database update`).
- **A new `prompt_templates` row was needed, same recurring reason as every prior step**: no `template_type='deep_learning'` row existed before this handler, because nothing consumed it. [add_deep_learning_prompt_template.sql](src/DeepLearning.Infrastructure/Persistence/Migrations/add_deep_learning_prompt_template.sql) adds one `shared_methodology`/`translation` row supplying `{{ task_type }}`/`{{ source_text }}` and the JSON contract (`referenceText`/`comparisonNotes`/`sentencePatterns[]`/`vocabExpressions[]`) the handler parses — same hand-run-SQL convention as the question_gen/grading/followup rows. **Applied to the real Supabase DB by the user on 2026-08-30** — the Testcontainers test DB never runs this file either way; `DeepLearningContentControllerTests` seeds its own minimal marker-string `PromptTemplate` row directly, same convention as `SubmissionsControllerTests`' TaskB flawed-text test.
- **New endpoints on `QuestionsController`**: `POST /api/v1/questions/{id}/deep-learning` (generate-or-return-cached) and `GET /api/v1/questions/{id}/deep-learning` (404 if nothing has been generated yet for that question — `GetDeepLearningContentByQuestionIdQueryHandler` throws `NotFoundException` off `IReferenceTranslationRepository.GetByQuestionIdAsync` returning null).
- **Tests**: `Api/DeepLearningContentControllerTests.cs` — isolation + persistence + idempotency (one test), 404-before-generation (one test), structured-output rejection on an empty `patternName` (design doc §10.3's hard-constraint philosophy, one test), and Step 6+7 composition (one test — generates deep-learning content for a question, then grades a fresh submission for that same question and asserts `ExtractKnowledgePointsOnGraded` picked up the newly-linked `SentencePattern`/`VocabExpression` with zero code changes to that Step 6 handler).

Design doc §7's separate "题库批量导入工具" (a standalone console tool) is still not built and remains out of scope — but a real deployment can now populate the seed pool through the running API without any hand-run SQL. `Api/GenerateQuestionControllerTests.A_seed_reference_question_imported_through_the_api_is_automatically_used_by_a_later_generate_call` proves the full loop end-to-end through HTTP only: import with `IsSeedReference=true` → generate a matching question with no explicit `SeedQuestionIds`/`CategoryId` → the traceability endpoint shows the imported question was picked up automatically.
  - **This also exposed (and required fixing) a latent fragility in the Step 8 traceability test itself**: `Generate_records_which_seed_reference_questions_were_used_and_they_are_traceable_via_the_api` originally asserted `Assert.Single(links)`, which silently assumed it was the only test in the whole `ApiCollection`-shared DB that could ever produce an `IsSeedReference=true`/`TaskType.A`/`Difficulty.medium` row — true only because nothing else *could* create one yet. The moment the API gained a real way to do that, other tests' rows started legitimately landing in the same take-3 automatic pool and the exact-count assertion broke. Fixed the same way as `QuestionBankRepositoryTests`: `Assert.Contains`/`Assert.DoesNotContain` on the specific seed ids instead of an exact count — `matchingSeed` is still guaranteed present (created immediately before the generate call, within the same sequential, non-parallelized collection, so nothing more recent can exist yet), `nonMatchingSeed` (wrong difficulty) is still guaranteed absent regardless of pollution.
- **Tests**: `Integration/QuestionBankRepositoryTests.cs` (Testcontainers Postgres — seed-candidate task-type/difficulty/category filtering, category tagging reflected in `HasCategoryMapAsync`/`ListCategoryIdsAsync`; list-membership assertions rather than exact-count, since `PostgresCollection` shares one DB across the whole collection and other tests' rows can coexist), `Api/QuestionBankCategoriesControllerTests.cs` (CRUD, 404 on unknown parent, tagging flips `InBank` + `GetQuestionByIdResult.CategoryIds` and the tagged question then appears in a category-filtered list, 409 on double-tagging), `Api/ReviewLibraryControllerTests.cs` (domain/scenario/frequency-tag filtering, review-state overlay including the never-reviewed default, mark-reviewed upsert proving `TimesEncountered` stays untouched across mastery updates, 404 on an unknown pattern, 404 — not a raw 500 — on an unregistered user), `Application/Features/Questions/GenerateQuestionValidatorTests.cs` (the `SeedQuestionIds` cap/duplicate/empty-guid rules), on `QuestionsControllerTests`: `Import_with_is_seed_reference_true_sets_origin_and_source_type_to_the_real_exam_pair` / `Import_without_specifying_is_seed_reference_defaults_to_false_...`, and on `GenerateQuestionControllerTests`: the seed-reference-links traceability test (now pollution-safe, see above), manual-selection bypass (404 unknown id, 400 non-seed id, and the bypass-proving test itself), the full API-only end-to-end loop test described above, the retry-executor end-to-end test (see "AI-call retry executor" above), and the two weak-point-targeting tests (`TargetWeakPoints=false` never injects a hint even with an active weak point on file; `TargetWeakPoints=true` + a forced `weak_point_targeting_ratio=1.0` policy + two weak points of different priority injects only the higher-priority one's category). `Application/Features/Questions/WeakPointTargetingSelectorTests.cs` covers the ratio/roll pure-function logic directly.

## Directory structure and dependency direction

```
DeepLearning.Domain          <- no dependencies at all, pure C#
    ↑
DeepLearning.Application     <- depends on Domain
    ↑
DeepLearning.Infrastructure  <- depends on Application + Domain
    ↑
DeepLearning.Api             <- depends on Infrastructure + Application
```

- **Domain**: entities (`Entities/`), enums (`Enums/`), domain events (`Events/`), domain exceptions (`Exceptions/`), base classes and shared value objects (`Common/`). Doesn't reference any other project, and doesn't reference frameworks like EF/MediatR.
- **Application**: business use cases. `Features/<BusinessDomain>/Commands|Queries/<UseCaseName>/` holds the CQRS four-piece set; `Behaviors/` holds the MediatR pipeline; `Interfaces/` holds abstractions for repositories and external services (LLM, etc.); `Common/` holds cross-use-case shared types (pagination, etc.). Only depends on Domain — doesn't reference concrete implementations like EF Core or Npgsql.
- **Infrastructure**: where the interfaces defined by Application land. `Persistence/` is EF Core + Npgsql (DbContext, Configurations, Migrations, Repositories, UnitOfWork). If external services like an LLM API or email get added later, they should also get a new folder in this layer implementing Application's interfaces.
- **Api**: the ASP.NET Core entry point. `Controllers/` only does parameter binding and calls `IMediator.Send(...)` — no business logic. `Middleware/` holds cross-cutting concerns like global exception handling.

## Database: Supabase (Postgres) + EF Core

- The connection string key is consistently `ConnectionStrings:DefaultConnection`. For local development it's filled in at [appsettings.Development.json](src/DeepLearning.Api/appsettings.Development.json) — **this file is excluded by `.gitignore` and isn't committed**, so after a fresh clone / on a new machine you need to fill it in by hand again (it contains the real Supabase password). Production goes through the `ConnectionStrings__DefaultConnection` environment variable.
- Runtime read entry point: [DependencyInjection.cs](src/DeepLearning.Infrastructure/DependencyInjection.cs). Design-time entry point for `dotnet ef` commands: [AppDbContextFactory.cs](src/DeepLearning.Infrastructure/Persistence/AppDbContextFactory.cs) (only reads environment variables, not `appsettings.json` — remember to `export`/`$env:` the environment variable before running `dotnet ef` commands locally).
- The project uses `EFCore.NamingConventions`'s snake_case convention globally (see `.UseSnakeCaseNamingConvention()` in [AppDbContext.cs](src/DeepLearning.Infrastructure/Persistence/AppDbContext.cs)). A C# property like `CreatedAt` is automatically mapped to the column `created_at` — no need to hardcode column names in Configurations unless overriding the default rule.
- **Native Postgres enums**: every time a new enum is added, it needs to be registered in two places — missing either one causes runtime/design-time errors:
  1. `modelBuilder.HasPostgresEnum<T>(name: "..._enum", nameTranslator: ...)` in `AppDbContext.OnModelCreating`
  2. `o.MapEnum<T>("..._enum", nameTranslator: ...)` in [NpgsqlEnumConfiguration.cs](src/DeepLearning.Infrastructure/Persistence/NpgsqlEnumConfiguration.cs)

  Most enums use `NpgsqlNullNameTranslator` (the C# member name matches the SQL label verbatim); `Visibility`/`MasteryLevel` use `NpgsqlSnakeCaseNameTranslator` instead because their labels contain C# reserved words (`new`/`private`) — the C# members are written in PascalCase (`New`/`Private`) and the snake_case translator converts them back to the label.
- [Migrations/schema.sql](src/DeepLearning.Infrastructure/Persistence/Migrations/schema.sql) is the script originally run by hand in the Supabase SQL Editor to create the schema — it is **not** exported from EF Migrations. Its own comments state that all future schema changes must go through `dotnet ef migrations add`; don't hand-edit this file or manually alter tables in Supabase again.
- The `__EFMigrationsHistory` table was manually created afterward (because the tables were created via schema.sql, not `dotnet ef database update`) — its column names follow the project's snake_case convention, written as `migration_id`/`product_version` (not EF's default PascalCase).
- A legacy issue was resolved on 2026-08-29: the primary key/foreign key/unique/CHECK constraints in `schema.sql` were written inline without explicit names, so the names Postgres auto-generated didn't match what the EF migration snapshot expected (`pk_*`/`fk_*`/`ix_*`/`ck_*`) — these have been manually aligned with `RENAME CONSTRAINT`. **For any future migration that needs to operate on a constraint by name, treat the names in [AppDbContextModelSnapshot.cs](src/DeepLearning.Infrastructure/Persistence/Migrations/AppDbContextModelSnapshot.cs) as authoritative.**

## Order of steps for building a new CQRS feature

1. **Repository interface**: whatever persistence operations are needed, add them to `Application/Interfaces/I<Aggregate>Repository.cs`. One repository per aggregate root — don't split by table. The interface must be `public` (not `internal`), since the Infrastructure project implements it across assembly boundaries.
2. **Repository implementation**: `Infrastructure/Persistence/Repositories/<Aggregate>Repository.cs`, implemented directly with `AppDbContext`. **The repository itself never calls `SaveChanges`** — it's only responsible for querying/marking changes; persisting is handled uniformly through `IUnitOfWork`.
3. Register the new repository as `AddScoped` in `Infrastructure/DependencyInjection.cs`.
4. Build the four-piece set under `Application/Features/<BusinessDomain>/Commands|Queries/<UseCaseName>/`:
   - `<UseCase>Command`/`Query`: `: IRequest<TResult>`, pure data.
   - `<UseCase>Validator`: `: AbstractValidator<TCommand>`, auto-discovered by `AddValidatorsFromAssembly`; `ValidationBehavior` runs it automatically before the handler.
   - `<UseCase>Result`: the external DTO — don't return Domain entities across the boundary directly.
   - `<UseCase>CommandHandler`: `: IRequestHandler<TCommand, TResult>`, injects the repository + `IUnitOfWork`; after modifying the entity, call `await _unitOfWork.SaveChangesAsync(ct)` once, then map to Result and return. Queries generally don't need `IUnitOfWork`.
5. In the Api layer, the corresponding Controller injects `IMediator` and calls `await _mediator.Send(command)`.
6. If this feature needs to trigger domain events after saving: this already works (see "Domain events & Step 6 downstream subscribers") — call `aggregate.AddDomainEvent(new SomeEvent { ... })` on an `AggregateRoot` before `_unitOfWork.SaveChangesAsync(ct)`, and it's collected/dispatched automatically. To subscribe to an existing event, add a class implementing `INotificationHandler<DomainEventNotification<TEvent>>` (MediatR's assembly scan picks it up automatically, same as any other handler) — no change needed to whatever raises the event.

## Where to look when you have a question

| What you want to know/do | Where to go |
|---|---|
| What entities exist, what their fields are | `Domain/Entities/*.cs` (authoritative); `Migrations/schema.sql` is the database's actual current structure |
| A field's column name/type/constraints/index | `Infrastructure/Persistence/Configurations/<Entity>Configuration.cs` |

| MediatR pipeline order/how handlers are registered | `Application/DependencyInjection.cs` |
| Adding/modifying an enum | `Domain/Enums/` + `AppDbContext.OnModelCreating` + `NpgsqlEnumConfiguration.cs` (both need to change) |
| Adding a new repository method | `Application/Interfaces/I*Repository.cs` (interface) + `Infrastructure/Persistence/Repositories/*.cs` (implementation) |
| Adding a new command/query | `Application/Features/<Area>/Commands|Queries/<UseCase>/` |
| How to write a Controller | `Api/Controllers/`, inject `IMediator` — see `ExamTypesController.cs`/`QuestionsController.cs`/`SubmissionsController.cs`/`FollowUpsController.cs`/`WeakPointsController.cs`/`QuestionBankCategoriesController.cs`/`ReviewLibraryController.cs` for real examples; `ProgressController` is still an empty shell |

## Known pitfalls

- The existing empty-shell types/interfaces in `Application/Interfaces` and `Infrastructure/Persistence/Repositories` default to `internal`. Remember to change them to `public` when actually implementing the cross-assembly interface, otherwise the build fails (`IUnitOfWork` has already been changed — use it as a reference).
- Check the `.csproj` before adding a new project reference — when the project was first scaffolded, `Infrastructure` didn't reference `Application` and `Application` didn't reference `Domain`; this was only fixed on 2026-08-29. This means the skeleton's project references can't be fully trusted — verify for yourself before making changes.
- Before running `dotnet ef migrations add/list/database update` locally, set the `ConnectionStrings__DefaultConnection` environment variable first (the design-time factory doesn't read `appsettings.json`).
- There's no standalone design document file in the repo — the comment block at the top of `schema.sql` is currently the most complete written statement of the overall design intent, worth a look before changing the schema.
- [seed_naati_ct_en_zh.sql](src/DeepLearning.Infrastructure/Persistence/Migrations/seed_naati_ct_en_zh.sql) contains the real, official NAATI CT English→Chinese rubric data (`exam_types`, `assessment_dimensions` with verbatim Band text, `error_taxonomies`, `generation_policy`, `prompt_templates`) and has already been run by hand against the Supabase dev DB. Like `schema.sql`, it is **not** auto-executed by the app or by migrations — it's checked in purely as the historical record of what production data already exists.
- **Never point `ApiWebApplicationFactory`/Testcontainers-based tests at the real Supabase connection.** Its `InitializeAsync` overrides `ConnectionStrings__DefaultConnection` via `Environment.SetEnvironmentVariable` (not `WebApplicationFactory.ConfigureWebHost`'s `ConfigureAppConfiguration` — that hook applies too late for a minimal-hosting `Program.cs` where `AddInfrastructure(builder.Configuration)` reads and captures the connection string before `builder.Build()` even runs). If that override is ever broken again, the tests will silently write real HTTP-created exam types/users/prompt templates into the real dev Supabase DB, exactly like they did once already on 2026-08-29 before this was fixed (cleaned up by hand afterward — check `exam_types`/`users`/`prompt_templates` for stray `test_*`/`user_*`/`dup_*`/`api test content` rows if this regresses).
- Repository/integration tests that build their own `DbContextOptions` (see `PostgresContainerFixture`) must build it **once and reuse it**, not per-call — EF Core spins up a new internal service provider per distinct `DbContextOptions` instance, and after ~20 of them in one process it trips `ManyServiceProvidersCreatedWarning` and starts throwing.
- **`NpgsqlEnumConfiguration.MapEnums` must reuse the same `NpgsqlNullNameTranslator`/`NpgsqlSnakeCaseNameTranslator` instances every call, not `new` them each time — this bit for real on 2026-08-29.** `AddDbContext`'s configure action runs once per scope (i.e. once per HTTP request, since `AppDbContext` is Scoped), so a fresh `new NpgsqlNullNameTranslator()` per call made every request's resulting `DbContextOptions` fingerprint distinct in EF's internal service-provider cache (these translators don't have value equality) — the API host silently built a brand-new internal DI container on *every single request* instead of reusing one, and the 21st request in one test process tripped `ManyServiceProvidersCreatedWarning` into a hard 500. It went unnoticed through all of Step 1 because the Api test suite stayed just under ~20 requests; adding Step 2's `QuestionsControllerTests` pushed it over. Fixed by making the translators `private static readonly` fields. If this class is ever "simplified" back to per-call `new`, the bug returns — and it's confusing to debug because the *symptom* shows up as an unrelated test failing (e.g. a null/empty GUID from a JSON-deserialized 500-as-ProblemDetails response), not as the 500 itself.
- Testcontainers needs a Postgres image with the `vector` extension available (this schema's migrations enable pgvector) — use `pgvector/pgvector:pg16`, not plain `postgres:16-alpine`.
- [docker-compose.yml](docker-compose.yml) maps Postgres to **host port 5433, not 5432** — this machine (and possibly others) already runs a native Postgres service on 5432. Docker's port-proxy doesn't error on the collision; `psql`/`dotnet ef` just silently connect to the native install instead of the container and fail with a baffling password-auth error. Verified working end-to-end on 2026-08-29: `docker compose up -d` + `dotnet ef database update` against `Host=localhost;Port=5433;...` creates all 30 tables (29 + `__EFMigrationsHistory`) cleanly from empty.
- [.github/workflows/ci.yml](.github/workflows/ci.yml) runs `dotnet build` + `dotnet test` on push/PR to `master`/`main`. GitHub-hosted Ubuntu runners have Docker preinstalled, so the Testcontainers-backed integration/API tests run there with no extra service-container setup. Not yet actually exercised on GitHub itself (would need a push) — the YAML has only been syntax-checked locally.
- **`llm_provider_settings`/`llm_provider_models` are tables whose real-Supabase creation is deliberately hand-run, by the user's own request** (they wanted DB schema changes reviewed/applied by hand rather than run by the agent) — unlike everything else, the EF migrations (`20260829092630_AddLlmProviderSettings`, `20260829110847_AddLlmProviderModels`) were generated locally so `dotnet ef` history and Testcontainers-driven tests stay correct, but were never applied to Supabase via `dotnet ef database update`. [add_llm_provider_settings.sql](src/DeepLearning.Infrastructure/Persistence/Migrations/add_llm_provider_settings.sql) is the literal idempotent SQL from `dotnet ef migrations script` (safe to run as-is); [seed_llm_provider_settings.sql](src/DeepLearning.Infrastructure/Persistence/Migrations/seed_llm_provider_settings.sql) seeds the 4 provider rows (`mimo` active by default). **Verified against the real Supabase DB on 2026-08-29**: `llm_provider_settings` was already applied and seeded, but its `is_active=true` row was still `claude` — the seed script uses `ON CONFLICT (provider_key) DO NOTHING`, so re-running it after the seed file's default changed to `mimo` is a silent no-op on rows that already exist. **Flipping which row is active is a data UPDATE the user runs, not something re-running the seed script accomplishes** — either the two-statement UPDATE in the "AI integration" fallback bullet above, or `POST /api/v1/llm-provider-settings/mimo/activate` once deployed.
  - **`llm_provider_models` needed 4 files run in this exact order** (not 2, unlike every other hand-run table) — because its migration doesn't just create a new table, it also **drops the pre-existing, already-live `llm_provider_settings.model` column** (see the design-fix note in "AI integration" above: `Model` used to live on both tables and could drift, so it was consolidated onto `llm_provider_models` alone). **All 4 have now been run against the real Supabase DB (confirmed via `psql` on 2026-08-29)** — schema and data both verified matching exactly what's below; this whole bullet is now historical record of how it got there, not a pending TODO:
    1. [add_llm_provider_models.sql](src/DeepLearning.Infrastructure/Persistence/Migrations/add_llm_provider_models.sql) — creates the table + both indexes. No data loss risk, safe on its own. **Exception**: the user already ran an *earlier* version of this exact file once (before the design was fixed — that version had `thinking_enabled`/`effort`/`extra_settings` columns and no `is_current`), so on the real Supabase DB the table already exists in the old shape. For that case, [upgrade_llm_provider_models_schema.sql](src/DeepLearning.Infrastructure/Persistence/Migrations/upgrade_llm_provider_models_schema.sql) ALTERs it to the current shape instead (confirmed via `psql` on 2026-08-29 that all 3 dropped columns were NULL on every row, so nothing was actually lost) — run this in place of step 1 whenever the table already exists.
    2. [migrate_llm_provider_settings_model_to_catalog.sql](src/DeepLearning.Infrastructure/Persistence/Migrations/migrate_llm_provider_settings_model_to_catalog.sql) — **hand-written, not from `dotnet ef migrations script`** — copies each provider's existing `llm_provider_settings.model` value into `llm_provider_models` as an `is_current=true` row, so nothing is lost before the column is dropped. Safe to re-run; its `ON CONFLICT (provider_key, model) DO UPDATE` also correctly handles rows that already exist in the catalog (the exact situation above, since the old seed already inserted `claude-opus-5`/`claude-sonnet-5`/etc.).
    3. [seed_llm_provider_models.sql](src/DeepLearning.Infrastructure/Persistence/Migrations/seed_llm_provider_models.sql) — optional, adds extra known-but-not-current models (currently just `claude-sonnet-5`, which in the already-ran-the-old-seed case is a no-op since it's already there).
    4. [remove_model_column_from_llm_provider_settings.sql](src/DeepLearning.Infrastructure/Persistence/Migrations/remove_model_column_from_llm_provider_settings.sql) — drops `llm_provider_settings.model` and records the migration in `__EFMigrationsHistory`, **first deleting a stale history row for the old migration id `20260829104952_AddLlmProviderModels`** if present (the old `add_llm_provider_models.sql` self-inserted that id, which no longer matches any migration file after the design fix regenerated it as `20260829110847_AddLlmProviderModels`) — safe to run even if that stale row was never there. **Running this before step 2 is real, unrecoverable data loss** — don't reorder these. **This DropColumn (both here and in the matching `20260829110847_AddLlmProviderModels.cs` EF migration) is a real violation of design doc §7's additive-only migration discipline** — see item 3 of the design-doc-audit list near the top of this file (under "Progress against the design doc's Step 0-10 roadmap"); confirmed acceptable by the user (2026-08-30) only because the table had never gone live before the fix, not a pattern to repeat on a column with real data.
  - **If neither table/seed has been applied to Supabase yet, nothing hard-fails**: `LlmClientResolver` falls back to the hardcoded `mimo` keyed client if `llm_provider_settings` has no active row, and if a provider has no `is_current=true` row in `llm_provider_models`, `Model` on the request just stays null and the adapter's own appsettings-configured `Model` wins — but both are still worth applying for real so the admin API has real data to work with, and so `llm_provider_settings` actually has its `model` column removed rather than sitting there unused.
- **Three things from the 2026-08-30 audit-fix round are generated/written but not yet applied to the real Supabase DB** — run these before relying on the corresponding feature against real data:
  1. `dotnet ef database update` for migration `20260830122531_MakeUserPasswordHashNullable` (real, safe `AlterColumn` — loosens `users.password_hash` to nullable).
  2. `dotnet ef database update` for migration `20260830123650_AddSubmissionXminConcurrencyToken` — this one's `Up()`/`Down()` are deliberately empty (see "Submissions & grading (Step 4)" above for why), so running it changes nothing in the real schema; it only needs to be applied so `__EFMigrationsHistory` matches what's in source control.
  3. The hand-run [add_weak_point_targeting_question_gen_prompt_template.sql](src/DeepLearning.Infrastructure/Persistence/Migrations/add_weak_point_targeting_question_gen_prompt_template.sql) — additive `prompt_templates` row, same convention as every other prompt-template SQL file in this list.

## Running the tests

Requires Docker Desktop running (Testcontainers spins up real, throwaway Postgres containers — no mocked DbContext anywhere in the suite).

```bash
# Default / CI: excludes real provider calls (cost money, need network + live keys)
dotnet test DeepLearning.slnx --filter "Category!=LlmIntegration"

# Run the live provider calls explicitly — needs the 5 provider secrets set first, either
# via `dotnet user-secrets set "Llm:Claude:ApiKey" "..." --project src/DeepLearning.Api`
# (set once, works forever, no export needed — recommended) or exported env vars
# (Llm__Claude__ApiKey etc.) for this shell session. See "AI integration" above.
dotnet test DeepLearning.slnx --filter "Category=LlmIntegration"
```

Plain `dotnet test` with no filter runs everything including the live Claude call — don't do that in CI or on a loop. `.github/workflows/ci.yml` already uses the filtered form.

A `NU1903` warning about `SSH.NET` having a known high-severity advisory is expected and currently unresolved — it's a transitive dependency of `Testcontainers.PostgreSql` (used to talk to remote Docker contexts), not something this project calls directly, and it never ships in the Api project's output.
