# AGENTS.md — Project Map

A navigation file for AI collaborators: what this project looks like, where to find things, where to make changes, where new features should go, and what can be reused from where.

## What this project is

Backend for the NAATI CT translation practice software. .NET 10 + EF Core (Npgsql) + Supabase (hosted Postgres).
Standard four-layer Clean Architecture + CQRS (MediatR) + Repository/UnitOfWork.

**There is no frontend in this repo.** The design doc specifies a Next.js/React frontend, but nothing for it — no project, no scaffold, not even a folder — exists anywhere in this working directory. Don't assume one exists elsewhere in the workspace; it hasn't been started, and starting it is a separate scoping decision (App Router vs. other, TailwindCSS/shadcn vs. Ant Design, etc.) that hasn't been made yet.

## AI integration (Step 3): provider abstraction, config, and gotchas hit for real

- **Provider-neutral by design — 4 providers wired up for real: Claude, OpenAI, DeepSeek, Mimo.** `ILlmClient` (Application) knows nothing about any of them. Each is registered as a **keyed** service (`AddKeyedTransient<ILlmClient, ...>("claude" | "openai" | "deepseek" | "mimo")`, see `DependencyInjection.cs`). Handlers never inject `ILlmClient` directly or depend on a concrete provider — see the next bullet.
- **Which provider is active lives in the database, not config** (`llm_provider_settings` table, one row per provider, `is_active` marks the current one — a partial unique index guarantees at most one). **Which model that provider currently uses is a separate, dedicated table — `llm_provider_models` — not a column on `llm_provider_settings`.** `LlmProviderSettings` originally had its own `Model` string column alongside the `llm_provider_models` catalog, which meant two independently-editable copies of "the current model" that could silently disagree (PATCH the settings row's `Model` without touching the catalog, or vice versa). That was replaced (migration `20260829110847_AddLlmProviderModels`, still the *first* real deploy of this table since it was never applied before the fix) so `llm_provider_models` is the single source of truth: `IsCurrent` on that table (partial unique index **per `ProviderKey`**, not globally like `llm_provider_settings.IsActive`) marks which cataloged model is in effect for that provider. `ILlmClientResolver.GetActiveClientAsync()` (Infrastructure/Ai/LlmClientResolver.cs) loads the active `LlmProviderSettings` row, then separately loads that provider's current `LlmProviderModel` row, and wraps both into `ConfiguredLlmClient` so `ThinkingEnabled`/`Effort`/`ExtraSettings` (from settings) and `Model` (from the catalog's current row) become that call's defaults — a caller can still override any of them per-request on `LlmCompletionRequest`. If a provider has no current model row, `Model` stays null and the adapter's own appsettings-configured `Model` wins (same fallback behavior as before). `GenerateQuestionCommandHandler` calls the resolver instead of injecting `ILlmClient`. **Switching providers/models/effort is a data UPDATE, not a redeploy** — takes effect on the very next AI call. Table creation and seeding are hand-run SQL (`Infrastructure/Persistence/Migrations/{add,seed}_llm_provider_settings.sql`) by design — see "Known pitfalls" below for why this one didn't get auto-applied like everything else.
- **Mimo is both the seeded default and the code-level fallback.** `seed_llm_provider_settings.sql` inserts `mimo` as the only `is_active=true` row. Separately, `LlmClientResolver.FallbackProviderKey = "mimo"` is a hardcoded safety net in `GetActiveClientAsync()`: if `llm_provider_settings` has no `is_active=true` row at all (table not yet applied to Supabase, or someone deactivated everything), it logs a warning and resolves the keyed `mimo` client directly instead of throwing — so a missing/misconfigured table degrades to "use Mimo with its appsettings-configured defaults," not a hard failure of every AI feature. These two are independent: the seed decides what the *DB says* is active; the fallback decides what happens when the DB has *no opinion*.
- **Admin API for switching provider/model/thinking/effort at runtime** — `LlmProviderSettingsController` (`Api/Controllers/LlmProviderSettingsController.cs`), CQRS slice under `Application/Features/LlmProviders/`:
  - `GET /api/v1/llm-provider-settings` — lists all provider rows (`ListLlmProvidersQuery`).
  - `PATCH /api/v1/llm-provider-settings/{providerKey}` — partial update of `ThinkingEnabled`/`Effort`/`ExtraSettingsJson` (`UpdateLlmProviderSettingsCommand` — only non-null fields in the request body change; 404 via `NotFoundException` if the key doesn't exist). **Does not take a `Model` field** — that's `llm_provider_models`, see below.
  - `POST /api/v1/llm-provider-settings/{providerKey}/activate` — makes this provider the active one (`ActivateLlmProviderCommand`). Deliberately does **two sequential `SaveChangesAsync` calls** (deactivate every other currently-active row first, then activate the target) rather than one batched save — the partial unique index `ux_llm_provider_settings_single_active` is checked per-statement in Postgres, not deferred, so activating the new row before the old one's deactivation is committed would transiently violate it within the same transaction.
  - No create/delete endpoints — rows are meant to be seeded via SQL (one per known provider), matching the "reference data, hand-managed" treatment the rest of this table already gets.
- **`llm_provider_models` is both the catalog of known models per provider AND the single source of truth for which one is current.** `Domain/Entities/LlmProviderModel.cs` (`ProviderKey`, `Model`, `Label`, `IsCurrent`, `CreatedAt`) + `LlmProviderModelConfiguration.cs` — unique index on `(provider_key, model)` so a model can only be cataloged once per provider, plus a **partial unique index scoped to `provider_key`** (`ux_llm_provider_models_single_current_per_provider`, `WHERE is_current = true`) so each provider independently has at most one current model — unlike `llm_provider_settings.IsActive`'s partial unique index, which is global (one active provider across *all* rows), this one is per-provider (each provider can each have its own `IsCurrent=true` row simultaneously; selecting a model for `claude` doesn't touch `deepseek`'s current model). Endpoints on the same `LlmProviderSettingsController`:
  - `GET /api/v1/llm-provider-settings/{providerKey}/models` — list the catalog for one provider, each entry's `IsCurrent` included (404 if the provider itself doesn't exist).
  - `POST /api/v1/llm-provider-settings/{providerKey}/models` — add a new cataloged model, always `IsCurrent=false` (409 if `(providerKey, model)` already exists). **Adding a row here never changes what's currently running.**
  - `POST /api/v1/llm-provider-settings/{providerKey}/models/{model}/select` — makes an already-cataloged model the current one (`SelectLlmProviderModelCommand`; 404 if that exact `(providerKey, model)` isn't cataloged yet — add it first). Deliberately does **two sequential `SaveChangesAsync` calls** (un-set any other current row for the *same* `ProviderKey` first, then set the target), same reasoning as `ActivateLlmProviderCommand`. This is the only way to change what model a provider uses — `keeping claude-opus-5 cataloged while also using claude-sonnet-5` is exactly this: both stay in the catalog, `Select` just flips which one is current.
  - **No delete/rename endpoint for a catalog entry, and no way to un-select a current model back to "none" via the API** — consistent with this codebase's append-only-reference-data convention (see the CQRS section's Create+GetById+List-only rationale), but concretely means a typo'd model string added by mistake can only be fixed with direct SQL, and once a provider has a current model, switching to "no current model" (falling back to the adapter's appsettings default) isn't reachable except by picking another model first. Flagged, not yet requested to be fixed.
  - `ListLlmProvidersQuery`'s result now includes `CurrentModel` (nullable — joined from the catalog's `IsCurrent=true` row for that provider, null if none set) so the provider list still shows "what's running" at a glance without a second request.
  - Table creation/seeding follow the exact same hand-run-SQL convention as `llm_provider_settings`, but in **more steps since this table's deploy also had to migrate data off the old `llm_provider_settings.Model` column** — see "Known pitfalls" below for the exact run order (`add_llm_provider_models.sql` → `migrate_llm_provider_settings_model_to_catalog.sql` → optionally `seed_llm_provider_models.sql` → `remove_model_column_from_llm_provider_settings.sql`). The seed only adds models this project has actually confirmed (either live-tested or the exact model-id string independently verified) — currently just `claude-sonnet-5` (the migrate step already carries over whatever was actively in use, e.g. `claude-opus-5`). It deliberately does **not** include a guessed `deepseek-v4-pro` or similar — don't add an unverified model id to this table on a guess; confirm the exact string against that provider's own docs first (same rule that applied to Mimo's whole integration).
- **Secrets (API keys, Claude's WorkspaceId) are environment variables, not config or database** — keys `Llm:Claude:ApiKey`, `Llm:Claude:WorkspaceId`, `Llm:OpenAi:ApiKey`, `Llm:DeepSeek:ApiKey`, `Llm:Mimo:ApiKey`. No code change was needed for this — ASP.NET Core's default config pipeline already merges env vars (`Llm__Claude__ApiKey`, double-underscore = nested-key separator) and **.NET User Secrets** on top of `appsettings.json`; the only change was **removing** the `ApiKey`/`WorkspaceId` values that used to live in `appsettings.Development.json`.
  - **Local dev**: set once via `dotnet user-secrets set "Llm:Claude:ApiKey" "..." --project src/DeepLearning.Api` (repeat per key) — stored in `%APPDATA%\Microsoft\UserSecrets\<UserSecretsId>\secrets.json`, **outside the repo entirely**, auto-loaded by both `dotnet run` and `dotnet test`/`WebApplicationFactory` in Development (verified: the live tests pass with zero `export` needed once secrets are set this way). The Api project's `<UserSecretsId>` in the `.csproj` is just a random GUID pointing at that file — not a secret itself, fine to commit.
  - **CI/production**: real environment variables (`Llm__Claude__ApiKey=...`), same convention as `ConnectionStrings__DefaultConnection` further down this file — User Secrets is Development-only by design and won't be present there.
  - `BaseUrl`, `Model` (fallback only — the DB row's `Model` wins when going through the resolver), and the OpenAI-compatible per-provider fields stay in `appsettings.Development.json` since they aren't secret.
- **Two adapter classes, not four.** `ClaudeLlmClient` has its own shape (Anthropic's Messages API is structurally different — top-level `system`, content-block array, `thinking`/`output_config.effort`). OpenAI/DeepSeek/Mimo all speak the **same** OpenAI Chat Completions wire format (confirmed against each provider's own docs on 2026-08-29 via WebFetch, not assumed from memory — Mimo in particular is easy to get wrong by guessing), so they share **one** `OpenAiCompatibleLlmClient`, parameterized per provider by `OpenAiCompatibleOptions` (base URL, auth header name/prefix — Mimo uses a bare `api-key` header, not `Authorization: Bearer`, model id, and the output-length field name — DeepSeek uses `max_tokens`, OpenAI/Mimo use `max_completion_tokens`). Adding a 5th OpenAI-shaped provider needs **zero new C#**: one more named-options section + one more `AddKeyedTransient` line in `DependencyInjection.cs`, plus one more `llm_provider_settings` row. Adding a structurally different provider (Gemini, etc.) means one more adapter class shaped like `ClaudeLlmClient`.
- **`ThinkingEnabled`/`Effort` are honestly scoped to Claude only.** Claude: `ThinkingEnabled=false` sends `thinking:{type:"disabled"}` (omitted otherwise, runs adaptive); `Effort` maps to `output_config.effort`. For OpenAI/DeepSeek/Mimo, "thinking" isn't a universal boolean in the Chat Completions format — OpenAI's reasoning models use separate model ids or a Responses-API-only field, DeepSeek's reasoning is a distinct model name, Mimo's mechanism isn't confirmed — so rather than guess a field name, `OpenAiCompatibleLlmClient` leaves those two alone and relies on `ExtraSettings` (JSONB passthrough, merged directly into the request body — e.g. `{"reasoning_effort":"high"}`) as the generic escape hatch for whatever provider-specific knob is needed once actually confirmed against that provider's docs.
- **Raw `HttpClient`, not official provider SDKs — deliberate.** Matches the design doc's own "HttpClient+Polly" architecture, and a uniform raw-HTTP adapter shape is what actually makes swapping/adding providers cheap; the resilience pipeline (`LlmResiliencePipeline.cs`, via `Microsoft.Extensions.Http.Resilience` — Polly v8 under the hood) attaches to `HttpClient`, not to an SDK client, and is shared by all 4 providers' HttpClients.
- **Real bugs found only by actual live calls, all fixed**:
  1. Sending `"system": null` in Claude's request body (instead of omitting the key) got a real 400 ("system: Input should be a valid array") — fixed with `[JsonIgnore(Condition = JsonIgnoreCondition.WhenWritingNull)]` on `ClaudeLlmClient`'s request DTO.
  2. `AddStandardResilienceHandler`'s library defaults (10s per-attempt / 30s total timeout) are tuned for ordinary REST calls, not an LLM completion — a real Claude question-generation call with default adaptive thinking took longer than that and tripped `Polly.Timeout.TimeoutRejectedException`, uncaught by the original `catch (HttpRequestException)` clause, surfacing as a raw 500 instead of a clean `AiCallFailedException`→503. Fixed by widening the catch clause (both adapters) and raising `AttemptTimeout`/`TotalRequestTimeout` to 60s/180s in `LlmResiliencePipeline.Configure` — note the circuit breaker's `SamplingDuration` must stay ≥ 2× `AttemptTimeout` or `AddStandardResilienceHandler` fails **at startup** with an `OptionsValidationException`, not at call time.
  3. OpenAI's live test fails with 429 `insufficient_quota`/`credit_balance_exhausted` — that account has no billing credits. Not a code bug: the request is correctly authenticated (a bad key would be 401) and Polly correctly retried 3 times before giving up. DeepSeek and Mimo both succeeded for real on the same run, including again after secrets moved to env vars.
- **`prompt_templates` needed a new row for Step 3 to work at all**: the exam_specific/question_gen row seeded back in Step 1 only specifies content requirements (topic, difficulty), not an output contract — because the code that would consume it didn't exist yet. Added one new `shared_methodology`/`question_gen` row (subject_category=`translation`) via the real `POST /api/v1/prompt-templates` endpoint instructing the model to output *only* the JSON shape `GenerateQuestionCommandHandler` parses. If question generation ever starts failing to parse, check this row (`prompt_templates` where `template_type='question_gen' AND layer='shared_methodology'`) hasn't been deactivated or superseded incompatibly. This row instructs JSON output generically — it isn't Claude-specific, so it works unchanged no matter which provider is active.
- **Live-call tests are excluded from the default run** — see "Running the tests" below. `ClaudeLlmClientLiveTests.cs` and `OpenAiCompatibleLlmClientLiveTests.cs` (3 methods — one per OpenAI-shaped provider) both resolve their `ILlmClient` by DI key directly, bypassing `ILlmClientResolver`/the database entirely — they're testing the adapters, not the provider-switch mechanism. Requires the env vars above to be set.
- **Test-coverage gap, found by audit on 2026-08-29, closed same day**: no single test exercised the full real chain — real Postgres rows → `LlmClientResolver` querying them → keyed-DI resolution → an actual HTTP call. `LlmClientResolverTests.cs` (Infrastructure/Ai) covers the resolver's merge/fallback logic but against fake `ILlmProviderSettingsRepository`/`ILlmProviderModelRepository` implementations, never a real Postgres. `GenerateQuestionControllerTests.cs` swaps `ILlmClientResolver` itself for a fake (`FakeLlmClientResolver`), so it never ran the real resolver at all. ## Submissions & grading (Step 4): state machine, AI orchestration, structured-output validation

- **`Submission.TransitionTo(SubmissionStatus)`** (Domain/Entities/Submission.cs) is the whole state machine from design doc §4.1, encoded as a `Dictionary<SubmissionStatus, SubmissionStatus[]>` of legal next-states — `draft→submitted→grading→{grading_failed,graded}`, `grading_failed→{grading,grading_abandoned}` (the retry path), `graded→{under_dispute,archived}`, `under_dispute→{standard_revised,graded}`, `standard_revised→graded`. An illegal move throws `InvalidSubmissionStateException` (a `ConflictException`, so it's a 409, not a 400/404). There is deliberately no separate idempotency-key column on `submissions` (the design doc calls for one, but the schema never grew a field for it) — the state machine itself is the idempotency guard: `GradeSubmissionCommandHandler` calls `TransitionTo(grading)` before doing anything else, so a concurrent second grade call on the same submission sees it already in `Grading` and gets a 409 instead of double-grading.
- **`GradeSubmissionCommandHandler`** (Application/Features/Submissions/Commands/GradeSubmission) is the AI-orchestration handler, same shape as `GenerateQuestionCommandHandler` (Step 3): create an `AiCallLog` row + transition the submission to `Grading`, save immediately so both survive a hung call; build the prompt via `IExamConfigLoader`/`PromptRenderer` (unchanged from Step 3); call `ILlmClientResolver.GetActiveClientAsync()` (also unchanged — grading goes through the same DB-driven provider switch as question generation); parse the JSON response; validate it; persist `GradingResult`/`ErrorListItem` rows; transition to `Graded`. Any failure at any of those steps transitions the submission to `GradingFailed` and marks the `AiCallLog` `final_failure` before rethrowing (`FailAsync`, mirroring `GenerateQuestionCommandHandler`'s own `FailAsync`) — the caller retries by calling grade again, which is legal from `GradingFailed`.
- **Isolation (design doc §10.2) is structural, not a prompt reminder**: the handler only ever loads `Question.SourceText`, `Question.FlawedTranslationText` (TaskB only — see below), the submission's own `Content`, `MeaningCheckpoint` rows, and (TaskB only) `TaskBSeededError` rows — `IReferenceTranslationRepository` doesn't even exist yet (Step 7), so there's no code path that could accidentally pull `reference_translations` into a grading call even by mistake.
- **TaskB grading sends `Question.FlawedTranslationText` (the full text the user was annotating), not just `SourceText`** — `TaskBSeededError.PositionStart/PositionEnd` are character offsets into that flawed text, so without the text itself the AI has positions and category labels with nothing to locate them against and can't judge whether the user's annotations are actually correct. This was missing from the first version of `BuildTemplateModel`/`add_grading_content_prompt_template.sql` — caught by inspection the same day, before the SQL file was ever run against real Supabase — and is now covered by `SubmissionsControllerTests.Grade_for_task_b_includes_the_flawed_translation_text_in_the_prompt_sent_to_the_ai` (uses a prompt-capturing fake `ILlmClient` to assert on the actual rendered prompt, not just on persisted output).
- **`ExamTypeId` is caller-supplied on `GradeSubmissionCommand`, not derived from the Submission/Question** — same precedent as `GenerateQuestionCommand`. `Question` has no `exam_type_id` column (design doc §9.4 defers that FK until a second exam type exists), and the MVP only has one exam type anyway, so there's nothing to derive it from.
- **Structured-output validation is a hard constraint in code, not a prompt reminder** (design doc §10.3 — grading is where this first actually applies, since `error_category`/`dimension_key` only exist on grading output, not on question generation): every `dimensionKey` in the AI's response — both in `dimensions[]` and in each `errors[].dimensionKey` — must match a `dimension_key` among the `AssessmentDimension` rows loaded for that exam type + task type, or `RubricVersionNotFoundException` (a 404) is thrown; every `errors[].errorCategory` must match a `category_key` among the loaded `ErrorTaxonomy` rows, or the call is rejected (`AiCallFailedException`, a 503) — an AI response referencing a category/dimension not on file is never persisted, matching how `GenerateQuestionCommandHandler` already treats an unparseable JSON response as a hard failure rather than trying to salvage it.
- **`IGradingResultInterpreter` picks per-`scale_type` pass/fail logic** (`Infrastructure/Ai/GradingResultInterpreters/{Band15,Score100,RubricLevel}Interpreter.cs`), registered as three `IGradingResultInterpreter` entries in DI and selected in the handler via `IEnumerable<IGradingResultInterpreter>.ToDictionary(x => x.ScaleType)`. **Only `Band15Interpreter` has real data behind it** — NAATI CT's `assessment_dimensions` are 100% `scale_type='band_1_5'`, and every `level_descriptions` row numbers Band 1 as the best performance and Band 5 the worst (verified against the seeded rubric text), so `Band15Interpreter` reads `"Pass: Band 2 or above"` as "Band 2 or numerically better" (`pass_bool = reported_band <= threshold_band`). `Score100Interpreter`/`RubricLevelInterpreter` exist so the dispatch is real rather than a stub, but their bucketing/comparison logic is a documented placeholder with zero real exam-type data to validate it against — revisit both once a second exam type actually uses either scale.
- **`grading_results.band` is a fixed `INT 1-5` column regardless of `scale_type`** (schema's own `ck_grading_results_band_range` CHECK constraint) — `Score100Interpreter` buckets a 0-100 score into that 1-5 range for storage (`>=90→1 … <40→5`), also an unverified placeholder given zero real score_0_100 data exists yet.
- **A new `prompt_templates` row was needed, same reason as Step 3's question_gen row**: the three grading rows seeded by `seed_naati_ct_en_zh.sql` only specify HOW to grade (rubric criteria, error taxonomies, task-type pass thresholds) — none of them existed to inject the actual material to grade or an output contract, because `GradeSubmissionCommandHandler` didn't exist when they were written. [add_grading_content_prompt_template.sql](src/DeepLearning.Infrastructure/Persistence/Migrations/add_grading_content_prompt_template.sql) adds one `shared_methodology`/`grading` row supplying `{{ source_text }}`/`{{ flawed_translation_text }}`/`{{ submission_content }}`/`{{ meaning_checkpoints }}`/`{{ seeded_errors }}` and the exact JSON contract (`dimensions[]`/`errors[]`, camelCase keys) `GradeSubmissionCommandHandler` parses — same hand-run-SQL convention as `llm_provider_settings`/`llm_provider_models`. **Applied to the real Supabase DB by the user on 2026-08-30.** The Testcontainers test DB never runs this file either way — tests seed their own minimal `PromptTemplate` rows directly. If grading ever starts failing to parse, check this row (`prompt_templates` where `template_type='grading' AND layer='shared_methodology'` with the content-injection variables) hasn't been deactivated.
- **Scriban's nested-dictionary iteration (`{{ for band in dim.level_descriptions }}`) had never been exercised before Step 4** — the seeded grading prompt's `{{ for dim in dimensions }} ... {{ for band in dim.level_descriptions }}` shape (iterating a `Dictionary<string,string>` nested inside a list of anonymous objects) was written into `seed_naati_ct_en_zh.sql` back before grading existed, so nothing had ever rendered it. Pinned down by `tests/DeepLearning.UnitTests/Infrastructure/Ai/PromptRendererDimensionRenderingTests.cs` (calls `PromptRenderer` directly, no DB) before `GradeSubmissionCommandHandler` was built on top of the assumption that it works.
- **`CreateSubmissionCommandHandler`** rejects a `TaskType` mismatch between the request and the target `Question` (a `Question` created as TaskType.B can't be submitted against as TaskType.A) via a manually-thrown `FluentValidation.ValidationException` — this lives in the handler rather than the `AbstractValidator`, same reasoning as `ImportUserQuestionValidator`'s cross-field checks: it needs a DB lookup (`Question.TaskType`) that a pure `AbstractValidator` (no repository access) can't do. `Submission.Content` is raw JSON text (same `jsonb`-backed convention as `Question.Brief`) — TaskA sends a JSON-encoded string, TaskB a JSON array of `{positionStart, positionEnd, errorCategory, correctedText}` annotation objects (`CreateSubmissionValidator.HaveConsistentTaskShape`, added 2026-08-30 — see below; positions are offsets into the question's `FlawedTranslationText`, same convention as `TaskBSeededError`).
- **No persisted `Draft` state** — `CreateSubmissionCommandHandler` constructs the `Submission` (C# default `Status=SubmissionStatus.draft`) and immediately calls `TransitionTo(Submitted)` in the same handler call, so `Draft` is real (exercised, not skipped) but never durably observable via a GET — matches the design doc's actual flow (the user submits an already-composed answer; there's no separate "save draft" interaction in scope).

## Gaps found and fixed 2026-08-30 (post-Step-4 audit)

A user-requested audit of Steps 1-4 (prompted by re-reading the source prompt doc, `NAATI_CT_陪练评卷提示词.md`, added to the repo root that day) turned up several real gaps beyond what Step 4's own build already covered. Login/JWT, the frontend, and rate limiting were explicitly scoped out (still open, tracked nowhere in code — see the project's own known-gaps discussion, not repeated here). Everything below **was fixed the same day**:

- **`GenerateQuestion` never actually supported TaskB.** The one exam_specific/question_gen row from `seed_naati_ct_en_zh.sql` only describes a plain translation task and never references `{{ task_type }}` — calling `POST /questions/generate` with `TaskType=B` silently produced a `Question` with `TaskType=B` but `FlawedTranslationText=null` and zero `TaskBSeededError` rows (structurally broken, ungradable later). Fixed: `GenerateQuestionCommandHandler` now loads `error_taxonomies` and passes them + `task_type` into the template model; [add_taskb_question_gen_prompt_template.sql](src/DeepLearning.Infrastructure/Persistence/Migrations/add_taskb_question_gen_prompt_template.sql) adds a new `shared_methodology`/`question_gen` row, guarded by `{{ if task_type == "B" }}`, instructing the AI to also produce `flawedTranslationText`/`seededErrors[]`. The handler validates the AI's TaskB output the same way `ImportUserQuestionValidator` validates a human's: `FlawedTranslationText` non-empty, at least one seeded error, every `errorCategory` a known taxonomy, every position in-bounds and non-overlapping (`ValidateAndBuildTaskBSeededErrors`) — reject and fail the `AiCallLog` rather than persist a broken question. **Applied to the real Supabase DB by the user on 2026-08-30.**
- **Difficulty ratio (design doc §2's 简单30%/中等50%/困难20%) was never read anywhere.** `generation_policy` already had the right row seeded (`difficulty_distribution`, `{"easy":0.3,"medium":0.5,"hard":0.2}` — present in `seed_naati_ct_en_zh.sql`, which AGENTS.md's own "Known pitfalls" section already documents as run against Supabase; not independently re-verified via `psql` this session, so worth a quick `SELECT * FROM generation_policy WHERE policy_key='difficulty_distribution'` check before relying on it — the code has a safe 30/50/20 fallback either way, see below), but `GenerateQuestionCommand.Difficulty` was a required, always-caller-specified field with no code path that ever consulted the policy table. Fixed: `Difficulty` is now nullable on the command/API — when omitted, `GenerateQuestionCommandHandler.ResolveDifficultyAsync` reads the exam type's `difficulty_distribution` policy via the new `IGenerationPolicyRepository`/`GenerationPolicyRepository`, falling back to the same 30/50/20 default (`DifficultyDistributionSelector.DefaultWeights`) if no policy row exists yet. The actual weighted pick (`DifficultyDistributionSelector.Select`) is a pure static function taking the random roll as a parameter rather than touching `Random` itself, so `DifficultyDistributionSelectorTests` drives it deterministically; the handler itself just calls it with `Random.Shared.NextDouble()`. An explicit `Difficulty` on the request always wins outright and skips the policy lookup entirely.
- **`CreateSubmissionValidator` had no TaskA/TaskB shape check for `Content`** — unlike `ImportUserQuestionValidator`'s `HaveConsistentTaskShape`, any valid JSON was accepted regardless of `TaskType`. Fixed: `HaveConsistentTaskShape` now requires TaskA's `Content` to be a JSON string and TaskB's to be a non-empty JSON array of `{positionStart, positionEnd, errorCategory, correctedText}` objects (this pins down the annotation shape the design doc only loosely specified as `{position,error_category,corrected_text}` — the project didn't have a settled convention for it before this).
- **A real stuck-submission bug**: if the AI reported a `band` outside grading_results' `1-5` CHECK constraint, or if anything else failed during the final persist step of `GradeSubmissionCommandHandler`, the submission could be left sitting in `Grading` forever — there's no `Grading→Grading` transition, so a stuck submission could never be retried. Root cause: entity construction + the final `SaveChangesAsync` happened outside any try/catch that would call `FailAsync`. Fixed by (1) widening the try/catch to cover the whole parse→validate→build→persist sequence, (2) adding an explicit band-range check to `ValidatePayload` so an out-of-range band is a clean rejection instead of a raw `DbUpdateException`, and (3) a defensive reset in the catch block: if `TransitionTo(Graded)` already ran in-memory before the failure (e.g. the final save itself is what threw), the in-memory status is reset back to `Grading` before calling `FailAsync` — otherwise `FailAsync`'s own `TransitionTo(GradingFailed)` would illegally see `Graded` as the "current" status (since nothing from a failed `SaveChangesAsync` actually persisted) and throw a second, more confusing exception on top of the real one. Covered by `SubmissionsControllerTests.Grade_rejects_an_out_of_range_band_and_marks_the_submission_grading_failed_instead_of_getting_stuck`.
- **Design doc §11.2's "模拟中途失败验证整体回滚" integration test was never written for Step 4.** Added `SubmissionRepositoryTests.A_constraint_violation_in_one_grading_result_rolls_back_the_whole_batch_including_valid_rows` — adds one valid and one CHECK-constraint-violating `GradingResult` in the same `SaveChangesAsync` call against real Testcontainers Postgres and confirms *neither* survives, proving one `SaveChangesAsync` call really is one all-or-nothing DB transaction rather than "the bad row gets rejected while the good one commits."

## Directory structure and dependency direction

```
DeepLearning.Domain          <- no dependencies at all, pure C#
    ↑
DeepLearning.Application     <- depends on Domain
    ↑
DeepLearning.Infrastructure  <- depends on Application + Domain
    ↑
DeepLearning.Api             <- depends on Infrastructure + Application
```

- **Domain**: entities (`Entities/`), enums (`Enums/`), domain events (`Events/`), domain exceptions (`Exceptions/`), base classes and shared value objects (`Common/`). Doesn't reference any other project, and doesn't reference frameworks like EF/MediatR.
- **Application**: business use cases. `Features/<BusinessDomain>/Commands|Queries/<UseCaseName>/` holds the CQRS four-piece set; `Behaviors/` holds the MediatR pipeline; `Interfaces/` holds abstractions for repositories and external services (LLM, etc.); `Common/` holds cross-use-case shared types (pagination, etc.). Only depends on Domain — doesn't reference concrete implementations like EF Core or Npgsql.
- **Infrastructure**: where the interfaces defined by Application land. `Persistence/` is EF Core + Npgsql (DbContext, Configurations, Migrations, Repositories, UnitOfWork). If external services like an LLM API or email get added later, they should also get a new folder in this layer implementing Application's interfaces.
- **Api**: the ASP.NET Core entry point. `Controllers/` only does parameter binding and calls `IMediator.Send(...)` — no business logic. `Middleware/` holds cross-cutting concerns like global exception handling.

## Database: Supabase (Postgres) + EF Core

- The connection string key is consistently `ConnectionStrings:DefaultConnection`. For local development it's filled in at [appsettings.Development.json](src/DeepLearning.Api/appsettings.Development.json) — **this file is excluded by `.gitignore` and isn't committed**, so after a fresh clone / on a new machine you need to fill it in by hand again (it contains the real Supabase password). Production goes through the `ConnectionStrings__DefaultConnection` environment variable.
- Runtime read entry point: [DependencyInjection.cs](src/DeepLearning.Infrastructure/DependencyInjection.cs). Design-time entry point for `dotnet ef` commands: [AppDbContextFactory.cs](src/DeepLearning.Infrastructure/Persistence/AppDbContextFactory.cs) (only reads environment variables, not `appsettings.json` — remember to `export`/`$env:` the environment variable before running `dotnet ef` commands locally).
- The project uses `EFCore.NamingConventions`'s snake_case convention globally (see `.UseSnakeCaseNamingConvention()` in [AppDbContext.cs](src/DeepLearning.Infrastructure/Persistence/AppDbContext.cs)). A C# property like `CreatedAt` is automatically mapped to the column `created_at` — no need to hardcode column names in Configurations unless overriding the default rule.
- **Native Postgres enums**: every time a new enum is added, it needs to be registered in two places — missing either one causes runtime/design-time errors:
  1. `modelBuilder.HasPostgresEnum<T>(name: "..._enum", nameTranslator: ...)` in `AppDbContext.OnModelCreating`
  2. `o.MapEnum<T>("..._enum", nameTranslator: ...)` in [NpgsqlEnumConfiguration.cs](src/DeepLearning.Infrastructure/Persistence/NpgsqlEnumConfiguration.cs)

  Most enums use `NpgsqlNullNameTranslator` (the C# member name matches the SQL label verbatim); `Visibility`/`MasteryLevel` use `NpgsqlSnakeCaseNameTranslator` instead because their labels contain C# reserved words (`new`/`private`) — the C# members are written in PascalCase (`New`/`Private`) and the snake_case translator converts them back to the label.
- [Migrations/schema.sql](src/DeepLearning.Infrastructure/Persistence/Migrations/schema.sql) is the script originally run by hand in the Supabase SQL Editor to create the schema — it is **not** exported from EF Migrations. Its own comments state that all future schema changes must go through `dotnet ef migrations add`; don't hand-edit this file or manually alter tables in Supabase again.
- The `__EFMigrationsHistory` table was manually created afterward (because the tables were created via schema.sql, not `dotnet ef database update`) — its column names follow the project's snake_case convention, written as `migration_id`/`product_version` (not EF's default PascalCase).
- A legacy issue was resolved on 2026-08-29: the primary key/foreign key/unique/CHECK constraints in `schema.sql` were written inline without explicit names, so the names Postgres auto-generated didn't match what the EF migration snapshot expected (`pk_*`/`fk_*`/`ix_*`/`ck_*`) — these have been manually aligned with `RENAME CONSTRAINT`. **For any future migration that needs to operate on a constraint by name, treat the names in [AppDbContextModelSnapshot.cs](src/DeepLearning.Infrastructure/Persistence/Migrations/AppDbContextModelSnapshot.cs) as authoritative.**

## Order of steps for building a new CQRS feature

1. **Repository interface**: whatever persistence operations are needed, add them to `Application/Interfaces/I<Aggregate>Repository.cs`. One repository per aggregate root — don't split by table. The interface must be `public` (not `internal`), since the Infrastructure project implements it across assembly boundaries.
2. **Repository implementation**: `Infrastructure/Persistence/Repositories/<Aggregate>Repository.cs`, implemented directly with `AppDbContext`. **The repository itself never calls `SaveChanges`** — it's only responsible for querying/marking changes; persisting is handled uniformly through `IUnitOfWork`.
3. Register the new repository as `AddScoped` in `Infrastructure/DependencyInjection.cs`.
4. Build the four-piece set under `Application/Features/<BusinessDomain>/Commands|Queries/<UseCaseName>/`:
   - `<UseCase>Command`/`Query`: `: IRequest<TResult>`, pure data.
   - `<UseCase>Validator`: `: AbstractValidator<TCommand>`, auto-discovered by `AddValidatorsFromAssembly`; `ValidationBehavior` runs it automatically before the handler.
   - `<UseCase>Result`: the external DTO — don't return Domain entities across the boundary directly.
   - `<UseCase>CommandHandler`: `: IRequestHandler<TCommand, TResult>`, injects the repository + `IUnitOfWork`; after modifying the entity, call `await _unitOfWork.SaveChangesAsync(ct)` once, then map to Result and return. Queries generally don't need `IUnitOfWork`.
5. In the Api layer, the corresponding Controller injects `IMediator` and calls `await _mediator.Send(command)`.
6. If this feature needs to trigger domain events after saving (e.g., updating weak points/progress after grading a submission): `AggregateRoot` doesn't yet have a mechanism for collecting domain events, and `UnitOfWork.SaveChangesAsync` has no dispatch logic either — this needs to be designed separately (add a `DomainEvents` list to `AggregateRoot` + publish inside `UnitOfWork.SaveChangesAsync`). Don't assume this already works.

## Known pitfalls

- The existing empty-shell types/interfaces in `Application/Interfaces` and `Infrastructure/Persistence/Repositories` default to `internal`. Remember to change them to `public` when actually implementing the cross-assembly interface, otherwise the build fails (`IUnitOfWork` has already been changed — use it as a reference).
- Check the `.csproj` before adding a new project reference — when the project was first scaffolded, `Infrastructure` didn't reference `Application` and `Application` didn't reference `Domain`; this was only fixed on 2026-08-29. This means the skeleton's project references can't be fully trusted — verify for yourself before making changes.
- Before running `dotnet ef migrations add/list/database update` locally, set the `ConnectionStrings__DefaultConnection` environment variable first (the design-time factory doesn't read `appsettings.json`).
- There's no standalone design document file in the repo — the comment block at the top of `schema.sql` is currently the most complete written statement of the overall design intent, worth a look before changing the schema.
- [seed_naati_ct_en_zh.sql](src/DeepLearning.Infrastructure/Persistence/Migrations/seed_naati_ct_en_zh.sql) contains the real, official NAATI CT English→Chinese rubric data (`exam_types`, `assessment_dimensions` with verbatim Band text, `error_taxonomies`, `generation_policy`, `prompt_templates`) and has already been run by hand against the Supabase dev DB. Like `schema.sql`, it is **not** auto-executed by the app or by migrations — it's checked in purely as the historical record of what production data already exists.
- **Never point `ApiWebApplicationFactory`/Testcontainers-based tests at the real Supabase connection.** Its `InitializeAsync` overrides `ConnectionStrings__DefaultConnection` via `Environment.SetEnvironmentVariable` (not `WebApplicationFactory.ConfigureWebHost`'s `ConfigureAppConfiguration` — that hook applies too late for a minimal-hosting `Program.cs` where `AddInfrastructure(builder.Configuration)` reads and captures the connection string before `builder.Build()` even runs). If that override is ever broken again, the tests will silently write real HTTP-created exam types/users/prompt templates into the real dev Supabase DB, exactly like they did once already on 2026-08-29 before this was fixed (cleaned up by hand afterward — check `exam_types`/`users`/`prompt_templates` for stray `test_*`/`user_*`/`dup_*`/`api test content` rows if this regresses).
- Repository/integration tests that build their own `DbContextOptions` (see `PostgresContainerFixture`) must build it **once and reuse it**, not per-call — EF Core spins up a new internal service provider per distinct `DbContextOptions` instance, and after ~20 of them in one process it trips `ManyServiceProvidersCreatedWarning` and starts throwing.
- **`NpgsqlEnumConfiguration.MapEnums` must reuse the same `NpgsqlNullNameTranslator`/`NpgsqlSnakeCaseNameTranslator` instances every call, not `new` them each time — this bit for real on 2026-08-29.** `AddDbContext`'s configure action runs once per scope (i.e. once per HTTP request, since `AppDbContext` is Scoped), so a fresh `new NpgsqlNullNameTranslator()` per call made every request's resulting `DbContextOptions` fingerprint distinct in EF's internal service-provider cache (these translators don't have value equality) — the API host silently built a brand-new internal DI container on *every single request* instead of reusing one, and the 21st request in one test process tripped `ManyServiceProvidersCreatedWarning` into a hard 500. It went unnoticed through all of Step 1 because the Api test suite stayed just under ~20 requests; adding Step 2's `QuestionsControllerTests` pushed it over. Fixed by making the translators `private static readonly` fields. If this class is ever "simplified" back to per-call `new`, the bug returns — and it's confusing to debug because the *symptom* shows up as an unrelated test failing (e.g. a null/empty GUID from a JSON-deserialized 500-as-ProblemDetails response), not as the 500 itself.
- Testcontainers needs a Postgres image with the `vector` extension available (this schema's migrations enable pgvector) — use `pgvector/pgvector:pg16`, not plain `postgres:16-alpine`.
- [docker-compose.yml](docker-compose.yml) maps Postgres to **host port 5433, not 5432** — this machine (and possibly others) already runs a native Postgres service on 5432. Docker's port-proxy doesn't error on the collision; `psql`/`dotnet ef` just silently connect to the native install instead of the container and fail with a baffling password-auth error. Verified working end-to-end on 2026-08-29: `docker compose up -d` + `dotnet ef database update` against `Host=localhost;Port=5433;...` creates all 30 tables (29 + `__EFMigrationsHistory`) cleanly from empty.
- [.github/workflows/ci.yml](.github/workflows/ci.yml) runs `dotnet build` + `dotnet test` on push/PR to `master`/`main`. GitHub-hosted Ubuntu runners have Docker preinstalled, so the Testcontainers-backed integration/API tests run there with no extra service-container setup. Not yet actually exercised on GitHub itself (would need a push) — the YAML has only been syntax-checked locally.
- **`llm_provider_settings`/`llm_provider_models` are tables whose real-Supabase creation is deliberately hand-run, by the user's own request** (they wanted DB schema changes reviewed/applied by hand rather than run by the agent) — unlike everything else, the EF migrations (`20260829092630_AddLlmProviderSettings`, `20260829110847_AddLlmProviderModels`) were generated locally so `dotnet ef` history and Testcontainers-driven tests stay correct, but were never applied to Supabase via `dotnet ef database update`. [add_llm_provider_settings.sql](src/DeepLearning.Infrastructure/Persistence/Migrations/add_llm_provider_settings.sql) is the literal idempotent SQL from `dotnet ef migrations script` (safe to run as-is); [seed_llm_provider_settings.sql](src/DeepLearning.Infrastructure/Persistence/Migrations/seed_llm_provider_settings.sql) seeds the 4 provider rows (`mimo` active by default). **Verified against the real Supabase DB on 2026-08-29**: `llm_provider_settings` was already applied and seeded, but its `is_active=true` row was still `claude` — the seed script uses `ON CONFLICT (provider_key) DO NOTHING`, so re-running it after the seed file's default changed to `mimo` is a silent no-op on rows that already exist. **Flipping which row is active is a data UPDATE the user runs, not something re-running the seed script accomplishes** — either the two-statement UPDATE in the "AI integration" fallback bullet above, or `POST /api/v1/llm-provider-settings/mimo/activate` once deployed.
  - **`llm_provider_models` needed 4 files run in this exact order** (not 2, unlike every other hand-run table) — because its migration doesn't just create a new table, it also **drops the pre-existing, already-live `llm_provider_settings.model` column** (see the design-fix note in "AI integration" above: `Model` used to live on both tables and could drift, so it was consolidated onto `llm_provider_models` alone). **All 4 have now been run against the real Supabase DB (confirmed via `psql` on 2026-08-29)** — schema and data both verified matching exactly what's below; this whole bullet is now historical record of how it got there, not a pending TODO:
    1. [add_llm_provider_models.sql](src/DeepLearning.Infrastructure/Persistence/Migrations/add_llm_provider_models.sql) — creates the table + both indexes. No data loss risk, safe on its own. **Exception**: the user already ran an *earlier* version of this exact file once (before the design was fixed — that version had `thinking_enabled`/`effort`/`extra_settings` columns and no `is_current`), so on the real Supabase DB the table already exists in the old shape. For that case, [upgrade_llm_provider_models_schema.sql](src/DeepLearning.Infrastructure/Persistence/Migrations/upgrade_llm_provider_models_schema.sql) ALTERs it to the current shape instead (confirmed via `psql` on 2026-08-29 that all 3 dropped columns were NULL on every row, so nothing was actually lost) — run this in place of step 1 whenever the table already exists.
    2. [migrate_llm_provider_settings_model_to_catalog.sql](src/DeepLearning.Infrastructure/Persistence/Migrations/migrate_llm_provider_settings_model_to_catalog.sql) — **hand-written, not from `dotnet ef migrations script`** — copies each provider's existing `llm_provider_settings.model` value into `llm_provider_models` as an `is_current=true` row, so nothing is lost before the column is dropped. Safe to re-run; its `ON CONFLICT (provider_key, model) DO UPDATE` also correctly handles rows that already exist in the catalog (the exact situation above, since the old seed already inserted `claude-opus-5`/`claude-sonnet-5`/etc.).
    3. [seed_llm_provider_models.sql](src/DeepLearning.Infrastructure/Persistence/Migrations/seed_llm_provider_models.sql) — optional, adds extra known-but-not-current models (currently just `claude-sonnet-5`, which in the already-ran-the-old-seed case is a no-op since it's already there).
    4. [remove_model_column_from_llm_provider_settings.sql](src/DeepLearning.Infrastructure/Persistence/Migrations/remove_model_column_from_llm_provider_settings.sql) — drops `llm_provider_settings.model` and records the migration in `__EFMigrationsHistory`, **first deleting a stale history row for the old migration id `20260829104952_AddLlmProviderModels`** if present (the old `add_llm_provider_models.sql` self-inserted that id, which no longer matches any migration file after the design fix regenerated it as `20260829110847_AddLlmProviderModels`) — safe to run even if that stale row was never there. **Running this before step 2 is real, unrecoverable data loss** — don't reorder these.
  - **If neither table/seed has been applied to Supabase yet, nothing hard-fails**: `LlmClientResolver` falls back to the hardcoded `mimo` keyed client if `llm_provider_settings` has no active row, and if a provider has no `is_current=true` row in `llm_provider_models`, `Model` on the request just stays null and the adapter's own appsettings-configured `Model` wins — but both are still worth applying for real so the admin API has real data to work with, and so `llm_provider_settings` actually has its `model` column removed rather than sitting there unused.

## Running the tests

Requires Docker Desktop running (Testcontainers spins up real, throwaway Postgres containers — no mocked DbContext anywhere in the suite).

```bash
# Default / CI: excludes real provider calls (cost money, need network + live keys)
dotnet test DeepLearning.slnx --filter "Category!=LlmIntegration"

# Run the live provider calls explicitly — needs the 5 provider secrets set first, either
# via `dotnet user-secrets set "Llm:Claude:ApiKey" "..." --project src/DeepLearning.Api`
# (set once, works forever, no export needed — recommended) or exported env vars
# (Llm__Claude__ApiKey etc.) for this shell session. See "AI integration" above.
dotnet test DeepLearning.slnx --filter "Category=LlmIntegration"
```

Plain `dotnet test` with no filter runs everything including the live Claude call — don't do that in CI or on a loop. `.github/workflows/ci.yml` already uses the filtered form.

A `NU1903` warning about `SSH.NET` having a known high-severity advisory is expected and currently unresolved — it's a transitive dependency of `Testcontainers.PostgreSql` (used to talk to remote Docker contexts), not something this project calls directly, and it never ships in the Api project's output.
