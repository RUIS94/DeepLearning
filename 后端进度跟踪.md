# AGENTS.md — Project Map

A navigation file for AI collaborators: what this project looks like, where to find things, where to make changes, where new features should go, and what can be reused from where.

## What this project is

Backend for the NAATI CT translation practice software. .NET 10 + EF Core (Npgsql) + Supabase (hosted Postgres).
Standard four-layer Clean Architecture + CQRS (MediatR) + Repository/UnitOfWork.

**The frontend now exists and is built** — `src/DeepLearning.Web/` (Next.js 16 App Router + TS + Tailwind/shadcn + TanStack Query + Supabase Auth via `@supabase/ssr`). It **used to be** its own nested git repo, gitignored by this backend repo; as of 2026-09-05 it is **tracked in this repo** (185 files — `node_modules` and build output are ignored by its own `src/DeepLearning.Web/.gitignore`), so a single `git` command from the backend root now covers both sides. Its own `进度跟踪.md` still carries the old wording in places. [翻译练习软件_前端开发方案.md](翻译练习软件_前端开发方案.md) (2026-08-31) is the original build guide (page/route list, TS DTO type layer, Route-Handler proxy design); [src/DeepLearning.Web/进度跟踪.md](src/DeepLearning.Web/进度跟踪.md) tracks what's actually implemented and **diverges from the guide in places** (a collapsible left-sidebar shell instead of a top nav, AI-出题 / 导入题目 moved into slide-over panels, 复习库+薄弱点 merged into one `/review` page with tabs, admin pages folded into a `/exam-management/[examTypeId]` multi-tab page, real Supabase Auth wired). The two things most worth knowing before touching backend code on behalf of the frontend: (1) enums serialize as **raw integers** over the wire (no `JsonStringEnumConverter` registered anywhere in the API pipeline — the ordinal tables are in the guide's §6.2, fragile to future enum-member reordering, flagged in its §16), (2) there is still no CORS configuration and no role/auth-gating on any endpoint — both are load-bearing assumptions in the frontend's architecture (the proxy layer exists *because* of the CORS gap), not oversights to silently "fix".

### Two prompt-template fixes — both are new hand-run SQL, **NOT yet applied to the real Supabase DB** (outstanding)

1. **`fix_grading_dimension_key_prompt_template.sql` — urgent, fixes a live 503 on every TaskA grading.** `ai_call_logs` showed grading `final_failure` after 3 attempts with `"AssessmentDimension with id 'application_of_textual_norms_and_conventions' was not found."` — the grading prompt's output contract asks for `dimensionKey` "from the list above", but **no active grading `prompt_templates` row ever prints `dimension_key`**: `seed_naati_ct_en_zh.sql` §5.1's `shared_methodology`/`grading` row renders the dimension list by `dimension_name` only (`### {{ dim.dimension_name }}(...)`). The model snake-cases the display name → `meaning_transfer`/`language_proficiency` match by luck, but `"Application of textual norms and conventions"` → `application_of_textual_norms_and_conventions` ≠ the real key `textual_norms` → `RubricVersionNotFoundException` → `IAiCallRetryExecutor` re-prompts 3× (deterministic, same wrong key) → `AiCallFailedException` → 503. Fix deactivates that §5.1 row and inserts a `version=2` that prints `dimension_key:` next to each name and states the output contract explicitly. Matched by content substring (`'请依据以下评分维度对译文进行评判'`) because 3 `shared_methodology`/`grading` rows share `(template_type, layer, version=1)`. A fresh DB from seed must also run this file.
2. **`add_paragraphed_source_text_question_gen_prompt_template.sql` — AI-generated `source_text` is one unbroken blob** (confirmed via DB: an ai_generated `questions` row had 0 newlines; a user-uploaded one had per-line `\n` but 0 blank lines). The Step 3 `shared_methodology`/`question_gen` JSON-contract row (created via the API, not in any SQL file) never asks the model to paragraph `sourceText`. This adds one more additive `shared_methodology`/`question_gen` row telling the model to split `sourceText` into 3-5 paragraphs separated by a blank line (`\n\n`); also applies to TaskB `flawedTranslationText`. No handler/schema change — `GenerateQuestionCommandHandler` already persists `payload.SourceText` verbatim. The frontend renders paragraphs from `\n\n`; existing rows with no `\n\n` stay one flowing block (`ArticleText` component doesn't invent paragraph breaks).

### 2026-09-02: grading prompt — source title + estimatedPassProbability unit (outstanding SQL)

`fix_grading_source_title_and_probability_prompt_template.sql` — **new hand-run SQL, NOT yet applied to the real Supabase DB.** Fixes two bugs in the `add_grading_content_prompt_template.sql` content-injection row (`shared_methodology`/`grading`, `subject_category='translation'`, `version=1`, marker `【待评判材料】`):

1. **The source article's title was never sent to the AI.** The row printed only `原文:` + body; `questions.title` existed but `GradeSubmissionCommandHandler.BuildTemplateModel` never passed it. For any titled article the AI saw the user's translated title with nothing to match it against and scored it as `无中生有的信息增添`. Handler now passes `SourceTitle = question.Title` (Scriban → `source_title`); the `version=2` row renders a `原文标题` block when non-empty and tells the model a title shown there is source-owned. Absent block ⇒ genuinely untitled (old behaviour).
2. **`estimatedPassProbability` unit mismatch → "7000%" in the UI.** Old contract asked for `<0-100数字>`; the model returned e.g. `70`, persisted verbatim to `grading_results.estimated_pass_probability`. The frontend (`grading-result-panel.tsx`) renders `Math.round(p * 100)%` expecting a 0..1 fraction (mock data uses `0.78`), so `70` → `7000%`. `version=2` changes the contract to `0到1之间的两位小数`. The SQL also has an optional `UPDATE grading_results SET estimated_pass_probability = ROUND(estimated_pass_probability / 100, 2) WHERE estimated_pass_probability > 1` to normalise rows already written under the old contract. `grading-result-panel.tsx` also got a defensive `p > 1 ? p / 100 : p` clamp so legacy rows display correctly even before the data fix runs.

Same "new version, deactivate old" convention as `fix_grading_dimension_key_prompt_template.sql`; matched by the `【待评判材料】` marker + `version=1`. A fresh DB built from `add_grading_content_prompt_template.sql` must run this file too.

### Bug fix (committed `5a5af31`): `ImportUserQuestionCommandHandler` — empty `Brief` → 500

`questions.brief` is `jsonb`. `ImportUserQuestionValidator.BeValidJsonOrNull` deliberately treats `""` as OK (empty = "no brief"), but the handler then persisted `Brief = ""`, and Postgres rejects `''` for `jsonb` (`22P02`) → `DbUpdateException` → generic 500. Handler now normalizes: `Brief = string.IsNullOrWhiteSpace(request.Brief) ? null : request.Brief`. (`GenerateQuestionCommandHandler` was already fine — it stores the AI's JSON object.)

### Change (2026-09-02, user-requested): manual import auto-derives `word_count`

`ImportUserQuestionCommandHandler` no longer trusts a caller-supplied word count — it always sets `WordCount = WordCountCalculator.Count(request.SourceText)` (new `Application/Common/WordCountCalculator.cs`). Counting rule: one word per CJK ideograph/kana, otherwise one word per maximal letter-or-digit run (`state-of-the-art` = 4); punctuation/whitespace only separate. Only `SourceText` is counted — `Title`/`Brief` excluded, and TaskB's `FlawedTranslationText` is not counted (the field measures the passage to be translated). `WordCount` was removed from both `ImportUserQuestionCommand` and `QuestionsController.ImportUserQuestionRequest`. The AI path (`GenerateQuestionCommandHandler`) is untouched — it still stores the LLM payload's `wordCount`.

Order is best-effort chronological; a fresh-DB install is still the manual sequence, not this.
- **`SqlScriptRunner`** (`Persistence/Sql/SqlScriptRunner.cs`) — reads the manifest-ordered scripts (embedded resources: `<EmbeddedResource Include="Persistence\Sql\*.sql" />` in the Infrastructure `.csproj`), tracks applied ones in a `_sql_scripts` table (`name` PK, `applied_at`, `note`).   `dotnet run --project src/DeepLearning.Api -- sql <status|baseline|apply>`
  - `status` — list applied vs pending
  - `baseline` — record every pending script as applied **without executing it** (run once against a DB that is already current; position-agnostic)
  - `apply` — execute pending scripts, recording each; stops and reports on the first failure

  - is **strictly forward-only** — runs ONLY scripts positioned in the manifest *after* every already-recorded script, and **refuses if any pending script sits before a recorded one** (a "gap": `baseline` it or hand-apply it — `apply` won't back-fill).
  - Nothing invokes the runner on startup or during requests — only the explicit `sql` verb.
- **Intended flow for the real Supabase DB**: run any still-pending hand SQL the old way first (right now that's `consolidate_question_gen_prompt_templates.sql`), then `sql baseline` once → records all 33. From then on, a new script = add the file + append to `_manifest.txt` + `sql apply` (runs only the newly appended tail).

## 2026-09-04 / 09-05: grading rebuilt as four calls, NAATI's two severity levels, and the reasoning-budget bug

The longest round so far, all user-driven from real `src/DeepLearning.Api/logs/ai-trace/` transcripts. Grading went from one LLM call to **four**, the invented severity scale was collapsed onto NAATI's own two, and a provider-level bug was found that had been quietly voiding the pipeline's central reproducibility guarantee. **411 tests green** (`dotnet test --filter "Category!=LlmIntegration"`, was 323 on 2026-09-03); `SqlScriptRunnerTests` sync-check count 35 → **48**.

### 1. One grading call → four, behind one `prompt_templates` row

`GradeSubmissionCommandHandler` now makes four calls, all rendered from the SAME row and gated on `{{ stage }}`:

| stage | sees | emits |
|---|---|---|
| `evidence` | source + translation, source pre-split into numbered sentences | one status per sentence, checkpoint verdicts, findings |
| `proofread` | **the translation ALONE** — no source, and it is not told one exists | term-consistency table + findings |
| `sweep` | source + translation + the easy-to-miss checklist + this learner's weak points + active overrides | findings |
| `verdict` | the official five-Band text + the merged evidence | band / alternativeBand / confidence / cumulativeDensityFlag / rationale |

The three collection stages **run concurrently and are never shown each other's findings** — being handed a list turns a model into a validator that subtracts rather than a searcher that adds (measured: a "review the previous stage's list" pass added nothing and downgraded four findings). The handler takes their union, keeps the harsher reading of any duplicate, and re-numbers. Sentence splitting moved into code (`SplitSentences`) so the coverage check is real: a model that stops early can no longer emit fewer rows and still look complete.

Why not one call: asked to find, classify, rate and band at once, the model gave different answers on identical input, and its concrete detection rules reliably out-competed the abstract Band text — it found errors first and back-filled a Band to match. Prompt history is `rebuild_grading_prompt_v3_four_stage.sql` … `v10`, each file's header carrying the failure that produced it.

### 2. Severity: four invented levels → NAATI's two — `20260904110143_CollapseErrorSeverityToNaatiTwoLevels`

`moderate` and `critical` were this project's inventions. Across 55 real findings they produced **40 moderate / 14 major / 1 critical / zero minor** — a four-point scale used as a two-point one, with both points off where the rubric puts them. `ErrorSeverity` is now `minor` / `major`, and **no model ever names it**: each finding answers the two official questions and `DeriveSeverity` maps them (`q1 || q2 → major`). Asked to answer the questions AND pick a level, the model would answer "no, no" and write "major" — so the prompt no longer even states the mapping.

`NormaliseComprehensionClaims` demotes an unsubstantiated comprehension claim: if the stage cannot write down what the reader would wrongly believe, it did not impact comprehension. Without it the first four-stage run came back 38 major / 8 minor, with "還尚 is redundant, it affects fluency" scored major — NAATI's Minor, verbatim.

Also this round: `20260904003715_AddGradingResultConfidence` (`confidence` / `alternative_band` on `grading_results`, feeding a derived pass probability rather than an AI-estimated one) and `20260904070914_AddWeakPointGenerationStatus`.

### 3. The reasoning-budget bug — the real cause of "every grading retries"

`ai_call_logs` showed **every** grading run at `attempt_count` 2 or 3, always `success`. The rejection reason was invisible because `LastErrorMessage` was only written by `FailAsync`, i.e. only when the whole run died. That was fixed first (recovered rejections are now recorded even on a green run), and then the traces gave the answer:

- Mimo's deep thinking is **on by default**, and its `reasoning_content` is billed inside `max_completion_tokens` **together with the answer**. One evidence stage spent 31,000 characters deliberating and had ~200 characters of budget left for its JSON; the sweep stage was cut off at `findings[9]`.
- `OpenAiCompatibleLlmClient` never read `finish_reason`, so truncation surfaced as `Expected end of string ... Path: $.findings[9].errorCategory` — a message that names a field and reads exactly like a bad value in it. It sent a real investigation after the wrong bug, and the retry notice then told the model to check its `errorCategory` values, which was not the problem.
- **The worst part**: per Mimo's own docs, while deep thinking is on the model "does not support custom `temperature` and `top_p`" — they are forced to 1.0 / 0.95. So the `Temperature: 0m` that grading (and `WeakPointClassifier`) pass for reproducibility **had never taken effect**. Part of the run-to-run band swing this whole pipeline was built to fix was simply that.

Fixes: `OpenAiCompatibleOptions.ThinkingParameterName` (Mimo = `"thinking"`, emitted as `{"type":"enabled"|"disabled"}`; null for providers with no such switch, so OpenAI/DeepSeek are untouched) + grading and weak-point classification pass `ThinkingEnabled: false` **per call**, leaving question generation and the rest on their DB setting; `finish_reason` / Claude's `stop_reason` → `LlmCompletionResult.Truncated`, checked **before** parsing; stage budget 8192 → **16384**, doubling to 32768 on a truncated retry; and a truncation-specific re-prompt that says the output was cut off and **forbids dropping findings to fit** (the generic "fix just this one thing" can only be obeyed, for a length problem, by discarding evidence).

> `ThinkingParameterName` lives in `appsettings.Development.json`, which is **gitignored** (the whole `Llm` section is — `appsettings.json` has no `Llm` node at all). A fresh checkout loses it and thinking silently returns; the value is recorded in `OpenAiCompatibleOptions`' XML doc. Nothing breaks if it is missing — truncation is now detected and retried correctly — but temperature 0 stops being real again.

### 4. The two questions are `q1`/`q2`, and an unanswered pair is rejected

They were `q2`/`q3` for a while (a gap left when an earlier `q1` was removed), which meant the prompt had to explain its own numbering to the model. Renumbered. `NormaliseQuestionScheme` copies the emitted answers onto the canonical properties and **throws if either is missing** — the raw fields are `bool?` on purpose: both-false is a Minor, so a defaulted-missing answer does not look like an error, it looks like a mild finding, and a run of them looks like a clean grading of a competent translation.

```sql

```

What the v2 rewrite changed, each bought with a failed run:

- **The prompt gives instructions, not explanations.** Rationale for why a stage exists, arguments against the previous version's wording, and narration of what the system does with an answer had all accumulated. None of it tells the model to do anything, and the multi-stage rationale actively leaked the pipeline's structure into the one stage that must not know about it.
- **The proofread stage is handed no genre and no source text.** It used to open `你是中文科普稿件的责任校对` and judge register against popular science; this bank holds policy statements, public information leaflets and government notices. - **The error-category list no longer renders `category_name`.** `- distortion(Distortion): …` put a second, equally plausible string next to the only one `ValidateFindings` accepts, and it matches ordinally. The `description` stays: it is the only thing separating `distortion` from `unjustified_addition`.
- **Checkpoints gained `contradicted`.** `hit`/`partial`/`miss` had nowhere for "the translation asserts the opposite", which was flattened into `miss` — an omission, a Minor shape — when it is the canonical comprehension failure. Prompt-only: `BuildCheckpointVerdicts` passes the string through unvalidated.
- **Register is on the "must record" list.** `inappropriate_register` is a scoreable NAATI category that a model looking for a reason to skip will otherwise read as a style preference.
- **The verdict stage lost its house procedure.** A ratio rule, a worked example about 200- vs 2000-word texts (this exam's source is fixed at ~250 words, so it never applied), and a Band-2 fallback were all this project's inventions competing with the rubric in the one stage where the rubric should be the only thing in the room. `coverage_note` stays as background fact so "多不多" is still not answered from an impression.
- **The empty-dimension fallback is "not Band 1", not a number.** The pass line is Band 2 for `meaning_transfer`/`language_proficiency`/`revision_skills` but Band 3 for `textual_norms`/`error_categorisation`, so a single cap meant a different thing in each — and it was toothless in exactly the dimension that most often comes back with no evidence. Band 1 is an affirmative claim in every dimension (`consistently` / `accomplished` / `minimal or no` / `no or almost no` / `all or almost all`), so "cannot confirm, therefore cannot assert it" is the rubric's own logic.
- **The pass line is never rendered into any stage.** `pass_threshold` reaches the template model but no template prints it; pass/fail and the probability are computed in code (`IGradingResultInterpreter`, `EstimateDimensionPassProbability`). A model that knows the line stops choosing the best-fitting band and starts deciding whether to let someone through. `PromptRendererGradingTemplateTests.No_stage_is_told_the_pass_threshold` pins this.

- **Root cause**: `ExamConfigLoader.BuildPromptAsync` concatenates a "shared" query (`subject_category='translation'`, no exam-type filter) with a "specific" query (`exam_type_id=<NAATI>`, no subject filter). They are meant to be disjoint (shared rows have `exam_type_id IS NULL`, exam_specific rows have `subject_category IS NULL`), but the DB check constraint `ck_prompt_templates_layer_scope` is an **OR** and does not forbid a row carrying both. Every grading row except the newest had been stamped with the NAATI `exam_type_id`, so 3 rows matched **both** queries and rendered twice. `ExamConfigLoader` now filters each side by `Layer` explicitly (`shared_methodology` vs `exam_specific`) so a mis-scoped row can only land in one bucket — the misleading "enforced by the DB check constraint" comment was corrected.
- **The SQL** (same pattern as `consolidate_question_gen_prompt_templates.sql`): `DELETE FROM prompt_templates WHERE template_type='grading'` → one `exam_specific` row, a dedup'd merge of the 3 rows that were active. Section order controlled inside the template: role → task-type block (`{{ if task_type == "B" }}` conditional — Task A never sees Task B wording and vice versa; the per-dimension `Pass: Band X` lines dropped because the `{{ for dim }}` loop already prints each 通过线) → 评分关键原则 / 核对严谨度 / 自我纠正方法论 → `{{ weak_points }}` / `{{ active_overrides }}` → dimensions (+`dimension_key`) → error taxonomies (+`category_key`) → 待评判材料 → JSON contract.
- **Instruction dedup**: the three blocks were compressed **26 rules → 16** (near-duplicates merged, e.g. "系统性重复错误" stated in both 原则5 and 方法论11; "先划语法树" in both 核对3 and 方法论7), the leftover Markdown-tutoring instructions removed (提供参考译文时自查, 主动提供结构拆解辅助, 追问后上调下调 — all dead in a JSON-only call). Then 核对严谨度 grew back **16 → 18** with two targeted-detection items after live testing surfaced whole error classes the grader skimmed past: a逻辑连接词/虚词逐句定功能 process step (`while`/`as`/否定辖域 anchors, explicit "非穷举" note — triggered by a concessive `while` mistranslated as temporal), and 英语的隐性语法信号 (时态·体 / 语气强度·hedging / 冠词·单复数 = 泛指 vs 特指 — classes with no Chinese morphology, so they drop silently). **This block is the one to keep extending as more EN→ZH miss patterns surface — edit it in place via `PUT /api/v1/prompt-templates/{id}`, no migration; a few anchors, not a full taxonomy.**
- **`estimatedPassProbability` calibration**: the merged template gave the field no definition, so the AI stamped one holistic gut number into every dimension (observed: all `0.40`) and the backend's `ComputeOverallPassProbability` (product of the per-dimension numbers) compounded it. A calibration table was added below the JSON contract anchoring each dimension's number to the gap between its judged band and that dimension's pass threshold, and stating it must be estimated per-dimension. **Pass/fail itself was never affected — that's deterministic (`band` vs `pass_threshold` via `IGradingResultInterpreter`), never from this probability.** (This calibration edit landed *after* the file was first hand-run, so the user re-ran the file — it is idempotent `DELETE`+`INSERT`.)

### 2. Per-error severity + summary — EF migration `AddErrorSeverityAndSummary`

Design decision (user, from two options): one AI-judged `severity` axis, not a separate `impact` axis.

- New PG enum `error_severity_enum` (`minor`/`moderate`/`major`/`critical`; labels stored alphabetically to match Npgsql 10's `HasPostgresEnum` scaffolding — ordinal order is never relied on in SQL, all severity comparison is in C#). `error_list` gained `severity` (default `moderate`) + `summary VARCHAR(60)`.
- `impacts_core BOOLEAN` **kept** (schema-discipline "只做加法" waived per user for the dropped columns elsewhere, but this one stays) — no longer AI-driven, written deterministically as `severity IN ('major','critical')`. `GetSubmissionByIdResult.ErrorListResultItem` swapped `bool ImpactsCore` → `ErrorSeverity Severity` + `string? Summary`.
- Grading `errors[]` output contract: `"impactsCore"` → `"severity"` + `"summary"` (`≤20字定性`, e.g. 概念方向偏移). `GradeSubmissionCommandHandler.ValidatePayload` rejects an unknown/missing severity (hard constraint, like `errorCategory`). 评分关键原则 2 defines the 4-tier ladder and ties it to the 累积密度 judgment.
- Frontend derives the 影响核心 / 接近边界 / 非核心 badge from `severity` (major/critical → 影响核心, moderate → 接近边界, minor → 非核心) — `errorImpactLabel()` in `enums.ts`; no separate stored field.

### 3. Weak-point three-table rework — EF migration `ReworkWeakPointModel` + `fix_weak_point_classification_prompt_add_summaries.sql`

A structure/read/write audit of `weak_point_catalog` / `weak_points` / `weak_point_occurrences` found stale-copy columns and unbounded prompt growth. Decisions taken with the user: `pattern_summary` filled by the existing classifier call (v2, one pass); top-K = 6; catalog auto-create only on recurrence; `pattern_summary` not fed anywhere else yet.

- **`weak_point_catalog`**: dropped `is_active` → `status weak_point_catalog_status_enum` (`proposed`/`active`/`deprecated`) + `origin VARCHAR(20)` (`seed`/`auto`/`manual`). Runtime rule/AI matching reads `proposed`+`active` (`ListByExamTypeAsync`), admin reads all (`ListAllByExamTypeAsync`). No longer "insert-only via migration".
- **`weak_points`**: dropped `description` (a stale copy of `catalog.description`, never read in the prompt for catalog rows) and `evidence_note` (a snippet+explanation copy re-written on *every* occurrence — the same data is one indexed join away in `weak_point_occurrences` + `error_list`). Added `pattern_summary TEXT` — an AI-distilled, per-learner rolling description of how *this* learner manifests the kind; **this is the text the grading prompt injects** (falling back to `catalog.description` only until the first summary is computed). `category` made nullable (set only for legacy buckets; NULL once catalog-mapped). `ux_weak_points_user_category` changed to a **partial** index `WHERE catalog_id IS NULL`, mirroring `ux_weak_points_user_catalog WHERE catalog_id IS NOT NULL` — the two never both govern one row, so promotion/merge writes have one collision surface, not two.
- **`weak_point_occurrences`**: new unique index `(weak_point_id, submission_id)` — a re-grade (a second `SubmissionGradedEvent`) or concurrent event can no longer double-insert and inflate recurrence counts. `UpdateWeakPointsOnGraded` checks `OccurrenceExistsAsync` before adding.
- **`UpdateWeakPointsOnGraded`**: applies the classifier's per-kind `pattern_summary`; legacy buckets get a deterministic string (no AI); a legacy bucket that **already existed and recurs** is promoted — a deterministic `auto_{dim}_{cat}` `proposed` catalog kind is minted (or an existing one reused) and the weak point re-pointed, so the legacy set stays tiny (subsequent hits then match that kind via the rule). `ResolveStaleWeakPointsAsync` swapped `ListByUserAsync` (loads the user's whole submission history every grading) for a `ListRecentGradedCreatedAtAsync(userId, 5)` projection.
- **`WeakPointClassifier` v2** + `fix_weak_point_classification_prompt_add_summaries.sql`: one call now both classifies errors → catalog codes **and** returns a merged `pattern_summary` per touched kind (input gained `activeWeakPoints[] = {code, currentPatternSummary}` so the AI merges rather than rewrites; `WeakPointClassifierError.ImpactsCore` → `.Severity`). Return type `IReadOnlyDictionary<Guid,Guid>` → `WeakPointClassificationResult`. Still never throws — empty result ⇒ rule-only, unchanged from before.
- **Grading prompt**: `ListActiveWithCatalogByUserAsync(userId, limit: 6)` — the weak-point block is now a fixed-size top-6, ordered priority→recency. `BuildTemplateModel`'s `description` = `pattern_summary ?? catalog.description`.
- **`ListWeakPoints` DTO**: `Category` → `Label` (`catalog.Name ?? category ?? "(未归类)"`), `Description` → `PatternSummary`. `GenerateQuestionCommandHandler`'s weak-point hint uses `Catalog.Name`.

## AI integration (Step 3): provider abstraction, config, and gotchas hit for real

- **Provider-neutral by design — 4 providers wired up for real: Claude, OpenAI, DeepSeek, Mimo.** `ILlmClient` (Application) knows nothing about any of them. Each is registered as a **keyed** service (`AddKeyedTransient<ILlmClient, ...>("claude" | "openai" | "deepseek" | "mimo")`, see `DependencyInjection.cs`). Handlers never inject `ILlmClient` directly or depend on a concrete provider — see the next bullet.
- **Which provider is active lives in the database, not config** (`llm_provider_settings` table, one row per provider, `is_active` marks the current one — a partial unique index guarantees at most one). **Which model that provider currently uses is a separate, dedicated table — `llm_provider_models` — not a column on `llm_provider_settings`.** `LlmProviderSettings` originally had its own `Model` string column alongside the `llm_provider_models` catalog, which meant two independently-editable copies of "the current model" that could silently disagree (PATCH the settings row's `Model` without touching the catalog, or vice versa). That was replaced (migration `20260829110847_AddLlmProviderModels`, still the *first* real deploy of this table since it was never applied before the fix) so `llm_provider_models` is the single source of truth: `IsCurrent` on that table (partial unique index **per `ProviderKey`**, not globally like `llm_provider_settings.IsActive`) marks which cataloged model is in effect for that provider. `ILlmClientResolver.GetActiveClientAsync()` (Infrastructure/Ai/LlmClientResolver.cs) loads the active `LlmProviderSettings` row, then separately loads that provider's current `LlmProviderModel` row, and wraps both into `ConfiguredLlmClient` so `ThinkingEnabled`/`Effort`/`ExtraSettings` (from settings) and `Model` (from the catalog's current row) become that call's defaults — a caller can still override any of them per-request on `LlmCompletionRequest`. If a provider has no current model row, `Model` stays null and the adapter's own appsettings-configured `Model` wins (same fallback behavior as before). `GenerateQuestionCommandHandler` calls the resolver instead of injecting `ILlmClient`. **Switching providers/models/effort is a data UPDATE, not a redeploy** — takes effect on the very next AI call. Table creation and seeding are hand-run SQL (`Infrastructure/Persistence/Sql/{add,seed}_llm_provider_settings.sql`) by design — see "Known pitfalls" below for why this one didn't get auto-applied like everything else.
- **Mimo is both the seeded default and the code-level fallback.** `seed_llm_provider_settings.sql` inserts `mimo` as the only `is_active=true` row. Separately, `LlmClientResolver.FallbackProviderKey = "mimo"` is a hardcoded safety net in `GetActiveClientAsync()`: if `llm_provider_settings` has no `is_active=true` row at all (table not yet applied to Supabase, or someone deactivated everything), it logs a warning and resolves the keyed `mimo` client directly instead of throwing — so a missing/misconfigured table degrades to "use Mimo with its appsettings-configured defaults," not a hard failure of every AI feature. These two are independent: the seed decides what the *DB says* is active; the fallback decides what happens when the DB has *no opinion*.
- **Admin API for switching provider/model/thinking/effort at runtime** — `LlmProviderSettingsController` (`Api/Controllers/LlmProviderSettingsController.cs`), CQRS slice under `Application/Features/LlmProviders/`:
  - `GET /api/v1/llm-provider-settings` — lists all provider rows (`ListLlmProvidersQuery`).
  - `PATCH /api/v1/llm-provider-settings/{providerKey}` — partial update of `ThinkingEnabled`/`Effort`/`ExtraSettingsJson` (`UpdateLlmProviderSettingsCommand` — only non-null fields in the request body change; 404 via `NotFoundException` if the key doesn't exist). **Does not take a `Model` field** — that's `llm_provider_models`, see below.
  - `POST /api/v1/llm-provider-settings/{providerKey}/activate` — makes this provider the active one (`ActivateLlmProviderCommand`). Deliberately does **two sequential `SaveChangesAsync` calls** (deactivate every other currently-active row first, then activate the target) rather than one batched save — the partial unique index `ux_llm_provider_settings_single_active` is checked per-statement in Postgres, not deferred, so activating the new row before the old one's deactivation is committed would transiently violate it within the same transaction.
  - No create/delete endpoints — rows are meant to be seeded via SQL (one per known provider), matching the "reference data, hand-managed" treatment the rest of this table already gets.
- **`llm_provider_models` is both the catalog of known models per provider AND the single source of truth for which one is current.** `Domain/Entities/LlmProviderModel.cs` (`ProviderKey`, `Model`, `Label`, `IsCurrent`, `CreatedAt`) + `LlmProviderModelConfiguration.cs` — unique index on `(provider_key, model)` so a model can only be cataloged once per provider, plus a **partial unique index scoped to `provider_key`** (`ux_llm_provider_models_single_current_per_provider`, `WHERE is_current = true`) so each provider independently has at most one current model — unlike `llm_provider_settings.IsActive`'s partial unique index, which is global (one active provider across *all* rows), this one is per-provider (each provider can each have its own `IsCurrent=true` row simultaneously; selecting a model for `claude` doesn't touch `deepseek`'s current model). Endpoints on the same `LlmProviderSettingsController`:
  - `GET /api/v1/llm-provider-settings/{providerKey}/models` — list the catalog for one provider, each entry's `IsCurrent` included (404 if the provider itself doesn't exist).
  - `POST /api/v1/llm-provider-settings/{providerKey}/models` — add a new cataloged model, always `IsCurrent=false` (409 if `(providerKey, model)` already exists). **Adding a row here never changes what's currently running.**
  - `POST /api/v1/llm-provider-settings/{providerKey}/models/{model}/select` — makes an already-cataloged model the current one (`SelectLlmProviderModelCommand`; 404 if that exact `(providerKey, model)` isn't cataloged yet — add it first). Deliberately does **two sequential `SaveChangesAsync` calls** (un-set any other current row for the *same* `ProviderKey` first, then set the target), same reasoning as `ActivateLlmProviderCommand`. This is the only way to change what model a provider uses — `keeping claude-opus-5 cataloged while also using claude-sonnet-5` is exactly this: both stay in the catalog, `Select` just flips which one is current.
  - **No delete/rename endpoint for a catalog entry, and no way to un-select a current model back to "none" via the API** — consistent with this codebase's append-only-reference-data convention (see the CQRS section's Create+GetById+List-only rationale), but concretely means a typo'd model string added by mistake can only be fixed with direct SQL, and once a provider has a current model, switching to "no current model" (falling back to the adapter's appsettings default) isn't reachable except by picking another model first. Flagged, not yet requested to be fixed.
  - `ListLlmProvidersQuery`'s result now includes `CurrentModel` (nullable — joined from the catalog's `IsCurrent=true` row for that provider, null if none set) so the provider list still shows "what's running" at a glance without a second request.
  - Table creation/seeding follow the exact same hand-run-SQL convention as `llm_provider_settings`, but in **more steps since this table's deploy also had to migrate data off the old `llm_provider_settings.Model` column** — see "Known pitfalls" below for the exact run order (`add_llm_provider_models.sql` → `migrate_llm_provider_settings_model_to_catalog.sql` → optionally `seed_llm_provider_models.sql` → `remove_model_column_from_llm_provider_settings.sql`). The seed only adds models this project has actually confirmed (either live-tested or the exact model-id string independently verified) — currently just `claude-sonnet-5` (the migrate step already carries over whatever was actively in use, e.g. `claude-opus-5`). It deliberately does **not** include a guessed `deepseek-v4-pro` or similar — don't add an unverified model id to this table on a guess; confirm the exact string against that provider's own docs first (same rule that applied to Mimo's whole integration).
- **Secrets (API keys, Claude's WorkspaceId) are environment variables, not config or database** — keys `Llm:Claude:ApiKey`, `Llm:Claude:WorkspaceId`, `Llm:OpenAi:ApiKey`, `Llm:DeepSeek:ApiKey`, `Llm:Mimo:ApiKey`. No code change was needed for this — ASP.NET Core's default config pipeline already merges env vars (`Llm__Claude__ApiKey`, double-underscore = nested-key separator) and **.NET User Secrets** on top of `appsettings.json`; the only change was **removing** the `ApiKey`/`WorkspaceId` values that used to live in `appsettings.Development.json`.
  - **Local dev**: set once via `dotnet user-secrets set "Llm:Claude:ApiKey" "..." --project src/DeepLearning.Api` (repeat per key) — stored in `%APPDATA%\Microsoft\UserSecrets\<UserSecretsId>\secrets.json`, **outside the repo entirely**, auto-loaded by both `dotnet run` and `dotnet test`/`WebApplicationFactory` in Development (verified: the live tests pass with zero `export` needed once secrets are set this way). The Api project's `<UserSecretsId>` in the `.csproj` is just a random GUID pointing at that file — not a secret itself, fine to commit.
  - **CI/production**: real environment variables (`Llm__Claude__ApiKey=...`), same convention as `ConnectionStrings__DefaultConnection` further down this file — User Secrets is Development-only by design and won't be present there.
  - `BaseUrl`, `Model` (fallback only — the DB row's `Model` wins when going through the resolver), and the OpenAI-compatible per-provider fields stay in `appsettings.Development.json` since they aren't secret.
- **Two adapter classes, not four.** `ClaudeLlmClient` has its own shape (Anthropic's Messages API is structurally different — top-level `system`, content-block array, `thinking`/`output_config.effort`). OpenAI/DeepSeek/Mimo all speak the **same** OpenAI Chat Completions wire format (confirmed against each provider's own docs on 2026-08-29 via WebFetch, not assumed from memory — Mimo in particular is easy to get wrong by guessing), so they share **one** `OpenAiCompatibleLlmClient`, parameterized per provider by `OpenAiCompatibleOptions` (base URL, auth header name/prefix — Mimo uses a bare `api-key` header, not `Authorization: Bearer`, model id, and the output-length field name — DeepSeek uses `max_tokens`, OpenAI/Mimo use `max_completion_tokens`). Adding a 5th OpenAI-shaped provider needs **zero new C#**: one more named-options section + one more `AddKeyedTransient` line in `DependencyInjection.cs`, plus one more `llm_provider_settings` row. Adding a structurally different provider (Gemini, etc.) means one more adapter class shaped like `ClaudeLlmClient`.
- **`ThinkingEnabled`/`Effort` are honestly scoped to Claude only.** Claude: `ThinkingEnabled=false` sends `thinking:{type:"disabled"}` (omitted otherwise, runs adaptive); `Effort` maps to `output_config.effort`. For OpenAI/DeepSeek/Mimo, "thinking" isn't a universal boolean in the Chat Completions format — OpenAI's reasoning models use separate model ids or a Responses-API-only field, DeepSeek's reasoning is a distinct model name, Mimo's mechanism isn't confirmed — so rather than guess a field name, `OpenAiCompatibleLlmClient` leaves those two alone and relies on `ExtraSettings` (JSONB passthrough, merged directly into the request body — e.g. `{"reasoning_effort":"high"}`) as the generic escape hatch for whatever provider-specific knob is needed once actually confirmed against that provider's docs.
- **Raw `HttpClient`, not official provider SDKs — deliberate.** Matches the design doc's own "HttpClient+Polly" architecture, and a uniform raw-HTTP adapter shape is what actually makes swapping/adding providers cheap; the resilience pipeline (`LlmResiliencePipeline.cs`, via `Microsoft.Extensions.Http.Resilience` — Polly v8 under the hood) attaches to `HttpClient`, not to an SDK client, and is shared by all 4 providers' HttpClients.
- **Real bugs found only by actual live calls, all fixed**:
  1. Sending `"system": null` in Claude's request body (instead of omitting the key) got a real 400 ("system: Input should be a valid array") — fixed with `[JsonIgnore(Condition = JsonIgnoreCondition.WhenWritingNull)]` on `ClaudeLlmClient`'s request DTO.
  2. `AddStandardResilienceHandler`'s library defaults (10s per-attempt / 30s total timeout) are tuned for ordinary REST calls, not an LLM completion — a real Claude question-generation call with default adaptive thinking took longer than that and tripped `Polly.Timeout.TimeoutRejectedException`, uncaught by the original `catch (HttpRequestException)` clause, surfacing as a raw 500 instead of a clean `AiCallFailedException`→503. Fixed by widening the catch clause (both adapters) and raising `AttemptTimeout`/`TotalRequestTimeout` to 60s/180s in `LlmResiliencePipeline.Configure` — note the circuit breaker's `SamplingDuration` must stay ≥ 2× `AttemptTimeout` or `AddStandardResilienceHandler` fails **at startup** with an `OptionsValidationException`, not at call time.
  3. OpenAI's live test fails with 429 `insufficient_quota`/`credit_balance_exhausted` — that account has no billing credits. Not a code bug: the request is correctly authenticated (a bad key would be 401) and Polly correctly retried 3 times before giving up. DeepSeek and Mimo both succeeded for real on the same run, including again after secrets moved to env vars.
- **`prompt_templates` needed a new row for Step 3 to work at all**: the exam_specific/question_gen row seeded back in Step 1 only specifies content requirements (topic, difficulty), not an output contract — because the code that would consume it didn't exist yet. Added one new `shared_methodology`/`question_gen` row (subject_category=`translation`) via the real `POST /api/v1/prompt-templates` endpoint instructing the model to output *only* the JSON shape `GenerateQuestionCommandHandler` parses. If question generation ever starts failing to parse, check this row (`prompt_templates` where `template_type='question_gen' AND layer='shared_methodology'`) hasn't been deactivated or superseded incompatibly. This row instructs JSON output generically — it isn't Claude-specific, so it works unchanged no matter which provider is active.
- **Live-call tests are excluded from the default run** — see "Running the tests" below. `ClaudeLlmClientLiveTests.cs` and `OpenAiCompatibleLlmClientLiveTests.cs` (3 methods — one per OpenAI-shaped provider) both resolve their `ILlmClient` by DI key directly, bypassing `ILlmClientResolver`/the database entirely — they're testing the adapters, not the provider-switch mechanism. Requires the env vars above to be set.
- **Test-coverage gap, found by audit on 2026-08-29, closed same day**: no single test exercised the full real chain — real Postgres rows → `LlmClientResolver` querying them → keyed-DI resolution → an actual HTTP call. `LlmClientResolverTests.cs` (Infrastructure/Ai) covers the resolver's merge/fallback logic but against fake `ILlmProviderSettingsRepository`/`ILlmProviderModelRepository` implementations, never a real Postgres. `GenerateQuestionControllerTests.cs` swaps `ILlmClientResolver` itself for a fake (`FakeLlmClientResolver`), so it never ran the real resolver at all. The live-call tests above bypass the resolver entirely. Closed by `tests/DeepLearning.UnitTests/Api/LlmClientResolverFullChainTests.cs`: uses `ApiWebApplicationFactory.WithWebHostBuilder(...).ConfigureTestServices(...)` to re-register the keyed `"claude"`/`"deepseek"` `ILlmClient` *after* `AddInfrastructure`'s own registration (DI resolves the last registration for a given service+key, so the override wins) — the override still constructs the real `ClaudeLlmClient`/`OpenAiCompatibleLlmClient` classes, just wired to a `HttpClient` backed by an in-memory `HttpMessageHandler` returning a canned response instead of a real socket. Seeds real `llm_provider_settings`/`llm_provider_models` rows into the same Testcontainers Postgres the factory already migrates, then calls the real `LlmClientResolver` end to end and asserts the DB-driven model string reached the outgoing (faked) request body. Costs zero tokens/dollars, needs no API keys, not tagged `LlmIntegration` — runs on every `dotnet test`.

### Development-only AI call tracing (added 2026-08-30, user request)

- **`Infrastructure/Ai/AiTracingHandler.cs`** is a `DelegatingHandler` attached to every provider's `HttpClient` (`DependencyInjection.cs` captures the `IHttpClientBuilder` from `AddHttpClient<ClaudeLlmClient>`/`AddHttpClient("llm-openai-compatible")` into a variable, then calls `.AddStandardResilienceHandler(...)` and `.AddHttpMessageHandler<AiTracingHandler>()` on it separately — `AddStandardResilienceHandler` returns `IHttpStandardResiliencePipelineBuilder`, not `IHttpClientBuilder`, so it can't be chained directly into `AddHttpMessageHandler`, but both still append to the same underlying handler list in call order). Registered **after** the resilience handler, making it the *inner* handler — a Polly retry re-invokes everything inside it, so each logged "AI call #N" is a real outbound HTTP attempt, including retries, not one entry per logical `ILlmClient.CompleteAsync` call.
- **No-op outside Development** — checks `IHostEnvironment.IsDevelopment()` internally per call rather than being conditionally registered, so the DI wiring stays simple and the same either way; the check is cheap when it short-circuits. `dotnet run` picks up `Development` automatically via `Properties/launchSettings.json`; `WebApplicationFactory`-based tests default to `Production` (confirmed empirically — the full suite stayed clean, no tracing output), so **none of the test infrastructure needed to change**.
- **Logs the raw request/response JSON bodies verbatim** — deliberately at the HTTP layer rather than wrapping `ILlmClient`, so Claude's extended-thinking content comes along for free when thinking is enabled: `ClaudeLlmClient`'s own response parsing discards thinking blocks and keeps only the final text, but that parsing happens *after* this handler has already seen and logged the untouched raw body. No separate thinking-capture logic was needed.
- **Never logs headers** — `x-api-key` (Claude) and `Authorization`/`api-key` (the OpenAI-compatible clients) carry real secrets; only the method, URI, status code, elapsed time, and bodies are logged.
- **Correctness hazard avoided**: reading `HttpContent` off a one-shot stream exhausts it, which would leave `ClaudeLlmClient`/`OpenAiCompatibleLlmClient`'s own subsequent `ReadAsStringAsync()` call with nothing. Fixed by calling `LoadIntoBufferAsync()` before reading — once buffered, `HttpContent` supports being read any number of times. `AiTracingHandlerTests.cs` pins this down directly (asserts the response body is still intact after the handler runs, in both Development and non-Development modes, plus a content-less GET request) rather than trusting it by inspection.
- **Fixed a real, previously-dormant gap while wiring this up**: `Program.cs` never actually called `UseSerilog(...)` — `Serilog.AspNetCore` was referenced and `CorrelationIdMiddleware` was already pushing `CorrelationId` into `Serilog.Context.LogContext`, but with no Serilog sink ever configured, that push had nowhere to go. Fixed with a minimal `builder.Host.UseSerilog(...)` (Console sink, `Enrich.FromLogContext()`, `Microsoft.AspNetCore` overridden to `Warning`) — this is also what makes `AiTracingHandler`'s log entries carry the originating HTTP request's `CorrelationId` (the outbound `HttpClient` call runs inside the same async flow, and `LogContext` is `AsyncLocal`-based), giving real request-to-AI-call traceability without any extra plumbing.
- **Deliberately console-only, no separate file sink and no dev HTTP endpoint for browsing recent calls** — asked and the user picked Serilog console/structured logs only. If a dedicated `logs/ai-calls-.log` file or a `GET /api/v1/dev/ai-calls` browsing endpoint is wanted later, `Serilog.Sinks.File` and an in-memory ring buffer + dev-only controller are the natural next additions, not a redesign.

## Submissions & grading (Step 4): state machine, AI orchestration, structured-output validation

- **`Submission.TransitionTo(SubmissionStatus)`** (Domain/Entities/Submission.cs) is the whole state machine from design doc §4.1, encoded as a `Dictionary<SubmissionStatus, SubmissionStatus[]>` of legal next-states — `draft→submitted→grading→{grading_failed,graded}`, `grading_failed→{grading,grading_abandoned}` (the retry path — `grading_abandoned` itself is still never reached automatically, see the retry-executor note below; nothing auto-abandons a submission, that stays a manual/caller decision, deliberately not built), `graded→{under_dispute,archived}`, `under_dispute→{standard_revised,graded}`, `standard_revised→graded`. An illegal move throws `InvalidSubmissionStateException` (a `ConflictException`, so it's a 409, not a 400/404).
- **The idempotency guarantee under genuine concurrency — found broken by a full audit, fixed same day (2026-08-30).** There is deliberately no separate idempotency-key column on `submissions` (the design doc §7 calls for one, but the schema never grew a field for it); `Submission.TransitionTo(grading)` alone only ever guarded **sequential** misuse (a second, later grade() call on an already-`Graded`/`Grading` submission correctly 409s) — it did nothing for two `Handle` calls that both read `Submitted` before either commits, which would both pass the in-memory check and both persist their own `GradingResult`/`ErrorListItem` rows for the same submission. **Fixed with Postgres's built-in `xmin` system column as an EF optimistic-concurrency token** — `SubmissionConfiguration.Configure` maps a shadow `uint xmin` property with `.IsRowVersion()` (no new column, no data migration: `xmin` already exists on every Postgres table). `UnitOfWork.SaveChangesAsync` (Infrastructure) catches EF's `DbUpdateConcurrencyException` and translates it to `ConflictException` (Application can't reference EF Core directly, so the translation has to happen at the Infrastructure/Application boundary, not in the handler) — whichever of the two racing `SaveChangesAsync` calls loses gets a clean 409 instead of silently double-writing. **A migration exists (`20260830123650_AddSubmissionXminConcurrencyToken`) but its `Up()`/`Down()` are deliberately empty** — EF's migration diff sees a "new" xmin property and by default wants to `AddColumn`, but `xmin` is a reserved Postgres system column name; running that literal `AddColumn` would fail outright. The migration file exists only so `__EFMigrationsHistory`/`AppDbContextModelSnapshot.cs` stay consistent for future `migrations add` diffing — safe to run `dotnet ef database update` for it, it changes nothing in the real schema. Proven for real (not just by inspection) by `Integration/SubmissionConcurrencyTests.cs`: two separate `AppDbContext`s both load the same `Submitted` row, the first `TransitionTo(grading)`+save succeeds, the second's identical attempt throws `DbUpdateConcurrencyException` — deterministic (two contexts racing over one row), not a flaky `Task.WhenAll`-based timing test.
- **§4.2's AI-retry sub-state-machine — found half-real by the same audit (`AttemptCount`/`MaxRetries` were dead, every validation failure went straight to final_failure on attempt 1), fixed same day.** See the new "AI-call retry executor (design doc §4.2)" section below — the fix is shared across all 4 AI-orchestration handlers, not just grading, so it's documented once there rather than repeated per-step. `SubmissionStatus.grading_abandoned` is still never reached automatically post-fix — by design: the retry executor's job is "retry a few times within one grade() call," not "decide the submission is a lost cause." A submission that still ends up `GradingFailed` after the retry executor gives up is retried by the caller invoking grade() again, same as before.
- **`GradeSubmissionCommandHandler`** (Application/Features/Submissions/Commands/GradeSubmission) is the AI-orchestration handler, same shape as `GenerateQuestionCommandHandler` (Step 3): create an `AiCallLog` row + transition the submission to `Grading`, save immediately so both survive a hung call; build the prompt via `IExamConfigLoader`/`PromptRenderer` (unchanged from Step 3); call `ILlmClientResolver.GetActiveClientAsync()` (also unchanged — grading goes through the same DB-driven provider switch as question generation); parse the JSON response; validate it; persist `GradingResult`/`ErrorListItem` rows; transition to `Graded`. Any failure at any of those steps transitions the submission to `GradingFailed` and marks the `AiCallLog` `final_failure` before rethrowing (`FailAsync`, mirroring `GenerateQuestionCommandHandler`'s own `FailAsync`) — the caller retries by calling grade again, which is legal from `GradingFailed`.
- **Isolation (design doc §10.2) is structural, not a prompt reminder**: the handler only ever loads `Question.SourceText`, `Question.FlawedTranslationText` (TaskB only — see below), the submission's own `Content`, `MeaningCheckpoint` rows, and (TaskB only) `TaskBSeededError` rows. At the time this was originally written, `IReferenceTranslationRepository` didn't exist at all, which was itself the guarantee. Step 7 later added that interface (for reference-translation generation) and injected it into `CreateFollowUpQuestionCommandHandler` (for reference-translation follow-ups, see "Reference-translation follow-ups" below) — `GradeSubmissionCommandHandler` still does **not** inject it and has no code path to `reference_translations`, so the isolation guarantee itself is unchanged; only the "the interface doesn't even exist" reasoning for it is now historical.
- **TaskB grading sends `Question.FlawedTranslationText` (the full text the user was annotating), not just `SourceText`** — `TaskBSeededError.PositionStart/PositionEnd` are character offsets into that flawed text, so without the text itself the AI has positions and category labels with nothing to locate them against and can't judge whether the user's annotations are actually correct. This was missing from the first version of `BuildTemplateModel`/`add_grading_content_prompt_template.sql` — caught by inspection the same day, before the SQL file was ever run against real Supabase — and is now covered by `SubmissionsControllerTests.Grade_for_task_b_includes_the_flawed_translation_text_in_the_prompt_sent_to_the_ai` (uses a prompt-capturing fake `ILlmClient` to assert on the actual rendered prompt, not just on persisted output).
- **`ExamTypeId` is caller-supplied on `GradeSubmissionCommand`, not derived from the Submission/Question** — same precedent as `GenerateQuestionCommand`. `Question` has no `exam_type_id` column (design doc §9.4 defers that FK until a second exam type exists), and the MVP only has one exam type anyway, so there's nothing to derive it from.
- **Structured-output validation is a hard constraint in code, not a prompt reminder** (design doc §10.3 — grading is where this first actually applies, since `error_category`/`dimension_key` only exist on grading output, not on question generation): every `dimensionKey` in the AI's response — both in `dimensions[]` and in each `errors[].dimensionKey` — must match a `dimension_key` among the `AssessmentDimension` rows loaded for that exam type + task type, or `RubricVersionNotFoundException` (a 404) is thrown; every `errors[].errorCategory` must match a `category_key` among the loaded `ErrorTaxonomy` rows, or the call is rejected (`AiCallFailedException`, a 503) — an AI response referencing a category/dimension not on file is never persisted, matching how `GenerateQuestionCommandHandler` already treats an unparseable JSON response as a hard failure rather than trying to salvage it.
- **`IGradingResultInterpreter` picks per-`scale_type` pass/fail logic** (`Infrastructure/Ai/GradingResultInterpreters/{Band15,Score100,RubricLevel}Interpreter.cs`), registered as three `IGradingResultInterpreter` entries in DI and selected in the handler via `IEnumerable<IGradingResultInterpreter>.ToDictionary(x => x.ScaleType)`. **Only `Band15Interpreter` has real data behind it** — NAATI CT's `assessment_dimensions` are 100% `scale_type='band_1_5'`, and every `level_descriptions` row numbers Band 1 as the best performance and Band 5 the worst (verified against the seeded rubric text), so `Band15Interpreter` reads `"Pass: Band 2 or above"` as "Band 2 or numerically better" (`pass_bool = reported_band <= threshold_band`). `Score100Interpreter`/`RubricLevelInterpreter` exist so the dispatch is real rather than a stub, but their bucketing/comparison logic is a documented placeholder with zero real exam-type data to validate it against — revisit both once a second exam type actually uses either scale.
- **`grading_results.band` is a fixed `INT 1-5` column regardless of `scale_type`** (schema's own `ck_grading_results_band_range` CHECK constraint) — `Score100Interpreter` buckets a 0-100 score into that 1-5 range for storage (`>=90→1 … <40→5`), also an unverified placeholder given zero real score_0_100 data exists yet.
- **A new `prompt_templates` row was needed, same reason as Step 3's question_gen row**: the three grading rows seeded by `seed_naati_ct_en_zh.sql` only specify HOW to grade (rubric criteria, error taxonomies, task-type pass thresholds) — none of them existed to inject the actual material to grade or an output contract, because `GradeSubmissionCommandHandler` didn't exist when they were written. [add_grading_content_prompt_template.sql](src/DeepLearning.Infrastructure/Persistence/Sql/add_grading_content_prompt_template.sql) adds one `shared_methodology`/`grading` row supplying `{{ source_text }}`/`{{ flawed_translation_text }}`/`{{ submission_content }}`/`{{ meaning_checkpoints }}`/`{{ seeded_errors }}` and the exact JSON contract (`dimensions[]`/`errors[]`, camelCase keys) `GradeSubmissionCommandHandler` parses — same hand-run-SQL convention as `llm_provider_settings`/`llm_provider_models`. **Applied to the real Supabase DB by the user on 2026-08-30.** The Testcontainers test DB never runs this file either way — tests seed their own minimal `PromptTemplate` rows directly. If grading ever starts failing to parse, check this row (`prompt_templates` where `template_type='grading' AND layer='shared_methodology'` with the content-injection variables) hasn't been deactivated.
- **Scriban's nested-dictionary iteration (`{{ for band in dim.level_descriptions }}`) had never been exercised before Step 4** — the seeded grading prompt's `{{ for dim in dimensions }} ... {{ for band in dim.level_descriptions }}` shape (iterating a `Dictionary<string,string>` nested inside a list of anonymous objects) was written into `seed_naati_ct_en_zh.sql` back before grading existed, so nothing had ever rendered it. Pinned down by `tests/DeepLearning.UnitTests/Infrastructure/Ai/PromptRendererDimensionRenderingTests.cs` (calls `PromptRenderer` directly, no DB) before `GradeSubmissionCommandHandler` was built on top of the assumption that it works.
- **`CreateSubmissionCommandHandler`** rejects a `TaskType` mismatch between the request and the target `Question` (a `Question` created as TaskType.B can't be submitted against as TaskType.A) via a manually-thrown `FluentValidation.ValidationException` — this lives in the handler rather than the `AbstractValidator`, same reasoning as `ImportUserQuestionValidator`'s cross-field checks: it needs a DB lookup (`Question.TaskType`) that a pure `AbstractValidator` (no repository access) can't do. `Submission.Content` is raw JSON text (same `jsonb`-backed convention as `Question.Brief`) — TaskA sends a JSON-encoded string, TaskB a JSON array of `{positionStart, positionEnd, errorCategory, correctedText}` annotation objects (`CreateSubmissionValidator.HaveConsistentTaskShape`, added 2026-08-30 — see below; positions are offsets into the question's `FlawedTranslationText`, same convention as `TaskBSeededError`).

## AI-call retry executor (design doc §4.2, added 2026-08-30, self-audit fix)

Fixes the "half-real §4.2 retry sub-state-machine" gap (see the top-of-file audit note) — applies identically to all 4 AI-orchestration handlers (`GenerateQuestionCommandHandler`, `GradeSubmissionCommandHandler`, `CreateFollowUpQuestionCommandHandler`, `GenerateDeepLearningContentCommandHandler`), documented once here rather than per-step.

- **Two genuinely different layers of "retry" exist, and only one of them was ever real.** `LlmResiliencePipeline.cs`'s Polly config retries HTTP-transport failures (timeouts/429/5xx) **inside** one `ILlmClient.CompleteAsync()` call — that was already correct (§7's "最多3次重试,指数退避+熔断"), untouched by this fix. What was missing: a 200-OK response whose *content* fails structured-output validation (malformed JSON, an `errorCategory`/`dimensionKey` not on file, etc.) used to be treated as an immediate, single-shot `final_failure` — Polly never sees this at all, since it only inspects transport-level outcomes, not response bodies.
- **`Application/Interfaces/IAiCallRetryExecutor.cs`** (impl: `Infrastructure/Ai/AiCallRetryExecutor.cs`, registered `AddSingleton` in `DependencyInjection.cs`) — `Task<T> ExecuteAsync<T>(AiCallLog log, Func<Task<T>> attempt, CancellationToken)`. Runs `attempt`; on any exception, increments `log.AttemptCount` and retries with exponential backoff + jitter (2s/4s/8s.../base delay configurable via constructor, defaults to 2s) as long as `AttemptCount < MaxRetries`, otherwise lets the exception propagate unchanged so the handler's own `catch`/`FailAsync` logic still decides the final state — this executor only owns *whether to retry*, never the failure-handling policy itself.
- **Each handler wraps only the "build request → call LLM → parse → validate" portion**, not the later entity-construction/persist step — a DB write failure isn't something re-prompting the AI would fix. For `GradeSubmissionCommandHandler`/`CreateFollowUpQuestionCommandHandler`/`GenerateDeepLearningContentCommandHandler` this meant splitting what used to be one big "everything from the LLM call onward" try/catch into two: an inner retry-wrapped one for "get a valid payload" and an outer one (unchanged in spirit) for "persist it." `GenerateQuestionCommandHandler` already had this shape as two separate try blocks, so it just needed the first one's body moved inside the executor's delegate.
- **Test-speed pitfall already hit and fixed**: the executor's real 2s/4s/8s backoff would make every existing "AI response is invalid" test sit through real multi-second sleeps for no product-relevant reason. `ApiWebApplicationFactory.ConfigureWebHost` overrides `IAiCallRetryExecutor` with a 1ms base delay for the whole API test collection — retry/attempt-count behavior is still exercised for real, just fast. Direct unit tests of the executor (`Infrastructure/Ai/AiCallRetryExecutorTests.cs`) construct their own instance with an explicit tiny delay the same way.
- **Tests**: `Infrastructure/Ai/AiCallRetryExecutorTests.cs` (pure, no DB/HTTP — succeeds first try without incrementing AttemptCount, retries then succeeds with AttemptCount matching the number of real calls, gives up after exactly `MaxRetries` attempts and rethrows the last exception, `MaxRetries=1` never retries at all, respects cancellation mid-backoff) and `Api/GenerateQuestionControllerTests.Generate_retries_on_a_malformed_ai_response_and_succeeds_once_the_ai_returns_something_valid` (end-to-end through the real API + real Postgres — a fake `ILlmClient` returns unparseable garbage twice then a valid response the third time, asserts 201 Created and that the persisted `AiCallLog.AttemptCount` is really `3`, not `1`).

## Auth (Supabase JWT), added 2026-08-30

Registration/login are entirely Supabase Auth's job now — this backend never issues or validates credentials itself, only validates the JWT Supabase Auth already issued (design decision, user-confirmed: front-end/clients call Supabase Auth's own REST API directly for sign-up/sign-in; nothing here proxies that). Auth is **opt-in, not `[Authorize]`-enforced** on any existing endpoint (user-confirmed decision) — every endpoint that used to require an explicit `UserId`/`CreatedBy` in the request body/query still accepts one, but a valid JWT's identity always wins when present. This was a deliberate choice to keep all 220+ pre-existing tests working unchanged (none of them send a JWT) while still letting new, authenticated calls omit the id entirely.

- **JWT verification**: `Program.cs` configures `AddAuthentication().AddJwtBearer(...)` against `Supabase:ProjectUrl` (new appsettings key — real value goes in `appsettings.Development.json`, same non-committed-secrets convention as `ConnectionStrings`; already filled in there since the Supabase project ref is derivable from the existing connection string). `options.Authority = "{ProjectUrl}/auth/v1"` — Supabase's newer **asymmetric JWKS signing** (user-confirmed this project's setup), so ASP.NET Core auto-discovers the public signing keys, no secret to store. `options.MapInboundClaims = false` so claims keep their raw JWT names (`sub`, `email`) instead of being remapped to the long `ClaimTypes.*` URIs. **Not yet verified against a real Supabase project's token** — the one piece flagged as needing a real end-to-end check: whether Supabase's `/auth/v1` truly serves the OIDC discovery document `Authority`-based config expects at `.well-known/openid-configuration`. If a real token ever fails to validate, this is the first thing to check — the fallback fix is `options.MetadataAddress` pointed directly at `{ProjectUrl}/auth/v1/.well-known/jwks.json` instead of relying on `Authority` discovery. If `Supabase:ProjectUrl` is unset (e.g. a fresh clone before the config is filled in), `AddJwtBearer`'s configure action returns early — no crash, tokens just never validate, same "missing config degrades gracefully" precedent as `LlmClientResolver`'s fallback.
- **`Application/Interfaces/ICurrentUserService`** (`UserId`/`Email`, both nullable) — impl `Api/Services/CurrentUserService.cs` via `IHttpContextAccessor`, reading the `sub`/`email` claims off `HttpContext.User`. Lives in Api (not Infrastructure) because `IHttpContextAccessor` is an ASP.NET Core hosting concept — same layering precedent as `GlobalExceptionHandler`/`CorrelationIdMiddleware`. Every controller that needs a user id now does `_currentUser.UserId ?? request.UserId` (or the equivalent for `CreatedBy`) — `SubmissionsController`, `FollowUpsController`, `ReviewLibraryController` (all 4 actions — `userId`/`request.UserId` are now `Guid?`, falling through to `Guid.Empty` only if truly neither source has one), `WeakPointsController`, `QuestionsController` (`Import`/`Generate`). **The Application-layer Commands/Queries themselves are unchanged** — they still just take a `Guid`/`Guid?` UserId parameter; only the Api-layer controllers gained a second, JWT-sourced input to prefer. No `[Authorize]` attribute anywhere yet — deliberately deferred, see above.
- **`Api/Middleware/EnsureUserProfileMiddleware.cs`** (registered after `UseAuthentication()`, before `UseAuthorization()`/`MapControllers()`) syncs a `public.users` row from a validated JWT's `sub`/`email` claims the first time that `sub` is seen — Supabase's `auth.users` and this project's own `public.users` are separate tables, and every FK-constrained table (`submissions.user_id`, `weak_points.user_id`, etc.) needs a `public.users` row to point to. Deliberately **not** a Postgres trigger on `auth.users` (the standard Supabase-idiomatic approach) — that would need hand-run SQL against a schema this project's own migration tooling doesn't manage, and wouldn't be testable via `WebApplicationFactory`. Instead: plain C# middleware, `GetByIdAsync` check + insert-if-missing, only runs (any DB work at all) for requests that actually carry a valid JWT — zero overhead for the anonymous/explicit-`UserId` path. A concurrent double-insert race for the exact same brand-new `sub` (two requests both see "doesn't exist yet") is caught (`DbUpdateException`, from the `Username`/`Email` unique indexes) and swallowed, not treated as an error.
- **`User.PasswordHash` is now nullable, not removed** — Supabase Auth owns credentials, so nothing writes to this column anymore, but design doc §7's "migrations only add, never remove" discipline (see the top-of-file audit note about the one migration that already broke this once) means the column itself stays. `UserConfiguration.cs` drops `.IsRequired()`; migration `20260830122531_MakeUserPasswordHashNullable` is a real, safe `AlterColumn` (loosening a constraint, not narrowing one) — **applied to the real Supabase DB, confirmed 2026-08-31**.
- **Removed entirely, not deprecated-in-place**: `RegisterUserCommand`/`Handler`/`Validator`/`Result`, `IPasswordHasher`/`Pbkdf2PasswordHasher`, and `UsersController`'s `POST` registration action. These won't ever be called again now that Supabase Auth owns sign-up — kept-but-dead code here would just be confusing, unlike the `PasswordHash` column (which stays because dropping *columns* specifically violates the stated migration discipline; deleting dead *C# code* doesn't). `UsersController` now only has `GetById` (profile reads still useful).
- **Tests**: `Api/JwtAuthenticationTests.cs` — self-signs a test JWT with a symmetric key (via `PostConfigure<JwtBearerOptions>` in `ConfigureTestServices`, overriding `Program.cs`'s real Authority-based config for just that test client) so tests never need a real Supabase project; proves a valid JWT creates the `public.users` profile row on first sight, a second request from the same JWT doesn't error or duplicate it, requests without any JWT still work off the body-supplied `UserId` (nothing broken for the 220+ pre-existing tests), and — the actual point of making this opt-in rather than replacing the old field — a JWT's identity overrides an explicit-but-different `UserId` in the request body. Existing test files that used to seed a test user via the (now-removed) `POST /users` endpoint were switched to `ApiWebApplicationFactory.SeedUserAsync()` (new helper, direct `DbContext` insert) — `SubmissionsControllerTests`, `DeepLearningContentControllerTests`, `FollowUpsControllerTests`, `SubmissionGradedDomainEventTests`, `UsersControllerTests` (this last one rewritten down to just the two `GetById` tests, since there's no create endpoint left to test).

## Rubric versioning enforcement (design doc §10.1, fixed 2026-08-31)

Closes the last of the 5 audit-found gaps (see the top-of-file list — this one was originally left as "advisory only, user's call to defer," then picked up the next day).

- **The actual failure mode this prevents**: `assessment_dimensions.effective_from`/`effective_to` existed but nothing enforced "exactly one effective version of a given `dimension_key` at a time." If a second `rubric_version` row for the same `dimension_key` were ever inserted while the first was still open-ended, both rows would load from `ListByExamTypeAsync` simultaneously, and `GradeSubmissionCommandHandler`'s `dimensionsByKey = dimensions.ToDictionary(x => x.DimensionKey)` would throw `ArgumentException` (duplicate key) — a hard crash on the very next grading call for that exam type, not a soft "which version wins" ambiguity.
- **`IAssessmentDimensionRepository.ListByExamTypeAsync` now filters to the currently-effective window** — `WHERE EffectiveFrom <= now() AND (EffectiveTo IS NULL OR EffectiveTo > now())`, in addition to the existing `ExamTypeId`/`ApplicableTaskType` filters. `now` is captured once as a local `DateTimeOffset.UtcNow` per call (EF Core parameterizes this normally, no special handling needed). This is the query every grading call and every prompt-build goes through, so this one change is what actually prevents the `ArgumentException` — everything else below is what keeps the data in a shape this filter can rely on.
- **`IAssessmentDimensionRepository.ListOpenEndedByKeyAsync(examTypeId, dimensionKey)`** (new) returns whatever row(s) for that `dimension_key` still have `EffectiveTo == null` — i.e. haven't yet been superseded. `CreateAssessmentDimensionCommandHandler` calls this right after the existing exact-duplicate (`ExamTypeId`+`DimensionKey`+`RubricVersion`) check, and for each row found: if that row's own `EffectiveFrom` is already `>=` the new request's `EffectiveFrom`, the whole request is rejected with a 400 (`FluentValidation.ValidationException` thrown directly from the handler, same "hard constraint needs a DB lookup an `AbstractValidator` can't do" convention as `CreateSubmissionCommandHandler`'s `TaskType` check) — inserting a version that would need to retroactively end before it began is refused rather than silently corrupting the audit chain. Otherwise, the prior row's `EffectiveTo` is set to the new row's `EffectiveFrom`, keeping the effective windows contiguous (no gap, no overlap) — both the close-out and the new insert happen in the same `SaveChangesAsync` call, so it's atomic.
- **Deliberately scoped to `(ExamTypeId, DimensionKey)` only, ignoring `ApplicableTaskType`** — a dimension's applicable-task-type scoping is treated as part of its identity across versions (you revise "meaning_transfer," you don't redefine which task types it applies to mid-revision), so closing out is keyed on the name alone, not name+task-type.
- **No new migration needed** — `EffectiveFrom`/`EffectiveTo` already existed on `assessment_dimensions` since the original scaffold; this is purely a query-filter + handler-logic change.
- **Tests**: `Integration/AssessmentDimensionRepositoryTests.cs` — `ListByExamTypeAsync` excludes both a closed-out (past `EffectiveTo`) and a not-yet-started (future `EffectiveFrom`) row, returning only the one actually in its effective window; `ListOpenEndedByKeyAsync` excludes an already-closed row. `Api/AssessmentDimensionsControllerTests.cs` — creating a second version closes out the first (proven both via the list endpoint showing only the new `RubricVersion` and by reading the old row directly to confirm its `EffectiveTo` was actually set, with a small time-tolerance rather than exact-tick equality since a `DateTimeOffset` round-tripping through Postgres's microsecond-precision `timestamptz` can lose sub-microsecond precision); a second version whose `EffectiveFrom` would precede the current one's returns 400.

## Follow-ups & Rubric calibration (Step 5): observing/active state machine, auto- vs. manual-activation

- **`standard_overrides` is NOT a mechanism for rewriting the official rubric** (user-corrected 2026-08-30, same day as the initial build — the first version of this section and of `add_followup_prompt_template.sql` framed it that way, which was wrong). `assessment_dimensions.level_descriptions` stays authoritative and untouched; a `StandardOverride` row is a **correction note that patches how the AI applies the standard** in a recurring situation. `OriginalRuleText`/`RevisedRuleText` hold "what the AI's flawed judgment was" / "what it should conclude next time in a similar situation," not before/after rubric wording.
- **The prompt asks the AI to self-review against an 8-category checklist of ways its own prior judgment could have been wrong** (expanded same day from an initial 2-example list, also by user feedback) — not just "missed an error": false positive (flagging a correct translation as wrong, often because the AI's own internally-generated "ideal phrasing" quietly became an invisible answer key — the same reference-answer contamination risk §10.2 already guards against for `reference_translations`, just harder to spot since it never touches that table), source-text misreading, error miscategorized (right that it's wrong, wrong about which of the 8 `error_taxonomies` categories), wrong dimension attributed (worse than miscategorizing — each dimension has its own Band text/pass threshold, so misattribution inflates one dimension and deflates another), Band severity miscalibrated, cumulative density missed (§5's individually-minor-but-taken-together principle — a missed *relationship* between errors, not a missed error itself), inconsistent repeat judgment (no external cause, the AI is just unstable call to call), and (TaskB only, rendered via `{{ if task_type == "B" }}`) position mismatch (matching the user's annotation to the wrong seeded error). See `add_followup_prompt_template.sql`'s top comment and its 重要说明 block for the full wording; `PromptRendererFollowUpTemplateRenderingTests.cs` pins down that the TaskB-conditional bullet actually renders/omits correctly around this much Chinese punctuation (same "exercise the exact Scriban shape before building on top of it" precedent as `PromptRendererDimensionRenderingTests.cs` from Step 4).
- **`CreateFollowUpQuestionCommandHandler`** (Application/Features/FollowUps/Commands/CreateFollowUpQuestion) implements design doc §2.1's Q/R/S/T nodes and §10.6's calibration mechanism, same AI-orchestration shape as `GradeSubmissionCommandHandler`/`GenerateQuestionCommandHandler`. It requires the submission to already be `Graded` — `submission.TransitionTo(SubmissionStatus.under_dispute)` is the first mutating step, so a submission still `Grading`/`GradingFailed`/etc. gets a 409 (`InvalidSubmissionStateException`) before any AI call is even attempted. The AI answers the question and returns a `verdict` (`user_correct`/`user_incorrect`/`partial` — never `pending`, which is rejected as invalid AI output); `user_correct` additionally proposes a `standardRevision` (`scope`/`dimensionOrRule`/`originalRuleText`/`revisedRuleText`). The submission always ends back at `Graded`: `user_incorrect`/`partial` transition straight back, `user_correct` passes through `StandardRevised` first per §4.1's state machine (`Graded → UnderDispute → StandardRevised → Graded`). Unlike `Submission`, `FollowUpQuestion` has no state machine of its own and no "in-progress" persisted row — it's only constructed and saved once a valid AI response has been parsed; a failed AI call just fails the `AiCallLog` and resets the submission back to `Graded`, so the user simply resubmits the follow-up.
- **A `standard_overrides` row is insert-only and always starts `observing`** (never immediately authoritative, per §10.6) — `PreviousOverrideId` is set to whatever `StandardOverride` is currently `active` for that exact `(Scope, DimensionOrRule)` pair (`IStandardOverrideRepository.GetActiveByRuleAsync`), or `null` if none exists yet, forming the audit chain. **`StandardOverride` has no `exam_type_id` column** (design doc §9.4 defers that FK, same as `Question`), so this matching is global across all exam types by design — tests must use a unique `dimensionOrRule` string per scenario or they'll pollute each other's confirmation counts (see `FollowUpsControllerTests`' per-test GUID-suffixed `dimensionKey`).
- **Two independent activation paths, both landing on the same `(status=active, EffectiveFrom=now)` update, and both deprecating whatever was previously active for that rule**:

  2. **Manual, "经过一次人工复核"** (`Application/Features/StandardOverrides/Commands/ActivateStandardOverride` → `POST /api/v1/standard-overrides/{id}/activate`): promotes a specific `observing` row regardless of confirmation count. 409 (`ConflictException`) if the target isn't currently `observing` (already `active` or `deprecated`).

## A real EF Core bug found and fixed while building Step 5: `HasDefaultValue` + an enum whose "default" member isn't ordinal 0

- **Symptom**: `CreateFollowUpQuestionCommandHandler`'s own API test asserted the response's `Verdict` was `user_correct` and got back `pending` instead — despite the handler explicitly setting `Verdict = payload.Verdict` (confirmed `user_correct` via a debug trace) right before `SaveChangesAsync`.
- **Root cause**: `FollowUpQuestionConfiguration` had `builder.Property(x => x.Verdict).HasDefaultValue(FollowUpVerdict.pending)` — and EF Core's convention is that `HasDefaultValue(...)` **implicitly sets `ValueGeneratedOnAdd`** on that property unless told otherwise. For a newly-`Add`ed entity, EF Core treats a property whose current CLR value equals **the type's default** (for an enum, always its ordinal-0 member — `FollowUpVerdict.user_correct`, since `FollowUpVerdict` is declared `{ user_correct, user_incorrect, partial, pending }`) as "not explicitly set", omits it from the `INSERT` column list, lets Postgres apply the column's `DEFAULT` (`'pending'`), and then reads the DB-generated value back into the in-memory entity (Npgsql's provider does this via `RETURNING`) — silently overwriting the `user_correct` the handler had just assigned. `FollowUpVerdict.user_incorrect` (ordinal 1) never triggered this, which is why the sibling test with that verdict passed from the start and the bug went unnoticed until the specific `user_correct` path was exercised.
- **Why nothing else had hit this yet**: every *other* `HasDefaultValue(...)` enum column in the schema happens to have its designated "default" value **coincide with ordinal 0** (`CallStatus.pending`, `Visibility.Private`, `SubmissionStatus.draft`, `MasteryLevel.New`, `WeakPointStatus.active`, `OverrideStatus.observing`) — so the same silent-omission mechanism fires just as often, it just happens to substitute back the exact value the code already intended, making it invisible. **One more genuine landmine found by inspection, not yet exercised by any test**: `WeakPointConfiguration`'s `Priority` column defaults to `Priority.medium`, but `Priority` is declared `{ high, medium, low }` — `high` is ordinal 0, `medium` is not — so the day `Features/WeakPoints` (Step 6+) explicitly constructs a new `WeakPoint` with `Priority.high`, it would silently save as `medium` instead, exactly like `Verdict` did.
- **Fix**: added `.ValueGeneratedNever()` to all 10 of these enum property configurations (`FollowUpQuestion.Verdict`, `WeakPoint.{Status,Priority}`, `AiCallLog.Status`, `Question.Visibility`, `StandardOverride.Status`, `Submission.Status`, `{UserVocabReview,UserPatternReview,UserKnowledgePointReview}.MasteryLevel`) — the application always sets these explicitly at construction time (matching this codebase's own convention of setting `CreatedAt`/etc. in code rather than leaning on DB defaults), so EF should never treat any of them as store-generated. **Confirmed via `dotnet ef migrations add` that this produces an empty migration (no `Up`/`Down` operations)** — `HasDefaultValue(...)` (the actual DB-level `DEFAULT` constraint, still needed for the hand-run SQL seed scripts and any direct-SQL insert) is unchanged; only EF's own "is this store-generated" bookkeeping changes, which is a design-time-only concept with no DDL representation — so `AppDbContextModelSnapshot.cs` was updated to match (10 `.ValueGeneratedOnAdd()` annotations removed) but no new numbered migration file was kept.

- **Difficulty ratio (design doc §2's 简单30%/中等50%/困难20%) was never read anywhere.** `generation_policy` already had the right row seeded (`difficulty_distribution`, `{"easy":0.3,"medium":0.5,"hard":0.2}` — present in `seed_naati_ct_en_zh.sql`, which AGENTS.md's own "Known pitfalls" section already documents as run against Supabase; not independently re-verified via `psql` this session, so worth a quick `SELECT * FROM generation_policy WHERE policy_key='difficulty_distribution'` check before relying on it — the code has a safe 30/50/20 fallback either way, see below), but `GenerateQuestionCommand.Difficulty` was a required, always-caller-specified field with no code path that ever consulted the policy table. - **`CreateSubmissionValidator` had no TaskA/TaskB shape check for `Content`** — unlike `ImportUserQuestionValidator`'s `HaveConsistentTaskShape`, any valid JSON was accepted regardless of `TaskType`. Fixed: `HaveConsistentTaskShape` now requires TaskA's `Content` to be a JSON string and TaskB's to be a non-empty JSON array of `{positionStart, positionEnd, errorCategory, correctedText}` objects (this pins down the annotation shape the design doc only loosely specified as `{position,error_category,corrected_text}` — the project didn't have a settled convention for it before this).
- **A real stuck-submission bug**: if the AI reported a `band` outside grading_results' `1-5` CHECK constraint, or if anything else failed during the final persist step of `GradeSubmissionCommandHandler`, the submission could be left sitting in `Grading` forever — there's no `Grading→Grading` transition, so a stuck submission could never be retried. Root cause: entity construction + the final `SaveChangesAsync` happened outside any try/catch that would call `FailAsync`. Fixed by (1) widening the try/catch to cover the whole parse→validate→build→persist sequence, (2) adding an explicit band-range check to `ValidatePayload` so an out-of-range band is a clean rejection instead of a raw `DbUpdateException`, and (3) a defensive reset in the catch block: if `TransitionTo(Graded)` already ran in-memory before the failure (e.g. the final save itself is what threw), the in-memory status is reset back to `Grading` before calling `FailAsync` — otherwise `FailAsync`'s own `TransitionTo(GradingFailed)` would illegally see `Graded` as the "current" status (since nothing from a failed `SaveChangesAsync` actually persisted) and throw a second, more confusing exception on top of the real one. Covered by `SubmissionsControllerTests.Grade_rejects_an_out_of_range_band_and_marks_the_submission_grading_failed_instead_of_getting_stuck`.
- **Design doc §11.2's "模拟中途失败验证整体回滚" integration test was never written for Step 4.** Added `SubmissionRepositoryTests.A_constraint_violation_in_one_grading_result_rolls_back_the_whole_batch_including_valid_rows` — adds one valid and one CHECK-constraint-violating `GradingResult` in the same `SaveChangesAsync` call against real Testcontainers Postgres and confirms *neither* survives, proving one `SaveChangesAsync` call really is one all-or-nothing DB transaction rather than "the bad row gets rejected while the good one commits."

## Domain events & Step 6 downstream subscribers

Design doc §5's promise for `BE4`(Grading Orchestration Service): grading publishes one event, `BE7`/`BE8`/`BE12` (weak points / progress / review library) each subscribe independently, and a fourth future subscriber is "add an `EventHandler`", never "go change `GradeSubmissionCommandHandler`". Built and proven for real this session (2026-08-30), same day as the Step 5 work above.

- **`AggregateRoot` (Domain, still framework-free)** now carries `DomainEvents`/`AddDomainEvent`/`ClearDomainEvents` — a plain `List<object>`, not a MediatR type, so Domain still has zero package dependencies (design doc's own dependency-direction rule). `Submission`, `StandardOverride`, and `WeakPoint` are the three `AggregateRoot`s that currently raise events.
- **`Application/Common/DomainEventNotification<TDomainEvent>.cs`** is the only place a domain event touches MediatR — a generic `INotification` wrapper. `UnitOfWork.SaveChangesAsync` (Infrastructure) doesn't know the concrete event types at compile time, so it wraps each one via `typeof(DomainEventNotification<>).MakeGenericType(domainEvent.GetType())` + `Activator.CreateInstance` and publishes that. A handler subscribes to `INotificationHandler<DomainEventNotification<SubmissionGradedEvent>>`, not to `SubmissionGradedEvent` directly.
- **Dispatch order in `UnitOfWork.SaveChangesAsync`**: collect every tracked `AggregateRoot`'s pending events and clear them *before* calling `_context.SaveChangesAsync()`, then publish only *after* that save succeeds — a failed save never publishes anything for a transaction that didn't commit. A handler that itself calls `_unitOfWork.SaveChangesAsync()` to persist its own new aggregate (e.g. `WeakPoint` raising `WeakPointRecurredEvent`) goes through this exact same method recursively — no special-casing for nested saves, and no infinite loop risk since nothing currently subscribes to `WeakPointRecurredEvent`/`StandardOverrideActivatedEvent` (both are raised — by `WeakPoint` on a resolved→active flip, and by `StandardOverride` on both its activation paths — as forward-compatible hooks per the "adding a subscriber is free" design, but genuinely have zero listeners today).
- **The three `SubmissionGradedEvent` subscribers, and why each is scoped the way it is** (a user-requested clarifying discussion before writing any of this settled all three, since the design doc's own Step 6 roadmap line clashes with pieces of Steps 7/9 it also names — see each bullet):
  1. **`UpdateWeakPointsOnGraded`** (`Application/Features/WeakPoints/EventHandlers/`) — **⚠️ this bullet describes the original Step 6 form; the 2026-09-02 B1/B5 batches rewrote it substantially — read the "2026-09-02" section's "AI weak-point classification (B5)" subsection for current behaviour.** Originally: rule-based (no AI call), bucketed `error_list` rows by `"{DimensionName} - {ErrorCategoryName}"` per submission, upserted `weak_points`/`weak_point_occurrences`, and the §10.4 recurrence branch (`resolved`→`active`, `RecurrenceCount++`, `Priority=high`, `IsRecurrence=true` occurrence) was only reachable by manually flipping the status. **Now**: buckets against the curated `weak_point_catalog` (AI classifier first → `detection_source='ai'`, then the deterministic `default_dimension_key`/`default_error_category` rule → `'rule'`, then the legacy string), occurrences carry `error_list_id`/`snippet`/`detected_band`, and it runs a resolve sweep (active weak points not seen in the user's last 5 graded submissions → `resolved`) so recurrence is reachable in normal operation.
  2. **`UpdateProgressOnGraded`** (`Application/Features/Progress/EventHandlers/`) — **only ever touches TODAY's `progress_snapshots` row**, recomputed from source `grading_results` (not incremented in place — recomputing avoids the class of bug where an incremental average silently drifts from what a fresh query would show). Keyed on `(UserId, PeriodStart=PeriodEnd=today, DifficultyTier)`. `TrendNote`/`KeyTurningPoint` (AI-driven trend interpretation) and historical backfill across past periods are deliberately **not** built here — design doc §11.2 puts the real learning-curve analytics in Step 9's Hangfire job, and this handler never sets either field.
  3. **`ExtractKnowledgePointsOnGraded`** (`Application/Features/ReviewLibrary/EventHandlers/`) — was written as **the Step 6 "最小闭环" version, not Step 7's AI extraction**, and was never changed once Step 7 actually landed (see "Deep learning module (Step 7)" below): if the graded `Question` already has `SentencePattern`/`VocabExpression` rows linked via their `QuestionId` FK, upsert `user_pattern_review`/`user_vocab_review` (increment `TimesEncountered`) for this user. At the time this handler was written it was a no-op for almost every question (nothing populated those FK-linked rows yet) — it started doing real work the moment `GenerateDeepLearningContentCommandHandler` shipped, with zero changes needed here, confirming the "new capability needs no change to the consumer" shape the event bus was designed for (proven by `DeepLearningContentControllerTests.Grading_a_new_submission_after_deep_learning_content_exists_marks_its_patterns_and_vocab_as_reviewed`).
- **`WeakPoint` gained a DB-level uniqueness guarantee it didn't have before**: `WeakPointConfiguration` now has `ux_weak_points_user_category`, a unique index on `(UserId, Category)` — `UpdateWeakPointsOnGraded` looks the row up before deciding insert vs. update, and this is the backstop against two concurrent grading events for the same user/category racing into a duplicate row. Migration `20260830085658_AddWeakPointUserCategoryUniqueIndex` was generated via `dotnet ef migrations add` and, unlike the fully-hand-applied migrations elsewhere in this file, went through the normal `dotnet ef database update` path — **confirmed applied to the real Supabase DB by the user on 2026-08-30** (`dotnet ef database update` → "No migrations were applied. The database is already up to date.").
- **New read endpoint**: `GET /api/v1/weak-points?userId=&status=` (`ListWeakPointsQuery` → `WeakPointsController`) — the one piece of design doc §11.2's own Step 6 test list ("API测试(薄弱点列表接口)") that isn't just proving the event-bus wiring.

## Deep learning module (Step 7): isolated reference-translation generation, sentence patterns, vocab

Design doc §11.2's Step 7 line: "reference_translations独立调用生成、sentence_patterns/vocab_expressions". Built and proven the same day as Step 6 (2026-08-30).

- **`GenerateDeepLearningContentCommandHandler`** (`Application/Features/Questions/Commands/GenerateDeepLearningContent/`) is the AI-orchestration handler, same shape as `GenerateQuestionCommandHandler`/`GradeSubmissionCommandHandler`: create an `AiCallLog` row (`RequestType=AiOperationType.deep_learning`) + save immediately, build the prompt via `IExamConfigLoader`/`PromptRenderer` (unchanged infrastructure), call `ILlmClientResolver.GetActiveClientAsync()` (same DB-driven provider switch every other AI call goes through), parse the JSON response, validate it, persist, mark the `AiCallLog` success. Any failure marks the log `final_failure` and rethrows, mirroring every other AI-orchestration handler in this codebase.
- **Isolation is structural, not a prompt reminder — design doc §10.2 mirrored the other direction.** §10.2 already guarantees grading never reads `reference_translations`; this handler is the other half: its template model is **only** `{ TaskType, SourceText }` off the `Question` — there is no code path here that could pull in a `Submission`'s content, its `GradingResult`s, or `MeaningCheckpoint`s, so a generated reference translation can never be contaminated by (or leak into) any one user's specific answer. Proven for real, not just by inspection, by `DeepLearningContentControllerTests.Generate_is_isolated_from_grading_context_persists_content_and_is_idempotent_on_a_second_call`: it grades a submission whose `Content` carries a random marker string, then generates deep-learning content for the same question with a prompt-capturing fake client, and asserts the marker never appears in the captured prompt — the exact test design doc §11.2 calls for ("断言'参考译文生成请求'的实际payload里不包含评分相关上下文,验证隔离机制真正生效而非只是文档描述").
- **One AI call produces all three outputs together** (`referenceText`, `comparisonNotes`, `sentencePatterns[]`, `vocabExpressions[]`) — design doc §2.1 displays reference translation + sentence-pattern accumulation + vocab accumulation at the same "深入学习" flowchart step, so one call covers all three rather than three separate ones. `comparisonNotes` and each pattern's `breakdownSteps` are accepted as arbitrary JSON (`JsonElement`, stored via `.GetRawText()`) — same convention `Question.Brief` already uses — rather than a fixed shape, since design doc §6.9/§6.10 both type these columns as unstructured `JSONB`.
- **Idempotent per `Question`, not per `Submission`** — `reference_translations` has no `submission_id`/`user_id` column (design doc §6.9), only `question_id`, so a reference translation is generated once per `Question` and reused by every user who reaches that question's "深入学习" step afterward. `GenerateDeepLearningContentCommandHandler` checks `IReferenceTranslationRepository.GetByQuestionIdAsync` first and returns the cached row (`WasCached=true` on the result) without ever calling the LLM again if one already exists — proven by `DeepLearningContentControllerTests`' idempotency assertions (`FakeDeepLearningLlmClient.CallCount` stays `1` after a second call).
- **`comparison_notes` deliberately stays general, not per-user/per-submission — evaluated and decided against adding a field, user-requested review, 2026-08-30.** The design doc describes it as "与用户译文的对比说明" (comparison to *the* user's translation), but the table has no column to say *which* user/submission, unlike literally every other per-user/per-submission signal in this schema (`submissions`, `grading_results`, `error_list`, `follow_up_questions`, `weak_point_occurrences`, `user_pattern_review`, `user_vocab_review` all carry an explicit `user_id`/`submission_id` FK). That total absence, in a schema this consistent about the pattern everywhere else, reads as an intentional signal that `reference_translations` was meant to stay question-scoped, not a gap. Decision: `comparison_notes` stays general technique/pitfall commentary the AI writes alongside the reference text (already how `GenerateDeepLearningContentCommandHandler` implements it) — a literal per-submission diff is left to the frontend simply showing the user's own already-visible submission text next to the reference text, no additional AI-generated field needed for that. If a real product need for genuine per-submission comparison text ever surfaces, the additive fix is a new nullable `submission_id` column (or a separate join table) — cheap to add later and deliberately not built ahead of a real requirement (design doc §9.7's own YAGNI precedent).
- **New `AiOperationType` enum value: `deep_learning`** — added to the C# enum, the native Postgres enum (`ai_operation_type_enum`), and `prompt_templates.template_type`/`ai_call_logs.request_type` share this same enum, so no other schema change was needed. Migration `20260830093243_AddDeepLearningAiOperationType` adds the new label via `ALTER TYPE ... ADD VALUE` — **confirmed applied to the real Supabase DB by the user on 2026-08-30** (`dotnet ef database update`).
- **A new `prompt_templates` row was needed, same recurring reason as every prior step**: no `template_type='deep_learning'` row existed before this handler, because nothing consumed it. [add_deep_learning_prompt_template.sql](src/DeepLearning.Infrastructure/Persistence/Sql/add_deep_learning_prompt_template.sql) adds one `shared_methodology`/`translation` row supplying `{{ task_type }}`/`{{ source_text }}` and the JSON contract (`referenceText`/`comparisonNotes`/`sentencePatterns[]`/`vocabExpressions[]`) the handler parses — same hand-run-SQL convention as the question_gen/grading/followup rows. **Applied to the real Supabase DB by the user on 2026-08-30** — the Testcontainers test DB never runs this file either way; `DeepLearningContentControllerTests` seeds its own minimal marker-string `PromptTemplate` row directly, same convention as `SubmissionsControllerTests`' TaskB flawed-text test.
- **New endpoints on `QuestionsController`**: `POST /api/v1/questions/{id}/deep-learning` (generate-or-return-cached) and `GET /api/v1/questions/{id}/deep-learning` (404 if nothing has been generated yet for that question — `GetDeepLearningContentByQuestionIdQueryHandler` throws `NotFoundException` off `IReferenceTranslationRepository.GetByQuestionIdAsync` returning null).
- **Tests**: `Api/DeepLearningContentControllerTests.cs` — isolation + persistence + idempotency (one test), 404-before-generation (one test), structured-output rejection on an empty `patternName` (design doc §10.3's hard-constraint philosophy, one test), and Step 6+7 composition (one test — generates deep-learning content for a question, then grades a fresh submission for that same question and asserts `ExtractKnowledgePointsOnGraded` picked up the newly-linked `SentencePattern`/`VocabExpression` with zero code changes to that Step 6 handler).

## Reference-translation follow-ups (design doc §2.1 node `W`→`R`, added 2026-08-30, user-requested)

This section originally shipped as part of Step 7 flagging "a user disputing something about the reference translation isn't reachable yet" — closed the same day, after Step 7's own audit surfaced it as a real gap worth fixing rather than deferring.

- **Reuses the exact same follow-up mechanism as a grading dispute (design doc §2.1: node `W`'s "是" branch goes to the same node `R` node `Q`'s "是" branch does)** — same `CreateFollowUpQuestionCommandHandler`, same `POST /api/v1/follow-ups` endpoint, same verdict/`standardRevision` JSON contract, same observing→active `StandardOverride` path (auto count-based or manual). `OverrideScope.translation_reference` was already a legal enum value from Step 5 (§6.8), and `ValidatePayload` already accepted it generically (no taxonomy check, just non-empty `dimensionOrRule`/`revisedRuleText`) — it had simply never been exercised by any test, because nothing had a code path that could produce it meaningfully.

- **`add_followup_reference_translation_content.sql` replaces the shared_methodology/followup row as a version=2 update (deactivating version=1), not a second additive row** — same "new version, deactivate old" precedent as `fix_followup_exam_specific_prompt_template.sql`, chosen so all of this handler's content-injection logic and its one JSON output contract stay in a single template rather than being split across two rows whose relative render order would need to be reasoned about. The resulting `SeedReferenceLink` rows get `SimilarityReason = "manually specified by caller"` instead of the automatic path's `"same task type/category + difficulty=X"` string, so the traceability read (`GET .../seed-references`) still tells manual from automatic apart after the fact. `GenerateQuestionValidator` additionally caps the list at `MaxSeedQuestionIds` (5) and rejects duplicates/empty guids — pure rules, no DB access needed, so they live in the validator rather than the handler (unlike the IsSeedReference check above); see `GenerateQuestionValidatorTests.cs`. `IQuestionRepository` gained `ListByIdsAsync` for this lookup — a bulk-get, not a query filter, so it's a distinct method from `ListSeedReferenceCandidatesAsync` rather than a parameter on it. `CategoryId` is simply ignored when `SeedQuestionIds` is supplied (nothing left for it to filter).

Deliberately **opt-in per call, not a global switch** (design doc's own "不追求100%围绕薄弱点出题,否则出题会变得单一,也测不出其他方面有没有退步") — `Application/Features/Questions/Commands/GenerateQuestion/WeakPointTargetingSelector.cs` (pure/static, same `Select(weights/ratio, roll)`-takes-the-random-number-as-a-parameter testable shape as `DifficultyDistributionSelector`) is only consulted when the caller explicitly asks. ## Progress analytics (Step 9): Hangfire, weekly recompute + AI trend narrative, historical backfill

Design doc §11.2's Step 9 line: "`progress_snapshots`,Hangfire定时任务生成快照". Built 2026-08-31, same day as the Step 0-8 completeness audit above. **Cadence is weekly — user's own explicit decision** (asked because it directly drives both Hangfire's schedule and AI-call cost; the alternative considered was daily, rejected for cost).

- **First real use of Hangfire in this codebase** — `Hangfire.Core`/`Hangfire.AspNetCore`/`Hangfire.PostgreSql` added to `DeepLearning.Infrastructure.csproj`. `Infrastructure/DependencyInjection.cs` calls `services.AddHangfire(...).UsePostgreSqlStorage(...)` against the exact same `ConnectionStrings:DefaultConnection` everything else uses — no separate infra, no separate connection string to manage. `services.AddHangfireServer()` is also unconditional (runs in tests too, against the Testcontainers Postgres `ApiWebApplicationFactory`/`PostgresContainerFixture` already stand up — confirmed harmless: a `Cron.Weekly()` recurring job registered against a brand-new schedule doesn't fire until its next real weekly boundary, so no test run has ever seen it actually execute). `Program.cs` registers the actual recurring job (`RecurringJob.AddOrUpdate<ProgressSnapshotJob>("progress-snapshot-weekly", ..., Cron.Weekly)`) and gates `app.UseHangfireDashboard()` behind `IsDevelopment()` — same reasoning as Scalar/OpenApi: no auth/role system exists anywhere in this codebase yet to gate the dashboard behind in production.
- **`ProgressSnapshotJob.RunAsync`** (`Infrastructure/BackgroundJobs/ProgressSnapshotJob.cs`) is deliberately thin — pure iteration, zero business logic, same "controllers only bind + call `IMediator.Send`" convention extended to this codebase's one other entry point. For each active `ExamType` × each user with grading activity in the trailing 12 weeks (`IProgressRepository.ListUserIdsWithGradingActivitySinceAsync`) × each of the 3 `Difficulty` tiers × each of the trailing 12 ISO weeks (`ProgressWeekCalculator.TrailingWeeks`, oldest-first), it sends one `GenerateProgressTrendSnapshotCommand`. One unit throwing (logged, not rethrown) never aborts the rest of the weekly batch — proven by `Infrastructure/BackgroundJobs/ProgressSnapshotJobTests.cs` (pure, hand-rolled fakes for `IMediator`/`IExamTypeRepository`/`IProgressRepository`, no DB — this codebase has no mocking library, see `tests/.../Api/FakeLlmClient.cs`'s own precedent). **12-week lookback is a deliberate, documented bound** — an unbounded historical scan on a job that runs every week would grow more expensive run over run for no benefit, since every earlier week already got its own snapshot the first time the job ever saw it; re-running an already-populated week is a safe, idempotent no-op update (recompute-from-source, not increment), which is also what makes this same iteration cover both "this week's fresh snapshot" and "backfill any recently-missed week" with one code path.
- **`GenerateProgressTrendSnapshotCommandHandler`** (`Application/Features/Progress/Commands/GenerateProgressTrendSnapshot/`) is the one (user, difficulty tier, week) unit of work, and the only AI-orchestration handler in this codebase that deliberately splits into two independently-persisted phases instead of one all-or-nothing operation:
  1. **Recompute** (always succeeds, no AI): `ProgressSnapshotCalculator.Compute` — pure logic extracted from Step 6's `UpdateProgressOnGraded` (which now calls the same shared class instead of its own private `AverageBand` helper, so there is exactly one implementation of "how to average a period's `grading_results`" in this codebase, not two that could quietly drift) — recomputed from `IProgressRepository.GetGradingResultsForUserInPeriodAsync` for the given week's bounds (that method already took arbitrary `periodStart`/`periodEnd`, Step 6 just always called it with `periodStart == periodEnd == today`; Step 9 is the first caller to pass a real week-wide range). Zero grading results in that week → returns `Skipped=true`, no row written, no AI call spent (design doc gives no reason to manufacture an all-null row or spend an AI call narrating a week where nothing happened). Otherwise the weekly `ProgressSnapshot` row (`GetByUserPeriodAsync`, create-if-missing) is upserted and saved **immediately**, independent of the AI step below.
  2. **AI trend narrative** (best-effort): fetches up to 4 prior weeks via the new `IProgressRepository.ListRecentBeforeAsync`, builds a prompt (`IExamConfigLoader`/`progress_trend` operation type) carrying only the numeric aggregates for the current + prior weeks (`AiCallLog.RequestType = AiOperationType.progress_trend`, `RelatedId = UserId`), calls through `ILlmClientResolver`/`IAiCallRetryExecutor` (same retry sub-state-machine as every other AI call), parses `{trendNote, keyTurningPoint}`. **On failure, this is logged and swallowed, not rethrown** — the numeric snapshot already committed successfully in phase 1, and this runs unattended out of a weekly batch across every active user, so one user's AI hiccup must not roll back numbers that were already correct, and there is no synchronous caller waiting on an all-or-nothing response to reject. This is the one deliberate exception to this codebase's otherwise-universal "AI failure fails the whole operation" convention (`GradeSubmissionCommandHandler` et al.) — the justification is that this handler's failure mode genuinely differs in kind (unattended batch analytics vs. a user-facing synchronous request).
- **`AiOperationType.progress_trend`** — new enum value (C# + native Postgres enum via `ALTER TYPE ... ADD VALUE`, same mechanism as Step 7's `deep_learning` value). Migration `20260830145959_AddProgressTrendAiOperationType` — **confirmed applied to the real Supabase DB by the user on 2026-08-31** (`dotnet ef database update`).
- **A new `prompt_templates` row, same recurring reason as every prior step**: [add_progress_trend_prompt_template.sql](src/DeepLearning.Infrastructure/Persistence/Sql/add_progress_trend_prompt_template.sql) — additive `shared_methodology`/`translation` row supplying `{{ difficulty_tier }}`/`{{ current }}`/`{{ history }}` and the JSON contract (`trendNote`/`keyTurningPoint`) the handler parses. **Confirmed hand-run against the real Supabase DB by the user on 2026-08-31.** The Testcontainers test DB never runs this file either way (`GenerateProgressTrendSnapshotCommandHandlerTests` seeds its own minimal marker-string `PromptTemplate` row directly, same convention as every other content-injection test in this codebase).
- **Read endpoint**: `GET /api/v1/progress?userId=&difficultyTier=` (`GetProgressSnapshotsQuery` → `ProgressController`, same `_currentUser.UserId ?? userId ?? Guid.Empty` JWT-or-explicit-id precedence as `WeakPointsController`) — design doc §11.2's own Step 9 test list ("API测试(进度查询接口)"). Returns every snapshot row for the user (daily rows from Step 6's `UpdateProgressOnGraded` and weekly rows from this step's job coexist in the same table, distinguished only by how far apart `PeriodStart`/`PeriodEnd` are — no separate granularity column), oldest period first.
- **Self-audit fix (2026-08-31, same day, before this ever ran against real data): a real AI-cost bug found in `GenerateProgressTrendSnapshotCommandHandler` and fixed.** `ProgressSnapshotJob` re-sends every one of its trailing 12 weeks on every weekly run — that's deliberate (it's what lets one code path cover both "this week's fresh snapshot" and "backfill any week the job missed"), but the handler's first version called the AI unconditionally every time regardless of whether a week had already been narrated, so every historical week would have been re-narrated — and re-billed — on every single weekly run forever, directly undermining the whole reason cadence was set to weekly instead of daily (AI-call cost). Fixed by comparing the freshly-recomputed aggregate against whatever `ProgressSnapshot` already existed for that period: if a snapshot already has a non-empty `TrendNote` **and** the recomputed averages/pass-rate are bit-for-bit unchanged from what's already stored, the AI step is skipped entirely (the cheap numeric recompute+save still always runs). A genuine change to a past week's numbers (e.g. a late-graded submission landing in an already-processed week) still triggers a fresh narrative, since "unchanged" is checked on the actual recomputed values, not on whether the period was seen before. Covered by two new tests in `Integration/GenerateProgressTrendSnapshotCommandHandlerTests.cs`: re-running the exact same, unchanged week a second time makes zero additional AI calls; a new submission landing in an already-narrated week does trigger re-narration.
- **Known, documented limitation (not fixed — no second exam type exists yet to expose it, same YAGNI precedent as deferring `exam_type_id` on `Question`/`StandardOverride` elsewhere in this codebase): `ProgressSnapshotJob` loops over every active `ExamType` in its outermost loop, but `progress_snapshots` has no `exam_type_id` column** (matches design doc §6.14 exactly as specified — progress is tracked at `(user, difficulty_tier, period)` granularity only). With today's single active exam type this is harmless. The moment a second active `ExamType` exists, the job would call `GenerateProgressTrendSnapshotCommand` **twice** for the exact same `(user, tier, week)` — once per exam type — and since both calls resolve to the identical `ProgressSnapshot` row (no exam-type column to distinguish them), the second call's prompt template (loaded via that second exam type's `subject_category`/`exam_type_id`) would silently overwrite the first's narrative, and — worse — the self-audit fix above's "unchanged, skip" check means whichever exam type's command happens to run *second* in the loop wins the narrative permanently the first time both see identical numbers, with no signal that anything was skipped. Revisit this (most likely fix: derive the exam type set from something scoped to the user's actual activity, or accept one exam type's template as canonical for progress narration) before a second exam type goes live — flagged here so it isn't rediscovered as a confusing "why did this user's trend note change to oddly-templated text" bug report months from now.
- **Tests**: `Application/Features/Progress/{ProgressSnapshotCalculatorTests,ProgressWeekCalculatorTests}.cs` (pure, no DB — design doc §11.2's own "单元测试(统计计算逻辑)" ask), `Integration/GenerateProgressTrendSnapshotCommandHandlerTests.cs` (real Postgres — the zero-activity skip path, a two-week recompute+trend sequence proving the second week's AI prompt actually carries the first week's already-persisted numbers as history, the idempotent-skip-on-unchanged-data regression test and its re-narrate-on-genuine-change counterpart from the self-audit fix above, and the AI-failure-preserves-the-numeric-row path with `AiCallLog` ending `final_failure`), `Infrastructure/BackgroundJobs/ProgressSnapshotJobTests.cs` (pure — iteration count = exam types × users × tiers × weeks, one failing unit doesn't stop the batch, zero active exam types sends nothing), `Api/ProgressControllerTests.cs` (list/filter/empty contract, snapshot rows seeded directly via DbContext same convention as other read-only-endpoint tests).

## Directory structure and dependency direction

```
DeepLearning.Domain          <- no dependencies at all, pure C#
    ↑
DeepLearning.Application     <- depends on Domain
    ↑
DeepLearning.Infrastructure  <- depends on Application + Domain
    ↑
DeepLearning.Api             <- depends on Infrastructure + Application
```

- **Domain**: entities (`Entities/`), enums (`Enums/`), domain events (`Events/`), domain exceptions (`Exceptions/`), base classes and shared value objects (`Common/`). Doesn't reference any other project, and doesn't reference frameworks like EF/MediatR.
- **Application**: business use cases. `Features/<BusinessDomain>/Commands|Queries/<UseCaseName>/` holds the CQRS four-piece set; `Behaviors/` holds the MediatR pipeline; `Interfaces/` holds abstractions for repositories and external services (LLM, etc.); `Common/` holds cross-use-case shared types (pagination, etc.). Only depends on Domain — doesn't reference concrete implementations like EF Core or Npgsql.
- **Infrastructure**: where the interfaces defined by Application land. `Persistence/` is EF Core + Npgsql (DbContext, Configurations, Migrations, Repositories, UnitOfWork). If external services like an LLM API or email get added later, they should also get a new folder in this layer implementing Application's interfaces.
- **Api**: the ASP.NET Core entry point. `Controllers/` only does parameter binding and calls `IMediator.Send(...)` — no business logic. `Middleware/` holds cross-cutting concerns like global exception handling.

- The `__EFMigrationsHistory` table was manually created afterward (because the tables were created via schema.sql, not `dotnet ef database update`) — its column names follow the project's snake_case convention, written as `migration_id`/`product_version` (not EF's default PascalCase).
- A legacy issue was resolved on 2026-08-29: the primary key/foreign key/unique/CHECK constraints in `schema.sql` were written inline without explicit names, so the names Postgres auto-generated didn't match what the EF migration snapshot expected (`pk_*`/`fk_*`/`ix_*`/`ck_*`) — these have been manually aligned with `RENAME CONSTRAINT`. **For any future migration that needs to operate on a constraint by name, treat the names in [AppDbContextModelSnapshot.cs](src/DeepLearning.Infrastructure/Persistence/Migrations/AppDbContextModelSnapshot.cs) as authoritative.**

## Local dev database: switching between Supabase and a throwaway Docker Postgres (2026-09-05)

Full operating instructions live in [本地开发数据库操作手册.md](本地开发数据库操作手册.md). What belongs here is the
design and the incident behind it.

**The switch.** `launchSettings.json` has four profiles — `http|https (Supabase)` and `http|https (LocalDocker)`. The
LocalDocker ones override `ConnectionStrings__DefaultConnection` with an env var (env vars outrank JSON in the default
configuration order) and declare `DB_PROFILE=LocalDocker`. `dev.ps1 -Db LocalDocker` selects the profile.

**Why `DB_PROFILE` exists at all.** It is cross-checked against the connection string's host at startup by
[DatabaseTargetResolver](src/DeepLearning.Infrastructure/Persistence/DatabaseTarget.cs), which **refuses to start** on a
mismatch in either direction — LocalDocker pointing at a remote host, or Supabase pointing at this machine. That is not
defensive decoration; see the pitfall below. `GET /health/db` reports the resolved target (host/port/database, never
credentials) so "which database am I actually on" is answerable from outside the process.

**Preparing a fresh container — two paths, not equivalent:**

| | `sql bootstrap` | `db pull-reference` |
|---|---|---|
| source | the repo's `Persistence/Sql/*.sql` | the live Supabase rows |
| needs network | no | yes |
| includes hand edits made upstream | **no** | yes |
| `question_bank_categories`, `questions` | empty | populated |

The shared database is **not** the sum of the seed scripts — dimensions, error taxonomies and prompt rows have been
edited by hand and through the API since they were seeded (the same fact `SqlScriptRunner`'s forward-only apply path is
built around). Replaying the scripts yields a database that is internally valid but different from the one the app
actually behaves against: close enough to trust, wrong where it matters. So `db pull-reference` is the default and
`sql bootstrap` is the offline/CI fallback.

- `sql bootstrap` = `Database.MigrateAsync()` + every manifest script except those listed in
  [_bootstrap_skip.txt](src/DeepLearning.Infrastructure/Persistence/Sql/_bootstrap_skip.txt) (scripts that cannot run
  against an EF-built schema). Skipped ones are still recorded, so a later `sql apply` sees no gap. Fresh-DB-only
  (refuses a non-empty `_sql_scripts`) and local-only. Note **`sql apply` cannot build a new database** — it requires a
  baseline and refuses on an empty one, which is why this verb had to exist.
- `db pull-reference` ([ReferenceDataSync](src/DeepLearning.Infrastructure/Persistence/ReferenceDataSync.cs)) streams 15
  whitelisted tables with PostgreSQL binary COPY, piped connection-to-connection, so no value is parsed or re-formatted
  in between (enums, JSONB, timestamps arrive as stored). Columns are named explicitly on both sides — an EF-built
  schema and one grown by hand have no reason to share physical column order. FK triggers are off during the load
  (`question_bank_categories.parent_id` is self-referencing, so no row order is safe), and dependencies are closed
  **transitively**: asking for `question_category_map` pulls `questions`, which pulls `users`. It also baselines the SQL
  scripts afterwards, so a pull-only container is not a dead end for `sql apply`. Source connection string:
  `ConnectionStrings:ReferenceSource`.
- Whitelist boundary: **"what the question is" is copied; "who practised and how they did" is not.** `submissions`,
  `weak_points`, `grading_summaries`, `follow_up_*`, `progress_*`, `ai_call_logs` stay local and disposable. `users` is
  included only because `questions.created_by` points at it — not for login: the backend never issues or checks
  credentials, and `EnsureUserProfileMiddleware` creates the local row from a validated JWT on first request, which is
  also why `users.password_hash` stays empty and filling it in would accomplish nothing.

**Four structural reasons a temp-DB session cannot write to Supabase**, none of them convention: one write connection
only; the `DB_PROFILE` cross-check; a local-host check inside both commands (the write side is always
`DefaultConnection`, already proven local — no argument combination reverses the direction); and the source session is
opened with `SET default_transaction_read_only = on`, so a future edit that adds a write there fails at the server
rather than succeeding quietly.

**`seed_llm_provider_defaults_for_fresh_db.sql`** was appended for this work. An EF-migrated fresh database gets
`llm_provider_settings`/`llm_provider_models` in their final shape, so the historical create/migrate/drop chain for
those tables cannot run there (all of it is in `_bootstrap_skip.txt`, including `seed_llm_provider_settings.sql`, which
inserts into the long-removed `model` column). Rather than edit already-baselined history, the new script states the
desired end state and is a no-op on any database that already has it. Critically it inserts model rows with
`is_current = false` and promotes a default only where a provider has **no** current row: inserting `is_current = true`
directly would violate `ux_llm_provider_models_single_current_per_provider` on a database where someone had switched
models by hand, wedging `sql apply`. `LlmProviderSeedIsNoOpTests` pins every one of those cases. Applied to the real
Supabase DB on 2026-09-05 — `sql status` there now reports `applied: 49, pending: 0`.

**Docker data lifecycle** — three modes, one compose override each: `docker-compose.yml` alone (anonymous volume —
`docker compose down` leaves it dangling, use `down -v`), `+ docker-compose.ephemeral.yml` (tmpfs, loses data on
restart, zero disk), `+ docker-compose.persistent.yml` (named volumes that survive `down`).

**Test doubles (same round).** The 12 hand-written `ILlmClientResolver` implementations were replaced by one
NSubstitute helper, [LlmClientResolverSubstitute](tests/DeepLearning.UnitTests/TestInfrastructure/LlmClientResolverSubstitute.cs)
— three of them were already the identical generic wrapper written out three times, and the rest existed only so that
adding an LLM scenario also required adding a resolver class. This is **not** a move toward mocking generally: doubles
that carry real content (`FakeGradingPayloads`' boundary fixtures, the fixed-JSON clients) stay hand-written, and
nothing in persistence is ever substituted — every data test still runs against a real Postgres container.

## Order of steps for building a new CQRS feature

1. **Repository interface**: whatever persistence operations are needed, add them to `Application/Interfaces/I<Aggregate>Repository.cs`. One repository per aggregate root — don't split by table. The interface must be `public` (not `internal`), since the Infrastructure project implements it across assembly boundaries.
2. **Repository implementation**: `Infrastructure/Persistence/Repositories/<Aggregate>Repository.cs`, implemented directly with `AppDbContext`. **The repository itself never calls `SaveChanges`** — it's only responsible for querying/marking changes; persisting is handled uniformly through `IUnitOfWork`.
3. Register the new repository as `AddScoped` in `Infrastructure/DependencyInjection.cs`.
4. Build the four-piece set under `Application/Features/<BusinessDomain>/Commands|Queries/<UseCaseName>/`:
   - `<UseCase>Command`/`Query`: `: IRequest<TResult>`, pure data.
   - `<UseCase>Validator`: `: AbstractValidator<TCommand>`, auto-discovered by `AddValidatorsFromAssembly`; `ValidationBehavior` runs it automatically before the handler.
   - `<UseCase>Result`: the external DTO — don't return Domain entities across the boundary directly.
   - `<UseCase>CommandHandler`: `: IRequestHandler<TCommand, TResult>`, injects the repository + `IUnitOfWork`; after modifying the entity, call `await _unitOfWork.SaveChangesAsync(ct)` once, then map to Result and return. Queries generally don't need `IUnitOfWork`.
5. In the Api layer, the corresponding Controller injects `IMediator` and calls `await _mediator.Send(command)`.
6. If this feature needs to trigger domain events after saving: this already works (see "Domain events & Step 6 downstream subscribers") — call `aggregate.AddDomainEvent(new SomeEvent { ... })` on an `AggregateRoot` before `_unitOfWork.SaveChangesAsync(ct)`, and it's collected/dispatched automatically. To subscribe to an existing event, add a class implementing `INotificationHandler<DomainEventNotification<TEvent>>` (MediatR's assembly scan picks it up automatically, same as any other handler) — no change needed to whatever raises the event.

## Known pitfalls

- The existing empty-shell types/interfaces in `Application/Interfaces` and `Infrastructure/Persistence/Repositories` default to `internal`. Remember to change them to `public` when actually implementing the cross-assembly interface, otherwise the build fails (`IUnitOfWork` has already been changed — use it as a reference).
- Check the `.csproj` before adding a new project reference — when the project was first scaffolded, `Infrastructure` didn't reference `Application` and `Application` didn't reference `Domain`; this was only fixed on 2026-08-29. This means the skeleton's project references can't be fully trusted — verify for yourself before making changes.
- Before running `dotnet ef migrations add/list/database update` locally, set the `ConnectionStrings__DefaultConnection` environment variable first (the design-time factory doesn't read `appsettings.json`).
- There's no standalone design document file in the repo — the comment block at the top of `schema.sql` is currently the most complete written statement of the overall design intent, worth a look before changing the schema.
- [seed_naati_ct_en_zh.sql](src/DeepLearning.Infrastructure/Persistence/Sql/seed_naati_ct_en_zh.sql) contains the real, official NAATI CT English→Chinese rubric data (`exam_types`, `assessment_dimensions` with verbatim Band text, `error_taxonomies`, `generation_policy`, `prompt_templates`) and has already been run by hand against the Supabase dev DB. Like `schema.sql`, it is **not** auto-executed by the app or by migrations — it's checked in purely as the historical record of what production data already exists.
- **Never point `ApiWebApplicationFactory`/Testcontainers-based tests at the real Supabase connection.** Its `InitializeAsync` overrides `ConnectionStrings__DefaultConnection` via `Environment.SetEnvironmentVariable` (not `WebApplicationFactory.ConfigureWebHost`'s `ConfigureAppConfiguration` — that hook applies too late for a minimal-hosting `Program.cs` where `AddInfrastructure(builder.Configuration)` reads and captures the connection string before `builder.Build()` even runs). If that override is ever broken again, the tests will silently write real HTTP-created exam types/users/prompt templates into the real dev Supabase DB, exactly like they did once already on 2026-08-29 before this was fixed (cleaned up by hand afterward — check `exam_types`/`users`/`prompt_templates` for stray `test_*`/`user_*`/`dup_*`/`api test content` rows if this regresses).
- Repository/integration tests that build their own `DbContextOptions` (see `PostgresContainerFixture`) must build it **once and reuse it**, not per-call — EF Core spins up a new internal service provider per distinct `DbContextOptions` instance, and after ~20 of them in one process it trips `ManyServiceProvidersCreatedWarning` and starts throwing.
- **`NpgsqlEnumConfiguration.MapEnums` must reuse the same `NpgsqlNullNameTranslator`/`NpgsqlSnakeCaseNameTranslator` instances every call, not `new` them each time — this bit for real on 2026-08-29.** `AddDbContext`'s configure action runs once per scope (i.e. once per HTTP request, since `AppDbContext` is Scoped), so a fresh `new NpgsqlNullNameTranslator()` per call made every request's resulting `DbContextOptions` fingerprint distinct in EF's internal service-provider cache (these translators don't have value equality) — the API host silently built a brand-new internal DI container on *every single request* instead of reusing one, and the 21st request in one test process tripped `ManyServiceProvidersCreatedWarning` into a hard 500. It went unnoticed through all of Step 1 because the Api test suite stayed just under ~20 requests; adding Step 2's `QuestionsControllerTests` pushed it over. Fixed by making the translators `private static readonly` fields. If this class is ever "simplified" back to per-call `new`, the bug returns — and it's confusing to debug because the *symptom* shows up as an unrelated test failing (e.g. a null/empty GUID from a JSON-deserialized 500-as-ProblemDetails response), not as the 500 itself.
- Testcontainers needs a Postgres image with the `vector` extension available (this schema's migrations enable pgvector) — use `pgvector/pgvector:pg16`, not plain `postgres:16-alpine`.
- [docker-compose.yml](docker-compose.yml) maps Postgres to **host port 5433, not 5432** — this machine (and possibly others) already runs a native Postgres service on 5432. Docker's port-proxy doesn't error on the collision; `psql`/`dotnet ef` just silently connect to the native install instead of the container and fail with a baffling password-auth error. Verified working end-to-end on 2026-08-29: `docker compose up -d` + `dotnet ef database update` against `Host=localhost;Port=5433;...` creates all 30 tables (29 + `__EFMigrationsHistory`) cleanly from empty.
- **`dotnet run --launchProfile` is silently wrong — the real flag is `--launch-profile`.** dotnet run does not reject the misspelling; it forwards the unknown option to the application as a plain argument and then falls back to the FIRST profile in `launchSettings.json`. That profile is a Supabase one, so `dev.ps1 -Db LocalDocker` — the command whose entire purpose is "do not touch the shared database" — ran against production instead, booting normally and installing the Hangfire schema there, with no error anywhere. Caught on 2026-09-05 while verifying the switch. Two guards now exist: the `DB_PROFILE` cross-check (which refuses to start on exactly this combination) and `DevDatabaseSwitchConfigTests.Dev_script_uses_the_real_dotnet_run_flag_name`, which greps `dev.ps1` itself. This is the concrete case behind AGENTS.md #12 — a "port/service collision fails silently" of the config kind.
- **`docker compose down` does NOT delete the data.** The default compose file declares no named volumes, but the postgres/redis images declare `VOLUME` in their own Dockerfiles, so data lands on an *anonymous* volume. `down` removes only the container; the anonymous volume is left dangling on disk and a later `up` creates yet another one. The next container is genuinely clean, but disk usage grows silently — always `down -v`, or use the tmpfs (`ephemeral`) override which creates no volume at all.
- **`sql apply` cannot initialise an empty database** — it requires a baseline and refuses without one, by design (the real DB has hand edits that live in no `.sql` file, so replaying history over it must be impossible). A fresh container is prepared with `sql bootstrap` or `db pull-reference`, never `sql apply`. Both of those refuse anything that is not on this machine.
- **`_manifest.txt` is not a valid fresh-install order and never was.** `add_llm_provider_models.sql` and `upgrade_llm_provider_models_schema.sql` are alternatives to each other (the doc-comment in each says so), and both collide with the EF migration that now creates that table outright; `migrate_llm_provider_settings_model_to_catalog.sql` reads a column that same migration removed. That is what `_bootstrap_skip.txt` is for — the manifest stays the historical record, and the skip list carries the reason each entry cannot run against an EF-built schema. `SqlBootstrapTests` is what surfaced this; nothing had ever tested a fresh install before.
- [.github/workflows/ci.yml](.github/workflows/ci.yml) runs `dotnet build` + `dotnet test` on push/PR to `master`/`main`. GitHub-hosted Ubuntu runners have Docker preinstalled, so the Testcontainers-backed integration/API tests run there with no extra service-container setup. Not yet actually exercised on GitHub itself (would need a push) — the YAML has only been syntax-checked locally.
- **`llm_provider_settings`/`llm_provider_models` are tables whose real-Supabase creation is deliberately hand-run, by the user's own request** (they wanted DB schema changes reviewed/applied by hand rather than run by the agent) — unlike everything else, the EF migrations (`20260829092630_AddLlmProviderSettings`, `20260829110847_AddLlmProviderModels`) were generated locally so `dotnet ef` history and Testcontainers-driven tests stay correct, but were never applied to Supabase via `dotnet ef database update`. dotnet test DeepLearning.slnx --filter "Category=LlmIntegration"

Plain `dotnet test` with no filter runs everything including the live Claude call — don't do that in CI or on a loop. `.github/workflows/ci.yml` already uses the filtered form.

A `NU1903` warning about `SSH.NET` having a known high-severity advisory is expected and currently unresolved — it's a transitive dependency of `Testcontainers.PostgreSql` (used to talk to remote Docker contexts), not something this project calls directly, and it never ships in the Api project's output.

## Common commands

```bash
# Build (building the Api project also builds Infrastructure/Application/Domain)
dotnet build src/DeepLearning.Api

# EF-related commands need the environment variable set first, then run from src/DeepLearning.Api.
# The design-time factory reads ONLY environment variables, so unlike the running app it does not
# get the Username/Password merged in from User Secrets — spell the whole string out here.
export ConnectionStrings__DefaultConnection="Host=...;Port=5432;Database=postgres;Username=...;Password=...;SSL Mode=Require;Trust Server Certificate=true"
dotnet ef migrations add <MigrationName>
dotnet ef migrations list
dotnet ef database update

# Against the throwaway local container instead (no secrets involved):
export ConnectionStrings__DefaultConnection="Host=localhost;Port=5433;Database=deeplearning;Username=postgres;Password=postgres"

# Database CLI verbs — these run Program.cs and exit without starting the web host.
# See 本地开发数据库操作手册.md for the full table.
dotnet run --project src/DeepLearning.Api --launch-profile "http (Supabase)"    -- sql status
dotnet run --project src/DeepLearning.Api --launch-profile "http (LocalDocker)" -- sql bootstrap
dotnet run --project src/DeepLearning.Api --launch-profile "http (LocalDocker)" -- db pull-reference
```

**`dotnet ef` from the repo root instead of `src/DeepLearning.Api`** fails with `No project was found. Change the current working directory or use the --project option.` — migrations live in `DeepLearning.Infrastructure`, not `DeepLearning.Api`, so `dotnet ef` can't infer both projects from a bare invocation outside that folder. Either `cd src/DeepLearning.Api` first (then the commands above work as written), or stay at the repo root and add both flags explicitly:
```powershell
# PowerShell, from the repo root — equivalent to cd-ing into src/DeepLearning.Api first
# appsettings.Development.json now carries the host half only — add Username/Password from User Secrets
$env:ConnectionStrings__DefaultConnection = "<host half from appsettings.Development.json>;Username=<Supabase:Username>;Password=<Supabase:Password>"
dotnet ef database update --project src/DeepLearning.Infrastructure --startup-project src/DeepLearning.Api
```
